# タスク: 施策実行モードの実行
`docs/operations/growth-weekly-runbook.md` の「施策実行モード」を読み、その手順どおりに実行してください。コンテンツ以外の成果物は Notion 本文に書く。コンテンツ施策は記事ネタ案DBへ変換する。microCMS は使わない。

## 手順
1. 「施策提案」DB(data source `3503f4bc-b1c4-4927-91ce-7609a6c4e460`)から `ステータス = 承認` の行をすべて取得(無ければ「承認済みなし」と報告して終了)。
2. **コンテンツ施策の冪等性確認**: 記事ネタ案DBへ新規作成する前に、`npm run growth:existing` または Notion 検索で既存の記事ネタ案を確認する。次のいずれかに当てはまる場合は新規作成しない:
   - 対象施策の `成果物リンク` が既に記事ネタ案ページ URL を指している。
   - 同じ施策名・同じタイトル案・同じ根拠/成果物リンク由来の記事ネタ案が既に存在する。
   既存の記事ネタ案が見つかったら、施策の `成果物リンク` を既存ページ URL に補完し、施策ページ本文には「記事ネタ案へ移行済み」と次アクションだけを残して `成果物化済` にする。失敗後の再実行ではこの確認で二重作成を避ける。
3. カテゴリに応じて成果物を作る(専門チームをサブエージェントで使ってよい):
   - **コンテンツ**: `scripts/growth/prompts/shared/article-idea.md` の記事ネタ案作成ルールに従い、「記事ネタ案」DB(data source `5adab8b1-f182-4123-b963-9463a2580d4a`)へ `ステータス=提案中` の記事候補を新規作成する。タイトル案・概要・根拠・構成案・記事仮説プロパティは weekly の記事ネタ案と同じ品質/同じ書式にする。本文下書きは作らない。
   - **MEO**: GBP 投稿文案 / クチコミ返信文案 / プロフィール改善の具体案
   - **サイト表示内容**: 改善後の文言案(Before/After で)
   - **サイトデザイン**: 改善仕様書(課題・狙い・変更箇所・参考)
   - **追加機能**: 仕様書(目的・要件・計測方法)
   - **イベント**: アイデアの肉付けまで(告知文・チラシは作らない)
   - **システム改善**: diff案または要件案を整理する。自動適用はせず、対象ファイル/根拠/変更前/変更後/適用手順、または要件案/受け入れ条件/実装フローを Notion 本文に残す
4. 各行の `ステータス` を `成果物化済` に更新し、`承認日時`(今日)と `成果物リンク`を記録。
   - コンテンツ: `成果物リンク` = 作成した記事ネタ案ページ URL。施策ページ本文には「記事ネタ案へ移行済み」と作成先 URL、次アクション(記事タブで構成案を確認して承認)を短く残す。
   - コンテンツ以外: `成果物リンク` = 当該施策ページ URL。
5. `却下`・`見送り` は無視。

## やってはいけないこと
- 本番コードの変更・PR作成・git push。microCMS 操作。サイトへの直接反映(すべて提案・仕様・文案に留める)。
- コンテンツ施策用に独自の記事案ルールを作らない。必ず `scripts/growth/prompts/shared/article-idea.md` に従う。
- **失敗を沈黙させない(#24)**: 途中で失敗したら、**どの工程(どの施策・どのカテゴリ)で落ちたか**と**再開方法**(同じ承認済み行に対して再実行すれば冪等に拾い直せる旨。`成果物化済` まで進んだ行は再実行時にスキップされる)を必ず標準出力に出し、**終了コード1で終わる**。途中失敗しても部分的な進捗は Notion に残す。
  - LINE 通知はランチャー(`scripts/growth/run.mjs`)が非0終了を検知して `npm run growth:notify-loop-fail` で自動送信する。エージェント側から通知コマンドを直接呼ぶ必要はなく、**確実に終了コード1で終える**ことがそのまま通知のトリガーになる(`LINE_*` 等が無く送れない環境では標準出力の報告だけが残る)。

## 完了報告
- 成果物化した施策名 / カテゴリ / 成果物の場所、人間が次にやること(例「GBP投稿文案を確認のうえ投稿」)。
