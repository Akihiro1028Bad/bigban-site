<workflow>
1. `npm run growth:fetch` を実行し、`data/snapshots/<実行日>.json` を読む(対象週は自動=直近の確定週)。`errors` が空でないソースは推測で埋めず、その旨を明記。
2. **既存行の確定取得(必須・推測禁止)**: `npm run growth:existing` を実行し、その出力を**唯一のグラウンドトゥルース**として扱う(対象週レポートの作成済み/未作成、施策提案・記事ネタ案の全行と却下理由・検証結果)。
   - 「週次グロースレポート: 未作成」と出たら、**重複ではないので手順4のレポートを必ず新規作成する**(スキップ禁止)。「作成済み」のときだけレポート作成を省く。
   - 学習ループ: この出力に含まれる却下/見送りの判断者メモ・検証結果を読み、効かなかった方向・オーナーが嫌う方向は繰り返さない。
3. マーケターチーム: Task ツールでサブエージェントを**並列起動**し、SEO / ローカル(MEO) / CRO / ブランドの4視点で、6カテゴリ(コンテンツ / MEO / サイトデザイン / サイト表示内容 / 追加機能 / イベント)を分析。外部文脈は Web 検索で3層(地域・東京/全国・世界)を確認。
4. 週次レポートを Notion DB「週次グロースレポート」に1ページ作成(今週の数字+優先上位+論点+データ注意)。
5. 施策登録:
   - コンテンツ → 「記事ネタ案」DB に ステータス=提案中。各案には タイトル案・概要・優先度・**根拠**(なぜこの記事か=数字/クエリ名) に加え、**構成案**(導入→H2/H3→CTA)を「構成案」プロパティに記載する(承認画面で記事の中身を把握・レビューできるようにするため)。
     - **記事の仮説(#計測強化 S4・必須・空欄で出さない)**: 各案に「公開後にこの記事は成功か」を判断できる仮説を必ず付け、次の Notion プロパティに書く。承認画面の「記事の仮説」カードと、下書きモード(drafts.md)のブリーフ、公開後レビュー(growth:review-due)がこれを使う。
       - `記事タイプ`(select。次のいずれか1つ): `獲得`(来店/予約に直結) / `不安解消`(始める前の不安を消す) / `資産`(検索で長く読まれる土台) / `比較`(他競技・他手段との比較) / `イベント`(時期もの)
       - `狙う読者`(text): 誰の・どんな状況か(例「本八幡近隣・運動再開したい40代」)
       - `検索意図`(text): その読者が打つ検索と知りたいこと(例「本八幡 ピックルボール 始め方」)
       - `勝ち筋`(text): なぜこの記事が勝てるか=市場の空白＋施設の強み(例「市川×屋内は無競争＋一次体験」)
       - `想定CTA`(multi_select。記事内で促す行動): `Instagram`/`LINE`/`予約`/`アクセス`/`価格`/`問い合わせ` から該当を選ぶ
       - `成功指標`(text): 公開28日で見る判定基準(例「『本八幡 ピックルボール』で10位以内＋予約クリック5件/月」)
       - 仮説が立てられない=勝ち筋が弱い案は**そもそも出さない**(下の本命/補欠ルール)。
     - **構成案の書式(厳守・各セクション=見出し＋1行説明)**: 各セクションを「`## 見出し`」の行＋**直後の1行にそのセクションで書く内容の一言**で表す。セクション間は**空行**で区切る。承認画面はこの書式をセクション単位でパースして表示する。例:
       ```
       ## 市川でできる場所は3つ
       屋外コート・体育館・屋内専用の違いを公平に整理する

       ## 屋内専用という選び方
       天候に左右されない利点を具体例で書く
       ```
       見出しは `#` で始める(`#` の数は1〜6・通常は `##`)。説明は1行で簡潔に(無理なら見出しのみでも可)。タイトル盛り・未確定情報の断定はしない(§13/§14/§15)。
     - **狙い目テーマ(市場の空白・優先的に提案)**: 競合調査では「市川/本八幡/千葉 × 屋内」の読み物がほぼ無競合だった。次の手薄な領域を優先する: ①ローカル一次体験(本八幡で始める/体験ルポ) ②屋内施設の体験価値(全天候・夜可・空調) ③始めた後の継続・上達・仲間づくり(市場が「入門」で止まっている) ④ラケット競技(テニス/卓球/バド)経験者の移行ガイド ⑤シニアの健康(施設の実体験ベース・効果は断定しない=§5) ⑥一人参加の不安解消 / 法人・昼活利用。土台(cornerstone)になる総合ガイドは §2 のとおり長め(3,000〜5,000字)で。
   - その他5カテゴリ → 「施策提案」DB に ステータス=未処理、週キー(例 `2026-W24`)・施策ID(例 `2026-W24-MEO-01`)付き
   - **重複防止**: 手順2の `growth:existing` 出力に載っている行のみを既存とみなす。同一週キー・同一施策名・既出・却下済みだけを再作成しない(出力に無いものは未作成なので作成する)。先週以前で未処理のまま残った行は見送りに更新。
   - **構成案修正中の行は触らない(競合回避・Epic #40)**: 「記事ネタ案」で `修正ステータス` が `依頼中`/`処理中`/`提示中` の行は、ユーザーが承認画面で構成案を直している最中なので、**その行の `構成案` を書き換えたり見送りに更新したりしない**(上書き事故を防ぐ)。`修正ステータス` が `なし`/`失敗`/未設定の行のみ通常どおり扱う。
6. 各カテゴリ最大5件・**質が量に優先**(根拠の薄い施策は出さない。無ければ少数でよい)。
   - **コンテンツ(記事ネタ案)は「量より仮説」(#計測強化 S5)**: 件数を埋めることを目的にしない。**本命1件＋補欠2件**を基本とし、上の「記事の仮説」が立つ・勝ち筋が明確な案だけを出す。仮説が弱い/根拠が薄い案は1件も出さなくてよい(無理に5件にしない)。本命は最優先テーマ(market gap×施設の強み)から選ぶ。
</workflow>
