<workflow>
1. `npm run growth:fetch` を実行し、`data/snapshots/<実行日>.json` を読む(対象週は自動=直近の確定週)。`errors` が空でないソースは推測で埋めず、その旨を明記。
   - `growth:fetch` 出力の `trend` 節(直近4週の週次系列+4週移動平均)を読み、前週比(2点)ではなくトレンドで増減を判断する。`trend.weeks < 4` のときは `trend.note` の「参考値」を尊重し、断定を避ける。
   - 指標は sessions/activeUsers と `ga4.ctaEvents` のイベント別値(GA4)・clicks/impressions/ctr/position(GSC)を見る。**keyEvents合計を予約数とみなさない**。
2. **既存行の確定取得(必須・推測禁止)**: `npm run growth:existing` を実行し、その出力を**唯一のグラウンドトゥルース**として扱う(対象週レポートの作成済み/未作成、施策提案・記事ネタ案の全行と却下理由・検証結果)。
   - 「週次グロースレポート: 未作成」と出たら、**重複ではないので手順7のレポートを必ず新規作成する**(スキップ禁止)。「作成済み」のときだけレポート作成を省く。
   - **避ける学習(却下理由の一般化)**: この出力に含まれる①施策提案の却下/見送りの判断者メモ・検証結果、②記事ネタ案の `却下理由`・`公開後判定=要改稿` の理由(出力に併記される)を読み、**理由を一般化して同じ失敗パターンを繰り返さない**。個別タイトルの回避に留めず、理由から共通の落とし穴(例: 需要が薄いニッチ・一次情報が出せないテーマ・競合が強すぎるクエリ)を抽出し、次のネタ選定でその型を避ける。効かなかった方向・オーナーが嫌う方向も同様に避ける。
   - **記事タイプ学習(#221/#286・必須)**: 出力末尾の「公開済み記事の成績サマリ(記事タイプ別)」を読み、**成功率・判定済み母数・未判定率**を必ずセットで確認する。成功本数だけで優先しない。判定済み3本未満は「探索中」であり本命と確定しない。たとえば 5/20 と 2/2 を率や本数だけで自動順位付けしない。公開後日数・計測期間・views実測母数・impressions実測母数の**観測条件**が揃わない型は直接比較しない。未計測と実測0を分け、比較不能なら判断保留とする。検索反応は流入指標であり、1表示1クリックのような低サンプルを成果や勝ちと断定しない。予約意図・LINE・Instagram・その他CTA・記事帰属実予約は分け、freshな記事帰属実予約を優先し、予約意図は代理指標と明記する。公開済みが0本のときは従来どおり市場の空白×施設の強みで選ぶ。
   - **記事単位の打ち手(改善6・必須)**: 出力の「公開済み記事の判定ラベル(記事単位)」節を読み、各ラベルを次の施策へ変換する材料にする。**CTR弱い→タイトル/description 改善ネタ、順位あと少し→リライト/内部リンク強化施策、読まれるが予約意図弱い→予約導線改善施策、要改稿→改稿提案**。ラベルは機械判定の参考値であり、実際に施策化するかは勝ち筋(市場の空白×施設の強み)と成功指標で最終判断する。ラベルは記事ネタ案(リライト系はコンテンツ)または施策提案(内部リンク/CTA/description はサイト系カテゴリ)に振り分ける。
   - **コールドスタート実験枠**: `growth:existing` で **公開済み記事が0件**かつ**生きている記事案も0件**のときだけ、通常の本命/補欠枠とは別に、GSC実データのある検索機会から記事案を**最大1件**提案してよい。詳細は `shared/article-idea.md` の「コールドスタート実験」を正典とする。`根拠` 先頭に `【コールドスタート実験】` を付ける。すでに実験案が進行中、または**観測中の実験記事**がある場合は追加しない。公開後の `公開後判定` が28日レビューで確定するまで、その実験記事からの**派生案を出さない**。
   - **オーナー手入力の取り込み(改善案#4)**: 出力の「オーナー手入力(実 KPI)」節を読み、**予約件数/LINE友だち数/IGフォロワー数/口コミ件数・平均評価があれば分析に組み込む**。成功指標の分母(実予約・SNS 成果・口コミ)にこの実数を接地させ、MEO 提案は口コミ実データに基づく。「手入力データなし」のときは**推測せず**従来どおり GA4/GSC と Web 検索だけで分析し、その旨をレポートのデータ注意点に明記する。
3. **学習ログの取得(システム振り返りの一次データ)**: `npm run growth:learning-log:recent` を実行し、直近4週の学習ログ(種別別件数・対象別ヒートマップ・画像リトライ上位・失敗モード頻度)を読む。学習ログが空(DS 未設定/0件)なら従来動作とし、推測でシステム改善提案を出さない。weekly が実行してよいのは引数無しの `growth:learning-log:recent` のみで、`-- recent 8` 等の可変引数は人間の手動調査用。手順2の「避ける学習」「伸ばす学習」には、編集領域ヒートマップ(毎回直される領域)・採否の採用観点・不採用ヒートマップ(ユーザーに却下されやすい指摘の型を把握し、同型の指摘を避ける)・画像リトライ多発スタイル・失敗モード頻度を併用する。編集ヒートマップで毎回直される領域は「避ける」側へ、採用観点で伸びている型は「伸ばす」側へ寄せる。
4. **予約ファネル分析(提案より先に必須)**: `scripts/growth/prompts/shared/growth-goals.md` に従い、データ欠損・計測期間・参考値を確認してから、`認知 → 興味 → 予約意図 → 予約完了 → コート稼働 → 再予約・継続` の順に診断する。
   - 成果判断の優先順位は **freshな記事帰属実予約 > freshな施設全体実予約または同週のオーナー手入力 > 記事別予約意図（代理指標） > 判断保留**。実予約が欠損または古い場合だけ予約意図を代理指標にする。
   - `reservation_click` と `reserve_entry_click` だけを予約意図に含める。LINE・Instagram・その他CTAは予約意図および実予約から分離し、予約成功へ加算しない。
   - 実予約数と販売可能枠が揃わない場合はコート予約率を算出しない。`/reserve` 到達や予約 CTA は「予約意図率」等の代理指標として明記する。
   - 事業目標への影響と根拠が大きいボトルネックを**最大3件**に絞る。各ボトルネックに「確認できる事実 / 原因仮説 / 反証材料 / 不足データ」を付け、反証材料が強い仮説は採用しない。
5. マーケターチーム: Task ツールでサブエージェントを**並列起動**し、SEO / ローカル(MEO) / CRO / ブランドの4視点で、手順4のボトルネックを解消する方法を6カテゴリ(コンテンツ / MEO / サイトデザイン / サイト表示内容 / 追加機能 / イベント)から分析。外部文脈は Web 検索で3層(地域・東京/全国・世界)を確認。各所見は「対象ファネル / ボトルネック / 発見 / 根拠 / 推奨施策 / 予約への作用 / 確度」に圧縮する。
6. **システム振り返り**: マーケターチーム分析に加えて、学習ログ + 既存信号(成績データ・公開後判定・却下理由)から次の4領域を分析する。
   - **①記事の質**: `編集`イベントの傾向(どの領域が毎回直されるか)・`採否`の採用観点から、プロンプト(`scripts/growth/prompts/*.md`)または文体ガイド(`docs/operations/growth-article-style.md`)の具体 diff 案を作る。対象ファイルの現行テキストを Read で確認し、変更前後を明示する。
   - **②運用効率**: `工程失敗`の頻度(どのモードがよく落ちるか)・`画像試行`のリトライ多発(どのスタイルが崩れやすいか)から、設定値の diff 案または手順の施策文を作る。
   - **③ツール機能**: 編集差分・採否の傾向から、機能開発の要件案(何を・なぜ・受け入れ条件の骨子)を作る。実装は通常フロー(spec→計画→実装)へ渡す前提で、施策には要件案だけを書く。
   - **④グロース施策の強化**: 既存 weekly の担当。学習ログを材料に既存の6カテゴリ提案を厚くする(新カテゴリは作らない)。
   - ①〜③の改善は「施策提案」DB に `カテゴリ=システム改善`・`-SYS-` 施策 ID で登録する。仮説・成功指標・検証予定日は既存施策と同じ書式で必須。diff 案/要件案はページ本文に書き、SI2 の `buildSystemProposalBlocks` と同型の構造(対象ファイル/根拠/変更前/変更後/適用手順、または要件案/受け入れ条件/実装フロー)に従う。効果を測れる仮説が立たない場合は0件でよい。
7. 週次レポートを Notion DB「週次グロースレポート」に1ページ作成。本文は「LINE要約 / KPI状況 / 最大ボトルネック(最大3件) / 今週の優先施策 / 日本一に向けた評価軸 / 論点 / データ注意」の順にする。「日本一」は断定せず、比較不能な軸は `未計測` または `比較データ不足` と書く。
   - **LINE要約(最上部・LINE通知が最優先で表示)**: 見出しは `LINE要約`(heading_2 または heading_3)、本文は段落または箇条書き。
     - **3〜5行・各100字以内**。非エンジニアのオーナーが LINE で読む前提の、専門用語を避けた平易な日本語。
     - 1行目は「今週の結論」(例:「検索流入は伸びたが予約導線への到達が弱い週でした」)。
     - 残りの行は「なぜそうなったか」「来週どう動くか」を書く。
     - **数字の羅列はしない**(指標の数字は LINE 通知側が別途表示する)。ここは意味づけと打ち手だけを書く。
8. 施策登録:
   - コンテンツ → 記事が有効なボトルネックに限り、「記事ネタ案」DB に `ステータス=提案中` の記事候補を作る。タイトル案・概要・優先度・根拠・構成案・記事仮説プロパティは、`scripts/growth/prompts/shared/article-idea.md` の共通ルールに従う。
   - コンテンツ以外カテゴリ → 「施策提案」DB に ステータス=未処理、週キー(例 `2026-W24`)・施策ID(例 `2026-W24-MEO-01` / `2026-W24-SYS-01`)付き
     - **施策の仮説(改善案#5・記事S4と対称・空欄で出さない)**: 各施策に効果測定できる仮説を必ず付け、任意プロパティに書く(未追加でも登録は動く=欠落耐性)。承認画面と施策版レビュー(`growth:proposal-review-due`)がこれを使う。
       - `仮説`(text): この施策で何がどう良くなるか＋根拠(どの数字がそう示すか)。
       - `成功指標`(text): 効いたと判断する基準と測る面(GA4/GSC/GBP/予約 等。例「GBP経由アクション +20%/月」)。
       - `検証予定日`(date): いつ成功指標を突き合わせるか(承認/着手からの目安・例 28日後)。
       - 効果を測れない(仮説・成功指標が立たない)施策は**そもそも出さない**(質が量に優先)。
   - **重複防止**: 手順2の `growth:existing` 出力に載っている行のみを既存とみなす。同一週キー・同一施策名・既出・却下済みだけを再作成しない(出力に無いものは未作成なので作成する)。先週以前で未処理のまま残った行は見送りに更新。
   - **構成案修正中の行は触らない(競合回避・Epic #40)**: 「記事ネタ案」で `修正ステータス` が `依頼中`/`処理中`/`提示中` の行は、ユーザーが承認画面で構成案を直している最中なので、**その行の `構成案` を書き換えたり見送りに更新したりしない**(上書き事故を防ぐ)。`修正ステータス` が `なし`/`失敗`/未設定の行のみ通常どおり扱う。
9. **提案品質ゲート**: 各提案の既存プロパティ `根拠` / `仮説` / `成功指標` / `検証予定日` / `確度` / `想定アクション` に、対象ファネル、解消するボトルネック、予約への作用、根拠、検証方法、人間の次アクションが判断できる内容を書く。DB スキーマは追加しない。
   - 各カテゴリ最大5件・**質が量に優先**(根拠の薄い施策は出さない。無ければ少数でよい)。
   - **コンテンツ(記事ネタ案)は「量より仮説」(#計測強化 S5/#286)**: 件数を埋めることを目的にしない。**本命1件＋補欠1件＋探索1件**を基本とし、上の「記事の仮説」が立つ案だけを出す。探索枠は `sampleStatus=exploring` の型があり、**同型の生きている記事案・観測中記事がない**場合だけ使う。未判定率が高い型は追加投稿より判定待ちを優先してよい。適切な探索仮説がなければ探索枠を含めて件数を埋めない。全型が探索中なら仮の本命を断定せず、観測条件と仮説を明記する。
   - **コールドスタート例外**: 上記で通常案が0件でも、手順2の条件を満たす場合は実験枠を最大1件だけ出す。コールドスタート実験枠は本命/補欠/探索とは別契約とし、観測完了前に次を積み増さない。
</workflow>

<reporting>

- **却下再提案の件数(#221・学習が効いている証拠)**: 今回の提案のうち、`growth:existing` の出力で**却下/見送り済みだった方向を再提案してしまった件数**を数えて報告する(理想は0件)。0件でない場合はどの案がどの過去却下と重なるかを1行で添える。記事タイプ別の成功率・母数・未判定率・観測条件を確認したか、本命/補欠/探索をどう配分したかも1行で報告する。
</reporting>
