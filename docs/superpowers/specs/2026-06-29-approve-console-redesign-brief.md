# 承認コンソール 0ベース再設計 — ブリーフ（設計合意書）

- 日付: 2026-06-29
- 対象: グロースループの「承認画面」プロトタイプ（現 `src/app/growth/approve-proto/`）
- 種別: 0ベース UI 再設計の**ブリーフ＋進め方の合意**（具体UI設計はこの後のデザイナーチームが生成する）
- ステータス: ガードレール合意済み。デザイナーチーム（ステージ1）はユーザーの合図で起動する。

---

## 1. 目的

AIグロースループの承認画面を **0ベースで再設計**し、「かなり使いやすい今どきのリッチUI」へ刷新する。
あわせて **無駄な機能の削ぎ落とし / 必要な機能の追加 / 既存機能のグレードアップ** を行う。
具体的なUI設計（IA・ビジュアル・詳細仕様）は、プロのUIデザイナーを模した**マルチエージェントのデザイナーチーム**が段階的に生成し、各段でユーザーが承認する。

## 2. ガードレール（合意事項）

| 項目 | 合意 |
|---|---|
| 北極星（最優先） | **バランス** — ワークフロー効率 × 信頼・品質 × 見た目の現代化を高次元で両立。トレードオフは都度デザイナーが最適解を出す。 |
| 大胆さ | **0ベースで再構築OK** — 情報設計・ナビゲーション・コア承認フロー・機能の増減まですべて俎上。今のIAに縛られない。 |
| 聖域（不可変） | **pull型の非同期思想のみ**。承認画面は「依頼を書くだけ」で、重い処理は常時稼働PCのループが拾う。構造上の必然として維持する。それ以外（承認フローの形・house style・5面ナビ・キーボード中心操作・画面分割など）はすべて再検討可。 |
| 美的方向 | **チームが2〜3案を実モックで提示 → ユーザーが選択**。事前に固定しない。 |
| 機能の削ぐ/残す/追加 | **チームが提案 → ユーザーが採否判断**。 |
| スコープ | 新ルート **`approve-proto2`（仮）** に0ベース実装。現 `approve-proto` は温存し、見比べ可能にする。 |

### 制約
- 技術: React + Next.js App Router + Tailwind CSS v4 + framer-motion。scoped CSS（`proto.css` 相当）/ CSS変数。
- データ: モックのみ（実API・実画像生成なし。モックのグラデ/SVGで見た目表現は可）。
- 利用者: **非エンジニアの運用担当者**。認知負荷が低く迷わない誘導重視。
- デバイス: デスクトップ主、ただしレスポンシブ（モバイル〜デスクトップ）対応必須。
- 品質: TypeScript strict / `any`禁止 / `import type` / アクセシビリティ（キーボード操作・aria・prefers-reduced-motion）。
- 検証: ユーザーがブラウザで動作確認。tsc/eslint クリーン・コンソールエラーゼロを維持。

## 3. 現状インベントリ（削ぐ/残す/追加の土台）

現 `approve-proto` の機能一覧（再設計の出発点。チームはこれを批判的に再構成してよい）:

- **ナビ5面**: 施策(proposal) / 記事=承認(approve) / プロンプト / 成績 / 公開キュー
- **詳細パネル4クラスタ**: 構成案 / プレビュー / 校正(本文コメント+修正案+アドバイス) / 素材(画像+プロンプト)
- **承認アクション**: 承認 / 却下 / 修正を依頼 / 構成からやり直す / 公開予約
- **施策トリアージ**: 承認=記事化 / 保留 / 却下(理由) / 仮説カード / 施策フォーム
- **校正系**: 修正ループ(往復) / 本文行コメント / アドバイス依頼(失敗パス) / 公開前チェック(段階ガード)
- **素材系**: メディアライブラリ / 画像指示の新設計（house-styleロック＋「オフ/おまかせ/指定」＋行為一言＋ライブプレビュー）
- **計測**: 成績ボード（GSC検索成績・行動ラベル・スパークライン） / 公開キュー（プル型予約・past-due）
- **操作系**: コマンドパレット(⌘K) / カンバン⇄リスト切替 / 一括操作 / 表示密度・ブランド配色トグル / キーボード操作(J/K/A/R/E/X/1-4)
- **状態系**: ローディング/空/エラー/ポーリング失敗バナー
- **横断対応（直近）**: アクセシビリティ（reduced-motion / モーダルdialog化 / focus-trap / tab↔tabpanel） / フルレスポンシブ

## 4. 進め方（段階ゲート）

各 ★ でユーザーが承認してから次へ進む。手戻りを最小化する。

1. **ステージ1: IA/UX再設計チーム**
   - 入力: 本ブリーフ＋現状インベントリ。
   - 処理: 複数デザイナーが0ベースで「ナビ/画面構成・コア承認フロー・削ぐ/残す/追加」を提案 → 審査パネルで比較 → 統合。
   - 出力: 推奨IA（ナビ構造・画面遷移・主要フロー）＋機能の増減リスト＋根拠。
   - ★ ユーザーが推奨IAを承認（修正可）。
2. **ステージ2: ビジュアル方向チーム**
   - 処理: 2〜3の美的方向を**実モック**（HTML/SVGウィジェット等）で提示。
   - ★ ユーザーが方向を選択。
3. **ステージ3: 統合詳細仕様**
   - 勝者IA × 選定ビジュアルを、コンポーネント構成・状態・インタラクション・文言・データ型まで具体化。
   - ★ ユーザーが最終確認。
4. **ステージ4: 実装**
   - `approve-proto2` に面ごとに実装し、ブラウザ検証（tsc/eslint/コンソール）。

## 5. ステージ1 デザイナーチームへのブリーフ（骨子）

- **問い**: 非エンジニア運用者が週次で多数のAI生成記事を「迷わず・速く・安心して」承認/却下/修正依頼するための最良のIAは何か。0ベースで考えよ。
- **必達**: pull型（承認画面=依頼を書くだけ）を壊さない。バランス（効率×信頼×現代性）。
- **求める出力**: ① ナビ/画面構成（現5面は前提にしない） ② コア承認フローの再設計 ③ 削ぐ機能・統合する機能・追加すべき機能とその根拠 ④ 主要画面のワイヤー級スケッチ（テキスト） ⑤ トレードオフ。
- **多様な視点**: 効率最優先 / 信頼・品質最優先 / 情報密度最優先 / ミニマル削ぎ落とし など、思想の異なる複数デザイナー＋審査パネル＋統合。
