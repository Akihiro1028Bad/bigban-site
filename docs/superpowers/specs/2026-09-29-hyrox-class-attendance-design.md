# HYROX DAISUKE CLASS 参加者通知 設計書

- 作成日: 2026-09-29
- 状態: 設計確定(オーナー承認済みの内容を文書化)。実装計画は `docs/superpowers/plans/` に別途作成する
- 目的: 関吉コーチの HYROX TRAINING @ DAISUKE CLASS の参加者を人単位で記録し、開催当日の朝にコーチ入りの LINE グループへ「今日の参加者・何回目・所見」を送る
- 前提: 早朝ピックル リピーター可視化(`feature/early-morning-repeaters`、設計書 `2026-09-29-early-morning-repeaters-design.md`)のマージ後に、そのブランチの上に積んで実装する。台帳の読み取り・Notion 書き込みの部品を流用する

## 1. 背景

- DAISUKE CLASS は LaBOLA のイベント(スクール)として受け付けており、予約は毎朝の「予約メールチェック」ルーチンが Notion「Labora 予約台帳」へ記帳している
- 2026-09-29 まで台帳にイベント名の列がなく、料金プランの文言(回ごとに表記が違う)からしかクラスを判別できなかった。同日、台帳に `イベント名` 列を追加し、予約メールチェックを「本文の `THE PICKLE BANG THEORY` の次の行をイベント名として記帳する」よう修正した。過去のイベント予約 173 件も同日に Gmail から埋め戻し済み(173/173、空欄 0、日時の不一致 0)
- 実在のイベント名の例: `HYROX TRAINING @ DAISUKE CLASS` / `HYROX TRAINING @ DAISUKE CLASS ビギナーの部` / `HYROX TRAINING @ DAISUKE CLASS ダブルスクラス`(表記は回によって揺れる)
- 開催は平日(水・金)19:00 ビギナーの部・20:00 通常回、週末は 15:00 ダブルス・16:00 通常回など。同じ日に複数の回がある

## 2. ゴールと非ゴール

**ゴール**

1. DAISUKE CLASS の参加を人単位・回単位で Notion に記録する(分析用の参加記録を含む)
2. 開催日の 8:45 に、コーチ入りの LINE グループへ当日の全回の参加者・通算の何回目・所見を送る(所見は1行。初参加の人だけ利用歴の行を足して2行)
3. 所見で、DAISUKE CLASS 以外の施設利用歴(HYROX 系イベント・HYROX エリア貸切・ピックル)から来た人を分かるようにする
4. Mac が起動していなくても通知は届く

**非ゴール**

- 体験会・モーニングクラス・ミニシミュレーション等を通知対象にすること(利用歴として参照するだけ)
- 1件の予約で複数人が申し込んだ場合の同行者の把握(台帳に名前がない)
- 節目・リワードの管理(今回は依頼なし)
- Web サイト・Artifact での公開表示

## 3. 構成

```
[クラウドルーチン] 毎日 08:45 JST(予約メールチェック 08:08 の記帳の後)
  リポジトリ(develop)のチェックアウトで
  1. npm ci
  2. npm run hyrox:sync        ← 集計スクリプト本体(決定的・テスト付き)
      ├ Notion API: 予約台帳を取得(読む列は 6章)
      ├ DAISUKE CLASS の抽出・クラス判定・名寄せ・回数・所見
      └ Notion API で書き込み ①参加者 ②参加記録 ③開催回 ④通知橋渡し
  3. ④を Notion コネクタで読む → 今日が開催日なら LINE グループ(コーチ入り)へ push
```

- 予約メールチェックは 08:08 頃に始まり 08:20 頃に終わる。08:45 の集計で当日朝までの申込が入る
- 集計はテニスベアの取得を伴わず `NOTION_TOKEN` だけで動くため、ローカルを使わずクラウドの1本にまとめた(オーナー決定 2026-09-30)
- 判定と文面はスクリプトで確定させる。クラウドの LLM はスクリプトの実行と、④を読んで送ることだけを行う(早朝と同じ方針)
- 秘密情報: クラウド環境 `env_016yu2zZKZC73qPmuKVKeSFY` に `NOTION_TOKEN`(連携 `bigban-growth`)と `LINE_HYROX_GROUP_ID` を登録する。`LINE_CHANNEL_ACCESS_TOKEN` は予約メールチェックと同じものを使う
- `NOTION_TOKEN` のクラウド登録は、早朝ピックルの方針「クラウドに新しい秘密情報は登録しない」の例外(オーナー決定 2026-09-30)

## 4. 流用する部品(`scripts/early-morning/`)

流用は `scripts/hyrox-class/` から `scripts/early-morning/` の汎用関数を**直接 import** する(オーナー決定)。早朝のファイルは動かさない・書き換えない。3つ目の利用者が出たときに `scripts/lib/` への移動を検討する。

| 部品 | import するもの |
|---|---|
| `notionClient.ts` | `createNotionClient` / `NotionClient` / `NotionApiError`(リトライ・429 対応・`filter_properties`) |
| `notionProps.ts` | プロパティの読み書き関数 |
| `identity.ts` | `normalizeName`(NFKC→空白除去)のみ |
| `dates.ts` | JST の日付計算・表示整形の関数 |
| `notionSync.ts` | `hashOf` / `readBridge` / `writeBridge` / `markBridgeFailed` のみ |

`notionSync.ts` の `syncPeople` / `syncRecords` / `syncSessions` は早朝専用の型(テニスベアの列を含む)に結びついているため流用しない。HYROX の同期は、同じ方式(キー単位の上書き・同期ハッシュ・スタッフ列を上書きしない)で `scripts/hyrox-class/` に書く。

HYROX 固有の新規コードは `scripts/hyrox-class/` に置く: 台帳の抽出とクラス判定、利用歴の集計、回数と状態、所見、LINE Flex 生成、同期、エントリポイント。

## 5. 対象の抽出とクラス判定

- **DAISUKE CLASS の予約**: `予約種別 = イベント` かつ `イベント名` に `DAISUKE` を含む(大文字小文字を区別しない)。埋め戻し後の実データで、旧表記 `DAISUKE class（経験者）` / `DAISUKE class（ビギナー）` を含む全クラスがこの条件で拾えることを確認済み(2026-09-29)
- **イベント名が空のイベント予約**(予約メールチェックの記帳漏れなど。埋め戻し直後の時点では 0 件): 対象外にして件数だけ標準出力に出す。料金プランからの推測はしない
- **クラス**(イベント名から。上から順に判定):
  1. `ビギナー` を含む → `ビギナー`
  2. `ダブルス` を含む → `ダブルス`
  3. それ以外 → `通常`
- **開催回**: `利用日` + `時間帯` の開始時刻(先頭5文字)で1回とする。クラスはその回の属性(回に属する予約のイベント名から判定)。同日の 19:00 ビギナーと 20:00 通常は別の回
- 開催回は台帳の予約から作る(LaBOLA のイベント一覧は読まない)。予約が全員キャンセルの回も ③ には申込数 0 で残し、LINE には載せない(状態の判定は日数で行うため、開催回の数は判定に使わない)

## 6. 台帳から読む列

`予約番号 / 予約者 / 利用日 / 時間帯 / ステータス / 受付日時 / コート / 予約種別 / イベント名 / 会員番号` の10列だけを `filter_properties` で取得する。会員番号は連絡先ではなく、氏名の表記違いを同じ人にまとめるためだけに読む(Notion には書かない)。電話番号・メール・住所・生年月日は取得しない。

## 7. 名寄せと「1回参加」の定義

- **人の識別**: 正規化した氏名(早朝の LaBOLA 側と同じ)
- **表記ゆれの統合**(オーナー決定): ① の `別名` 列にスタッフがもう一方の表記を入れると、次の実行で、その正規化氏名の行を統合する。統合元の行はアーカイブする。メモは統合先の値を残し、統合先が空なら統合元の値を移す。統合元の識別子をキーに持つ ② の行もアーカイブし、統合先の識別子で作り直す(スタッフが付けた `出欠` は引き継ぐ)。利用歴(8章)も別名を含めて引く
- **会員番号による自動統合**(オーナー決定 2026-09-30): 会員番号が同じ予約は同じ人にまとめる(冨/富のように、NFKC 正規化では同じにならない字の違いを拾うため)。会員番号がない来場者や、番号が変わった場合(一般会員→PBT Club へのアップグレードなど)は別名で補う。統合先: 別名を入れた行があればその中で識別子が最小の行、なければグループ内で識別子が最小の行。全予約(DAISUKE 以外の利用歴の行を含む)が対象
- **別名の扱い**(オーナー決定 2026-09-29/30):
  - 相互・連鎖・重複した別名は1人にまとめる。統合先は、別名を入れた行のうち識別子が最小の行
  - 統合時に、統合元の名前と別名を統合先の別名列へ追記する(既存の別名は消さない)。統合元をアーカイブしたあとも、次の実行で統合がほどけないようにするため
  - 別名は残したい行(統合先にしたい行)にだけ書く
  - 識別子が `lb:` で始まらない手作りの行(参加記録はキーが規定の形でない行)には触らない
- **1回参加**: ある開催回に、その人の予約が「有効」で1件以上あること。同じ回に2件あっても1回
- **無断欠席は判別できない**ため「参加＝有効な予約」とみなす。② の `出欠` にスタッフが「欠席」を付けた回は回数から除く
- **同行者**: 1件の予約で複数人分を払った場合も、数えるのは予約者1人だけ

## 8. 利用歴(所見用)

DAISUKE CLASS 以外の台帳の行を、同じ正規化氏名(と別名)で引いて3分類する。有効な予約のみ。

イベントの分類は**イベント名**で行い、`コート` はスペース予約の分類にだけ使う。埋め戻し後の実データで、HYROX のイベントがピックルのコートで記帳されている例(ミニシミュレーション 6件が `A:アルテミス`、ピクロックス 15件が `B:ビックバン`)があり、コートでは正しく分けられないため。

| 分類 | 条件 | 所見での表記 |
|---|---|---|
| HYROX 系イベント | `予約種別 = イベント` かつ DAISUKE 以外で、イベント名に `HYROX` / `ハイロックス` / `ピクロックス` のいずれかを含む(大文字小文字を区別しない) | イベント名から短い名前を作る(`体験会` / `モーニングクラス` / `ミニシミュレーション` / `ピクロックス` を含めばその語、どれでもなければ `HYROXイベント`)。回数が1回なら日付を付ける |
| HYROX エリア貸切 | `予約種別 = スペース` かつ `コート = HYROX` | `HYROXエリア貸切 N回` |
| ピックル | 上記以外のイベント、または `予約種別 = スペース` かつ `コート` が A/B/C | `ピックル N回` |

- テスト予約は除外する。`config.ts` の `EXCLUDED_RESERVATION_NOS`(予約番号の配列。初期値は `#3` と `#16`、2026-09-29 の埋め戻しでテスト予約と確認済み)で指定する

- 貸切は予約者本人の名前しか残らないため、同行して利用した人は拾えない
- テニスベア経由のピックル参加は氏名が取れないため含まない
- 数えるのは、その DAISUKE CLASS の回より前の利用日のものだけ

## 9. Notion の構成

親ページ「HYROX クラス参加者」(予約台帳と同じ非公開の場所。Notion コネクタで作成し、連携 `bigban-growth` に共有する)の下に4つ置く。個人名を置くのはここと LINE だけ(分析 runbook の「台帳の個人情報の扱い」の例外として早朝と同様に明記する。連絡先は置かない)。

### ① 参加者(1人1行)

| 列 | 型 | 書き手 | 内容 |
|---|---|---|---|
| 氏名 | title | ルーチン | 台帳の予約者名(正規化前、最新の表記) |
| 識別子 | text | ルーチン | `lb:{正規化氏名}`。上書き更新のキー |
| 別名 | text | **スタッフ** | 同じ人の別表記。入れると次回実行で統合する(7章)。ルーチンは上書き・削除しない。統合時だけ、統合元の名前と別名を追記する |
| 通算 | number | ルーチン | DAISUKE CLASS の参加回数 |
| ビギナー / 通常 / ダブルス | number | ルーチン | クラス別の参加回数 |
| 初参加日 / 最終参加日 | date | ルーチン | |
| 状態 | select | ルーチン | 新顔 / 常連 / ご無沙汰 / 通常 |
| 次回申込 | checkbox | ルーチン | 今日以降の回に有効な予約があるか |
| 利用歴 | text | ルーチン | 8章の3分類の要約(例「体験会 9/22・ピックル 5回」) |
| メモ | text | **スタッフ・コーチ** | ルーチンは上書きしない |
| 同期ハッシュ | text | ルーチン | 変化がない行は更新しない(①②③共通) |

ビュー: 次回の参加者 / 新顔 / ご無沙汰 / 通算ランキング / 別名が入っている行

`状態` と `次回申込` は LINE の所見には使わないが、Notion で常連・ご無沙汰・次回の参加者を一覧するために残す(オーナー決定 2026-09-29)。

### ④ 通知橋渡しページ「今日の DAISUKE CLASS」

本文は JSON のコードブロック1つだけ(毎回全体を置き換え)。形は早朝の橋渡しページと同じにし、`readBridge` / `writeBridge` / `markBridgeFailed` をそのまま使う。

```json
{
  "nextDate": "2026-10-07",
  "updatedAt": "2026-10-07T08:46:00+09:00",
  "status": "ok",
  "failure": null,
  "flex": { "type": "flex", "altText": "…", "contents": { } }
}
```

- `nextDate` は「通知する日」= 今日以降(JST)で LINE に載せる回がある最初の開催日。該当する回がなければ `nextDate: null` / `flex: null`。前日の集計で翌日分が置かれるため、当日朝の集計が失敗しても、8:45 には前日分が「⚠ 最新ではありません」付きで届く。ただし開催日が連続する日(土日など)は、前日の集計が置くのは前日自身の日付なので、当日の集計が失敗すると何も送られない(ルーチンの報告に集計の失敗が出る)
- 取得失敗時は `status: "failed"` と `failure` だけを書き換え、ほかは前回の値を残す

## 10. 判定ルール(初期値)

基準値は `scripts/hyrox-class/config.ts` の1か所に置く。DAISUKE CLASS は週に複数回・曜日も変わるため、早朝と違って**日数(週)**を単位にする。

| 項目 | 定義 |
|---|---|
| 新顔 | 通算 1〜2 回 |
| 常連 | 直近28日に3回以上 |
| ご無沙汰 | 通算3回以上、かつ最終参加から28日以上 |
| 通常 | 上記以外 |
| 週連続 | 今日の回を含めず、先週から遡って参加がある週(月曜始まり・JST)が続いた数 |

状態の優先順: ご無沙汰 > 常連 > 新顔 > 通常。

## 11. LINE 通知

- 送信: クラウドルーチン、毎日 08:45 JST。④の `nextDate` が今日で `flex` があるときだけ送る。それ以外の日は何も送らない
- 宛先: コーチ入りの HYROX 用グループ(`LINE_HYROX_GROUP_ID`)
- 文面(Flex bubble。例の名前は架空):

```
【本日の DAISUKE CLASS】10/7(水)

19:00 ビギナーの部  3名
・参加者A　初参加 🔰
   初めての方。声かけをお願いします
   これまで: 体験会(9/22)・ピックル 5回
・参加者B　4回目
   2週連続・前回 9/30

20:00 通常  5名
・参加者C　12回目
   通常回は初めて(ビギナー3回)
…
[Notionで一覧を開く]
最終更新 10/7 8:31
※予約は本日朝8時時点までを反映
```

- 回ごとに見出し(開始時刻・クラス名・人数)を出す。クラス名は ビギナー→「ビギナーの部」、通常→「通常」、ダブルス→「ダブルス」
- 並び順: 回ごとに、通算回数の多い順。初参加は最後にまとめる
- 所見(決まった文言で作る。AI は使わない。その回より前の参加(同じ日の前の回を含む)で決める)。上から順に当てはまるものを使う:
  1. DAISUKE CLASS の1回目 → 「初めての方。声かけをお願いします」+ 次の行に利用歴(8章)。利用歴がなければ「施設の利用も初めて」
  2. 今日のクラスに初めて(通算2回目以上) → 「{クラス}は初めて({前にいたクラス}N回)」。複数あれば回数の多い方
  3. 通算2回目 → 「2回目(初参加 M/D)」
  4. 最終参加から28日以上 → 「久しぶり(前回 M/D)」
  5. 2週以上連続 → 「N週連続・前回 M/D」
  6. それ以外 → 「直近28日でN回・前回 M/D」
- ④の `updatedAt` が今日より前なら、先頭に「⚠ 最新ではありません(最終更新 M/D HH:MM)」を足して送る
- ④の `status` が `failed` なら、先頭に「⚠ {failure の最初の「:」より前(予約台帳 / Notion読み取り / 集計 / Notion書き込み)}の処理に失敗したため前回のデータです」を足して送る
- Notion のリンクには `?openExternalBrowser=1` を付ける

## 12. エラー処理

- 台帳の取得に失敗したら ①②③ は更新しない。④ の取得状態だけ失敗に更新する(④の `nextDate` と `flex` は前回の値を残すので、前日に置いた翌日分が警告付きで送られる)
- 必須の列(予約者・利用日・時間帯・ステータス)が欠けた行は対象外にし、件数を標準出力に出す。推測で埋めない
- Notion 書き込みはリトライ付き。途中で失敗しても、次回実行で全期間を再計算してキー単位で上書きするので自然に収束する
- LINE への障害通知は④経由の1経路に限る
- 同じ実行内で集計が失敗しても、続けて④を読み、前日の集計で置かれた当日分があれば警告付きで送る。失敗のしかたで警告が変わる:
  - `npm run hyrox:sync` 自体が失敗: ④の `status` が失敗になり、`failure` に理由が入る。「処理に失敗した」と「最新ではありません」の両方の警告が付くことがある
  - `npm ci` が失敗: スクリプトが動かず④は ok のまま。「最新ではありません」の警告だけが付く
- クラウドルーチンは `NOTION_TOKEN` / `LINE_CHANNEL_ACCESS_TOKEN` / `LINE_HYROX_GROUP_ID` が未設定、または Notion に到達できないときは送らずに報告する(早朝の通知ルーチンと同じ)

## 13. 個人情報の扱い

- 個人名が置かれるのは Notion(①②④)と LINE グループ(コーチを含む)だけ
- リポジトリ(コード・テスト・ログ・コミット)に実在の氏名を残さない。テストのフィクスチャは架空の名前で作る

## 17. 検討した代替案

| 案 | 採否 | 理由 |
|---|---|---|
| 料金プランの文言からクラスを判定する | 不採用 | 回ごとに表記がバラバラで確実に判定できない。代わりに台帳へ `イベント名` 列を追加した |
| develop から独立して作り、必要な部品をコピーする | 不採用 | 同じ Notion 同期の処理が2か所に重複する。早朝のマージを待つ方を選んだ |
| 早朝のコードを「プログラム設定」で汎用化し、HYROX を2つ目の設定にする | 不採用 | 早朝側の改修とテストのやり直しが大きい。3つ目の利用者が出たときに再検討する |
| 部品を `scripts/lib/` へ移して共有する | 不採用(今回) | 早朝側の import とテストも直す必要がある。直接 import を選んだ |
| ローカル 8:30 集計 + クラウド 9:00 送信 | 不採用(オーナー決定 2026-09-30) | Mac に依存し仕組みが2つになる。テニスベア取得が無く `NOTION_TOKEN` だけで動くのでクラウドの8:45の1本にまとめた |
| 前夜 21:00 に送る | 不採用 | 当日朝までの申込が入らない。台帳更新(08:20 頃)の後の当日 8:45 にした |
| 早朝ピックルと同じスタッフグループに送る | 不採用 | コーチが読めない。コーチ入りの別グループにした |
| 利用歴をコートで分類する | 不採用 | HYROX のイベントがピックルのコートで記帳されている例があり、誤分類する |
