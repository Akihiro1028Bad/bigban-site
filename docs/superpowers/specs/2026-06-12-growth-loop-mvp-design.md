# AIグロースループ MVP 設計書

**作成日**: 2026-06-12
**ブランチ**: `feature/growth-loop-mvp`
**対象**: `THE PICKLE BANG THEORY` ブランドサイトのグロース運用自動化

## 1. 背景と目的

GA4・Search Console・サイト内容・業界情勢を AI が定期分析し、「次に打つべき施策」を提案・実行する仕組みを作りたい。最終的には施策の提案 → 承認 → 実行までを半自動化するが、本 MVP ではその成否を分ける最重要要素である**「提案の質」の検証**に絞る。

### 基本原則(全フェーズ共通)

1. **提案と実行を分離する** — AI が本番を直接変更しない。世に出る瞬間のボタン(公開・マージ)は必ず人間が押す
2. **根拠のない施策は出させない** — すべての提案に「どのデータがそう言っているか」と確度を添付
3. **ブランドの最終判断は人間** — 配色・タイポグラフィ・世界観は AI 単独で変更しない

## 2. MVP スコープ

### 毎週月曜朝に自動で起きること

1. 自宅 Windows PC(24時間稼働)で Claude Code がヘッドレス起動(タスクスケジューラ)
2. GA4 / Search Console / microCMS のデータを収集
3. 外部文脈(ピックルボール業界の話題・季節イベント・地域の動向)を **AI が分析時に Web 検索で取り込む**
4. 上記を統合して分析 → **Notion に週次レポート1ページ**を作成(今週の数字+施策提案、最大3件、根拠・確度つき)
5. **microCMS に記事下書きを1本**作成 — 最も価値の高い記事ネタを実際に執筆

> 外部文脈(ニュース・業界・季節)は GA4 のようなデータ取得・保存パイプラインを持たず、②の分析時に AI が Web 検索する形で取り込む(新規部品ゼロ、指示書に記載)。自社 SNS の数値取得(Instagram/X の API 連携)は重く X は有料のため MVP では扱わず、価値が見えてから検討する。

### オーナーの週次ルーティン(5〜10分)

- Notion レポートを読む → 良い提案は実行 or 次週へ指示
- microCMS 下書きを確認 → 良ければ公開、ダメなら削除
- スタッフ共有は LINE グループへ手動転送

### MVP に含めないもの

| 項目 | 理由 |
|------|------|
| LINE 自動通知 | 公式アカウント開設の手間。検証期間中は手動転送で足りる |
| 承認 → 自動実行ループ | 提案の質が確認できてから作る(最も構築が重い) |
| PR 自動作成(デザイン・SEO 修正) | 同上。MVP では提案文として読むだけ |
| スタッフ向け UI・権限設計 | まず提案の質をオーナーが見極めてから |

## 3. 成功判定(4週間運用して判断)

- 提案のうち「実際にやろう」と思えるものが**毎週1件以上**あるか
- 記事下書きが「ほぼそのまま公開できる」品質か
- No の場合は実行系を作らず、週次指示書のチューニングに戻る

## 4. アーキテクチャ

### 実行基盤:自宅 Windows PC + Claude Code ヘッドレス

```
[自宅 Windows PC]
  毎週月曜 7:00 タスクスケジューラ起動
     └─ スクリプト1本:
         ① git pull(リポジトリ最新化)
         ② claude -p で「週次グロース指示書」を実行
             ・GA4 / GSC データ取得(サービスアカウント)
             ・microCMS MCP で投稿状況取得、Web 検索で業界情勢
             ・分析 → Notion にレポート作成
             ・microCMS に記事下書き作成
         ③ ログ保存
```

**採用理由**
- ローカルの `~/.claude` 資産(スキル・MCP・ルール・メモリ)をそのまま使える
- サブスクリプション内で動作し、API 従量課金が発生しない
- リポジトリをクローンしておくことで、コードベースを読んだ上での提案が可能

**死活監視**: 専用の仕組みは作らない。毎週必ず Notion レポートが立つ運用のため、「月曜にレポートがない=停止」と判別できる。週次バッチなので1回飛んでも翌週リカバリで実害なし。

### データ保存層(2段構え・アーカイブ用途)

**分析(②)の主たる入力は API から直接取得する。** GA4 / GSC の API は任意期間を指定できるため、前週比も「今週」「先週」を都度取得すれば足り、保存データに依存しない。保存層は毎回の分析入力ではなく、**必要なときだけ読みにいくアーカイブ(保険)**と位置づける。

- 用途: 長期トレンドの振り返り、API のデータ保持期間を超えた過去の参照、再分析・デバッグ
- **MVP**: 各週の生データを日付つき JSON スナップショットで自宅 PC に保存(例: `data/snapshots/2026-06-15.json`)。リポジトリ管理外(`.gitignore`)。追加コストゼロ。普段の分析では読まない
- **MVP 後(学習ループ着手時)**: Google スプレッドシートに昇格。週1行の成績表を自動追記し、長期トレンドと施策の効果検証を担う。PC 故障でも残る。既存 OAuth に Sheets スコープを追加
- 方針: 最初から重い DB は作らず、価値が出る段階で蓄積を厚くする

### 権限設計(安全装置)

ヘッドレス実行では人間が許可ボタンを押せないため、設定ファイルで事前許可を明示的に絞る:

- **許可**: microCMS 下書き作成、Notion 書き込み、GA4/GSC 読み取り、Web 検索
- **不許可**: microCMS 公開、git push、PR 作成、その他すべて

## 5. 検討の経緯(却下した案と理由)

| 案 | 却下理由 |
|----|---------|
| LINE ボット承認(Flex Message ボタン + webhook + Notion 状態管理 + ポーリング) | 承認システムの自作は部品が多く複雑すぎる。承認ゲートは microCMS 公開ボタンと PR マージで既に存在していた |
| GitHub Actions cron で週次実行 | 実現可能だが API 従量課金が必要。ローカルのスキル・MCP 資産も使えない。信頼性要件が上がったら移行先候補として有効 |
| Claude Code クラウドスケジュール実行(routine) | 最も手軽だが、ローカルの MCP(microCMS 接続等)・スキル・メモリが使えない |
| Vercel に webhook + 実行基盤 | 関数実行時間の制約があり、コーディングエージェントの実行場所として不適。webhook 受付のみなら有効(MVP 後の候補) |
| 専用管理画面(/admin)の先行構築 | 使われるか不明な段階で作るのは無駄。Notion 運用が回ってから検討 |

## 6. MVP 後の拡張構想(参考)

1. **LINE 送信専用通知** — ボタンなし(webhook 不要)で週次サマリーをスタッフグループに自動送信
2. **承認 → 自動実行ループ** — Notion カードのステータス変更を自宅 PC がポーリングで検知し実行。外部公開・webhook なしの原則を維持
3. **デザイン施策の半自動化** — 承認後に AI がコード修正 → PR + Vercel プレビュー + Before/After スクリーンショット。CI green + 承認で反映
4. **スタッフ向け UI** — Notion カンバン(施策カード: 根拠・比較画像・お試しページリンク・承認ボタン)→ 定着したらサイト内 /admin 画面化。スタッフ向け文言は専門用語禁止(例: 「CTR 1.2%」→「100人に1人しかクリックしていない」)
5. **学習ループ** — 週次実行の冒頭で先週実行済み施策の効果を計測し Notion に追記、次の提案の精度を上げる

## 8. 認証方式(2026-06-12 決定:OAuth 方式に変更)

当初はサービスアカウントで GA4 / GSC に閲覧権限を付与する想定だったが、**Google 側のバグ**により頓挫したため OAuth 方式へ変更した。

### 経緯:Google のサービスアカウント追加バグ

- 2026-04-20 ごろから、それ以降に新規作成したサービスアカウントを GA4 / Search Console の「ユーザー追加」UI に登録できない不具合が発生(「このメールアドレスは Google アカウントと一致しません」/「email not found」)。Google 認識済み・修正時期未定。
- 参考: [piunikaweb](https://piunikaweb.com/2026/05/01/google-service-account-email-not-found-bug/) / [Google Developer forums](https://discuss.google.dev/t/problem-with-new-service-accounts/362176) / [Search Central Community](https://support.google.com/webmasters/community-guide/429538961/)
- 本プロジェクトで作成した `growth-loop@picluban.iam.gserviceaccount.com` もこれに直撃。

### 採用方式:OAuth 2.0(オーナー自身のアカウント)

オーナーは GA4・GSC 両方の所有者のため、「ユーザー追加」を行わず**自身の権限で API を読む**。バグを完全に回避でき、GA4 と GSC を単一の認証で賄える。

- Windows PC で一度だけ OAuth 同意 → リフレッシュトークンを保存 → 週次スクリプトが利用
- **必須設定**: OAuth 同意画面を「本番(公開)」にする。「テスト」状態のままだとリフレッシュトークンが7日で失効し週次実行が停止する([OAuth2 公式](https://developers.google.com/identity/protocols/oauth2))
- 必要スコープ(読み取り専用): `analytics.readonly` / `webmasters.readonly`
- OAuth クライアント(デスクトップアプリ種別)を作成し、JSON とトークンは Windows PC のみに保管・リポジトリ管理外

### 確定パラメータ(2026-06-12)

| 項目 | 値 |
|------|----|
| 認証方式 | OAuth 2.0 デスクトップアプリ(同意画面=本番公開済み) |
| OAuth クライアント JSON | Windows PC に保管(リポジトリ管理外) |
| GA4 プロパティ ID | `540956661` |
| GSC プロパティ | `https://www.thepicklebang.com/`(URL プレフィックス型) |

### 却下した代替案:API 経由でサービスアカウントを追加(案B)

- GA4 は Analytics Admin API `accessBindings.create`(OAuth Playground 等)で UI バグを回避して追加可能。手順: [okamomedia](https://www.okamomedia.tokyo/articles/ga4-service-account-add-error-bug)
- ただし **Search Console にはユーザー追加 API が存在せず**、GSC 側が解決できないため MVP 要件(GA4+GSC 両方)を満たせない。将来 GA4 単体でサービスアカウントを使いたくなった場合の参考として記録。
