# 早朝ピックル リピーター可視化 設計書

- 作成日: 2026-09-29
- 状態: 設計確定(ユーザー承認済みの内容を文書化)。実装計画は別途 `docs/superpowers/plans/` に作成する
- 目的: 施設主催「早朝ピックルボール」の参加者を人単位で数え、リピーターを可視化してリワード判断・声かけに使う

## 1. 背景と課題

早朝ピックル(6:00-8:00)の申込経路は2つある。

- **テニスベア**(サークル 36659 のイベント)。参加者の大半はこちら
- **LaBOLA**(予約システムのイベント予約)。予約メールチェックのルーチンが毎朝 08:00 頃に Notion「Labora 予約台帳」へ記帳している

スタッフは LaBOLA 予約をテニスベアのゲスト枠へ手入力して定員を合わせているが、2026-09-29 の実地確認で次のことが分かった。

| 開催日 | LaBOLA 予約(有効) | テニスベアのゲスト枠 | 判定 |
|---|---|---|---|
| 9/29 | 1 | 1 | 一致 |
| 9/22 | 2 | 3 | 1件多い |
| 9/15 | 2 | 2 | 一致 |
| 9/8 | 3 | 3 | 一致 |
| 8/25 | 1 | 1(「PBT CLUB会員枠1」) | 一致 |
| 8/11 | 4 | 0 | 4件漏れ |

- ゲスト枠の名前は「LBゲスト1」「ゲスト1(LABOLA経由)」など連番で、**本名は入っていない**。ゲスト枠から個人は特定できない
- 手入力は漏れと過剰の両方がある
- LaBOLA の会員番号は同一人物でも変わる(例: 一般会員→PBT Club で別番号)。**照合キーは氏名**
- 同じ日に「元イベント(中止)」と「訂正版」の2イベントが立つことがある(8/25)

## 2. ゴールと非ゴール

**ゴール**

1. 早朝ピックルの参加を人単位・回単位で Notion に記録する(分析用の参加記録を含む)
2. 1人1行の常連一覧で、累計・直近・連続・ご無沙汰・節目・リワード済みを見られる
3. 翌朝に早朝回がある日の 21:00 に、LINE グループへ「参加者一覧と各人の何回目か」を送る
4. Mac が起動していなくても通知は届く

**非ゴール**

- テニスベアのゲスト枠の運用を直すこと(集計はゲスト枠に依存しない設計にする)
- 無断欠席の自動検知(スタッフが任意で記録する欄だけ用意する)
- 施設主催の他イベント(オープンプレー・DAISUKE CLASS 等)や個人主催練習会の集計
- Web サイト・Artifact での公開表示(個人名を扱うため Notion と LINE に限定)

## 3. 構成

```
[Mac ローカルルーチン] 毎日 08:30 / 20:30(台帳の取り込み 08:00〜08:20 の後。スリープ明けの取りこぼしも実行)
  npm run early:sync        ← 集計スクリプト本体(決定的・テスト付き)
   ├ テニスベア: 早朝イベントの HTML を取得 → 埋め込みデータから参加者を抽出
   ├ Notion API: 予約台帳から早朝イベント予約を取得
   ├ 名寄せ・回数計算・判定
   └ Notion API で書き込み
       ├ ① 早朝常連(1人1行)
       ├ ② 早朝参加記録(1人×1回)
       ├ ③ 早朝開催回(1回1行)
       └ ④ 通知橋渡しページ「次回の早朝」(送信用 Flex JSON を含む JSON を置く)

[クラウドルーチン] 毎日 21:00 JST
   ④を Notion コネクタで読む → 翌日が開催日なら LINE グループへ push
```

- 判定と文面はローカルのスクリプトで確定させる。クラウドは「④を読んで送るだけ」で、AI の解釈による数字のぶれを避ける
- ローカルは `.env.local` の `NOTION_TOKEN`(連携 `bigban-growth`。予約台帳の読み取りを 2026-09-29 に確認済み)を使う
- クラウドは Notion コネクタと、予約メールチェックと同じ環境(`LINE_CHANNEL_ACCESS_TOKEN` / `LINE_GROUP_ID`)を使う。**クラウドに新しい秘密情報は登録しない**

## 4. データソース

### 4.1 テニスベア

- イベントページ `https://www.tennisbear.net/pickleball/event/{id}/info` は**ログイン不要**で、HTML 内の `window.__NUXT__` に参加者データが埋め込まれている(2026-09-29 に curl で確認)
- 参加者1件ごとに次を持つ: `user.id`(不変の数値。**ゲストは -1**)、`user.name`(ニックネーム)、`guestUserFlg`、`eventUserStatusType`、`applyDateTime`、`cancelDateTime`
- `window.__NUXT__` は `(function(a,b,...){return {...}}(引数...))` 形式。**外部サイトの JS を実行しない**ため、acorn で構文解析し、リテラル・配列・オブジェクト・引数参照・`void 0` 等の限られたノードだけを評価する小さな評価器で値を復元する。未対応ノードに当たったら推測せずエラーにする
- 開催回の発見: サークルページ `/pickleball/circle/36659/events` の HTML の `state.feature.circle.circleDetail.CircleOrganizedEvents` に、今後の予定(`circleOrganizedFutureEventList`)と過去分(`circleOrganizedPastEventList`、2026-09-29 時点で185件)の両方が入っている(curl で確認)。各要素は `id` / `eventTitle` / `startDatetimeString` / `callOff` を持つ
- イベント詳細は `state.feature.event.eventDetail.EventDetail.event` にあり、`id` / `startDateTime` / `callOff` / `participantList`(状態 `APPROVE`)/ `cancelUserList`(状態 `CANCEL`)を持つ。`applyingUserList` / `waitingUserList` は申込とみなさない
- 早朝イベントの判定: 開始時刻が 06:00 のイベント。タイトルの文言(「【早朝】」「初中級」「訂正版」等)には依存しない。火曜(初中級)・木曜(中級以上)の両方が対象(木曜は 2026-10-01 から再開)
- 中止の回は開催回として数えない。参加者も数えない

### 4.2 LaBOLA(Notion「Labora 予約台帳」)

- 抽出条件: `予約種別 = イベント` かつ `時間帯` の開始時刻が `06:00`(表記ゆれ `～` / `-` / `〜` があるため先頭5文字で判定)
- `ステータス`(有効/キャンセル)をそのまま使う
- 読む列は `予約番号 / 予約者 / 利用日 / 時間帯 / ステータス / 受付日時` のみ。電話番号・メール・住所・生年月日は取得しない
- 取得する列は Notion API の `filter_properties` で上記6列に限定する
- 開催回はテニスベアのイベントから作る。LaBOLA 予約の日付に対応する開催回(中止でない)がなければ、その予約は集計しない(件数だけ標準出力に出す)
- 反映の遅れ: 台帳は毎朝 08:00 頃に更新されるため、前日 08:00 以降の LaBOLA 予約は前夜の通知に入らない。通知に小さく注記する

## 5. 名寄せと「1回参加」の定義

- **人の識別**
  - テニスベア: `user.id`
  - LaBOLA: 正規化した氏名(NFKC 正規化→空白類をすべて除去)
- **ゲスト枠(`user.id = -1` または `guestUserFlg = true`)はすべて除外する**。ゲスト枠は LaBOLA 予約の写しなので、除外すれば二重計上しない。手入力の漏れ・過剰にも影響されない
- **両経路を使う人の統合**: ① 早朝常連のテニスベア行の「LaBOLA氏名」にスタッフが氏名を入れると、次の実行で同じ正規化氏名の LaBOLA 単独行を統合する。統合元の行はアーカイブする。スタッフ入力列は、リワード済みは両行の和集合、メモは統合先の値を残し、統合先が空なら統合元の値を移す
- **1回参加**: ある開催日に、その人の申込が1件以上「申込」状態で残っていること。同じ人が同じ日にテニスベアと LaBOLA の両方にいても1回。同じ日に2イベント(訂正版)あっても1回
- **無断欠席は判別できない**ため「参加＝申込」とみなす。② の「出欠」にスタッフが「欠席」を付けた回は回数から除外する

## 6. Notion の構成

予約台帳と同じ非公開の場所に作る。この4点に限り、個人名を置くことを分析 runbook の「台帳の個人情報の扱い」の例外として明記する(連絡先は置かない)。

### ① 早朝常連(1人1行)

| 列 | 型 | 書き手 | 内容 |
|---|---|---|---|
| 表示名 | title | ルーチン | テニスベアのニックネーム、なければ LaBOLA 氏名 |
| 識別子 | text | ルーチン | `tb:{テニスベアID}` または `lb:{正規化氏名}`。上書き更新のキー |
| テニスベアID | number | ルーチン | 空欄可 |
| LaBOLA氏名 | text | ルーチン/スタッフ | 正規化前の氏名。対応表を兼ねる |
| 累計 | number | ルーチン | 参加回数 |
| 直近8回 | number | ルーチン | 直近8開催のうち参加した回数 |
| 連続 | number | ルーチン | 最新の開催回から遡った連続参加回数 |
| 初参加日 / 最終参加日 | date | ルーチン | |
| 状態 | select | ルーチン | 新顔 / 常連 / ご無沙汰 / 通常 |
| 次回申込 | checkbox | ルーチン | 次回開催回に「申込」状態で入っているか |
| 次の節目 | text | ルーチン | 例「あと1回で10回」 |
| 到達節目 | multi-select | ルーチン | 到達済みの節目(5, 10, 20…) |
| 未渡し節目 | multi-select | ルーチン | 到達節目のうちリワード済みにないもの |
| リワード済み | multi-select | **スタッフ** | 渡した節目。ルーチンは上書きしない |
| メモ | text | **スタッフ** | ルーチンは上書きしない |
| 同期ハッシュ | text | ルーチン | 書き込む値の要約。変化がない行は更新しない(①②③共通) |

ビュー: 次回の参加者(次回申込 = true) / 未渡しリワード(未渡し節目が空でない) / ご無沙汰 / 累計ランキング / LaBOLA氏名が未対応

### ② 早朝参加記録(1人×1回)

| 列 | 型 | 内容 |
|---|---|---|
| キー | title | `{開催日}_{人の識別子}`(上書き更新のキー) |
| 開催日 | date | |
| 人 | relation → ① | |
| 経路 | select | テニスベア / LaBOLA / 両方 |
| 申込日時 | date | 複数経路なら早いほう |
| 状態 | select | 申込 / キャンセル / 元データになし |
| 回次 | number | その人にとって何回目か(「申込」かつ欠席でない回のみ採番) |
| 出欠 | select | 空欄 / 欠席。**スタッフのみ書く。ルーチンは上書きしない** |
| 元データ | text | テニスベアのイベントID / LaBOLA 予約番号 |
| 同期ハッシュ | text | 変化がない行は更新しない |

- 元データから申込が消えた場合、行は削除せず「元データになし」にする

### ③ 早朝開催回(1回1行)

| 列 | 型 | 内容 |
|---|---|---|
| 開催日 | title/date | |
| テニスベアイベントID | text | 同日に複数あればカンマ区切り |
| 中止 | checkbox | 同日のイベントがすべて中止なら true |
| 申込数 | number | 名寄せ後の人数 |
| 同期ハッシュ | text | 変化がない行は更新しない |

### ④ 通知橋渡しページ「次回の早朝」

本文は JSON のコードブロック1つだけにする(毎回全体を置き換え)。

```json
{
  "nextDate": "2026-10-06",
  "updatedAt": "2026-10-05T20:31:00+09:00",
  "status": "ok",
  "failure": null,
  "flex": { "type": "flex", "altText": "…", "contents": { } }
}
```

- 取得失敗時は `status: "failed"` と `failure`(どちらの取得か・理由)だけを書き換え、`nextDate` / `updatedAt` / `flex` は前回の値を残す
- 次回の開催回がない場合は `nextDate: null` / `flex: null`

## 7. 判定ルール(初期値)

基準値は `scripts/early-morning/config.ts` の1か所に置く。日数ではなく**開催回**を単位にする(祝日・中止で間隔が空いても判定がずれない)。

| 項目 | 定義 |
|---|---|
| 新顔 | 累計 1〜2 回 |
| 常連 | 直近8開催のうち4回以上 |
| ご無沙汰 | 累計3回以上、かつ最終参加より後の開催回に4回以上続けて不参加 |
| 通常 | 上記以外 |
| 連続 | 最新の開催回から遡って連続で参加した回数(中止回は開催回に含めない) |
| 節目 | 5・10・20・30・50回、以降50回ごと |

状態の優先順: ご無沙汰 > 常連 > 新顔 > 通常。

## 8. LINE 通知

- 送信: クラウドルーチン、毎日 21:00 JST。④の `nextDate` が翌日(JST)のときだけ送る。それ以外の日は何も送らない
- 宛先: 予約メールチェックと同じ LINE グループ(`https://api.line.me/v2/bot/message/push`)
- 文面(Flex bubble。以下は構成の例。実在の名前は使わない):

```
【明日の早朝ピックル】10/6(火) 6:00
申込 12名

・参加者A　15回目
・参加者B　10回目
・参加者C　 6回目(LaBOLA)
・参加者D　 3回目
・参加者E　初参加 🔰

[Notionで一覧を開く]
最終更新 10/5 20:30
※LaBOLA予約は本日朝8時時点までを反映
```

- 並び順: 回数の多い順、初参加は最後にまとめる
- 印は2種類だけ: 🔰(初参加)、(LaBOLA)(LaBOLA 予約の人)
- 節目・ご無沙汰・連続・ランキングは LINE に載せない(Notion のビューで見る)
- ④の `updatedAt` が24時間以上前なら、先頭に「⚠ 最新ではありません(最終更新 M/D HH:MM)」を足して送る
- ④の `status` が `failed` なら、先頭に「⚠ {どちら}の取得に失敗したため前回のデータです」を足して送る
- Notion のリンクは `?openExternalBrowser=1` を付ける(予約メールチェックと同じ)

## 9. エラー処理

- **取得失敗時は書き込まない**: テニスベアか予約台帳のどちらかが取得・解析に失敗したら、①②③は更新しない(一部だけのデータで上書きしない)。④の取得状態だけ失敗に更新する
- 解析器が未知の構文に当たった、または必須フィールド(`user.id`・状態・開始日時)が欠けた場合は失敗として扱う。推測で埋めない
- Notion 書き込みはリトライ付き(429 は `Retry-After` に従う)。途中で失敗しても、次回実行で全期間を再計算してキー単位で上書きするので自然に収束する
- ローカルルーチンは失敗時に Claude の実行結果として報告する。LINE への障害通知は④経由の1経路に限る(通知の二重化はしない)
- 外部アクセスは開催回ごとに1リクエスト、間隔 1 秒以上(テニスベアへの負荷配慮)

## 10. 個人情報の扱い

- 個人名が置かれるのは Notion(①②④)と LINE グループだけ
- リポジトリ(コード・テスト・ログ・コミット)に実在の氏名・ニックネームを残さない。テストのフィクスチャは架空の名前で作る
- スクリプトの標準出力は件数と所要時間だけにする
- 予約台帳からは電話番号・メール・住所・生年月日を取得しない

## 14. 追補: クラス別集計・所見・主催者除外(2026-09-29 オーナー決定)

実データの確認で次が分かった。早朝は**火曜=初中級、木曜=中級以上**の2クラス制で運用しており、木曜は9月まるごと休止(8/27中止・10/1再開)。全体の「直近8回」で見ると、火曜だけ来る人の皆勤が「8回中4回」に見え、木曜の人は休止中の火曜を欠席と数えられて「ご無沙汰」になっていた。

### 14.1 クラス
- 開催回にクラスを持たせる: 火曜=`初中級`、木曜=`中級以上`、それ以外の曜日=`その他`(6/24水・6/28日・6/29月の3回。タイトルは通常の「【早朝】ピックルボール」で、火木固定前の回)
- `その他` は累計(リワード基準)に含めるが、クラス別の判定には使わない
- ③ 早朝開催回に `クラス`(select)列を追加

### 14.2 クラス別の判定
- クラス別の数値は、そのクラスの**開催済みの回だけ**で数える(休止期間は開催がないので自然に数えない)
- クラス常連: そのクラスの直近4回のうち3回以上参加
- クラスご無沙汰: そのクラスの参加3回以上、かつそのクラスの最終参加後に同クラスの開催が4回以上続けて不参加
- 皆勤: そのクラスの初参加以降、同クラスの開催すべてに参加(3回以上)
- ① の `状態` は、参加しているクラス(初中級/中級以上)の**すべて**がご無沙汰なら「ご無沙汰」、**いずれか**がクラス常連なら「常連」、累計1〜2回なら「新顔」、それ以外は「通常」(この優先順)。7章の全体基準(直近8回で4回)は廃止
- ① に `初中級(火)` / `中級以上(木)` の参加回数列を追加。`累計`(全体)はリワード基準としてそのまま

### 14.3 主催者の除外
- テニスベアのイベント詳細の `organizer.id` と一致する参加者は、参加者一覧・回数から除外する(主催者は参加者一覧に自動で入るため)
- 追加で除外したいスタッフは `config.ts` の `EXCLUDED_TB_USER_IDS`(数値 ID の配列、初期値は空)で指定する。名前は書かない

### 14.4 LINE の所見
- 見出しにクラスを出す: 「10/6(火) 6:00 初中級」(その他は付けない)
- 各参加者の行の下に、所見を1行(灰色・小さい文字)で出す。所見は翌日の回を**含まない**それ以前のデータから決まった文言で作る(AI は使わない)
- 文言(その回のクラスを C、曜日名を W とする。上から順に当てはまるものを最大2つ、「・」でつなぐ):
  1. 全体の1回目 → 「初めての方。声かけをお願いします」(これ1つだけ)
  2. 全体の2回目 → 「2回目(前回 M/D が初参加)」
  3. C に初参加(全体は3回目以上) → 「W曜は初参加」
  4. C で皆勤 → 「W曜 皆勤(M/Dから N回連続)」
  5. C でクラスご無沙汰に当たる → 「久しぶり(W曜は M/D以来)」
  6. 上記以外 → 「W曜 X回中Y回」(X=C の初参加以降の開催数、Y=参加数)
  7. C で3回以上連続(皆勤でない) → 「N回連続」
  8. もう一方のクラスでクラス常連 → 「◯曜も常連」
  9. C の最終参加から28日以上(休止などで 5 に当たらない) → 「前回 M/D」
- `その他` の回は 1・2 と「累計N回目」相当の既存表示だけにする(所見は付けない)
