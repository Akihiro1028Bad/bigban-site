## 1. 要約

**案4「パイプライン1本道」を土台に、案2の確信メーター/ゲート先出し、案5の依頼トレイ/ガード→依頼変換、案1のUndo付き一括承認を接ぎ木した『俯瞰の効くパイプライン・コンソール』。**

中核の発想転換: **「面を切り替える」のをやめ、「記事が段階を進む」**。作業ホームは1つ（パイプライン盤）。左レールは"面"ではなく**段階別ステーション**（件数バッジ）。

なぜ案4ベースか:
- メンタルモデルが既存 `Stage` 列挙（idea→outline_review→generating→draft_review→scheduled→published）に最も素直。`STAGE_META`/`advanceStage`/`nextActionableId` が実装済みで確実に作れる。
- 俯瞰と迷わなさの両立（カンバンなし・件数バッジ）。
- pull型聖域をIAの背骨に（「承認＝公開でなく次工程の依頼」を全ゲートで文言統一）。

### 新トップレベル構造（左レール＝段階別パイプライン）
```
◎ 要対応（awaitingYou横串・既定着地点）
● 戻りあり（reviseStatus=presenting等）  ←最優先
─ 構成まち（outline_review）
─ 下書きまち（draft_review）
─ 予約まち（draft承認済→枠未定）

```
赤バッジ＝滞留/失敗。ラベリング: 「要対応＝やること／各段階＝置き場」。

## 3. コア承認フローの再設計

### 2段ゲートを1本の道に
ドロワー最上部に**確信メーター（6ドット進捗＋3チェック残量）**を常時固定。

| 段階 | プライマリCTA（文言で出し分け） | サブ |
|---|---|---|
| outline_review | **構成を承認 → 生成を依頼** | 構成を修正依頼 / 却下 |
| generating | （無し）「AIが執筆中 セク2/4」＋stuck時のみ巡回確認 | — |
| draft_review | **下書きを承認 → 公開予約**（ガード未充足時ロック） | 本文を修正依頼 / 構成からやり直す / 却下 |

- 全ゲートを「承認 → ◯◯を**依頼**」に統一（pull型の刷り込み）。承認は決して「いま公開」ではない。
- **最終公開（scheduled→published）は自動進行**。誤クリック即時公開を構造排除。

### pull型の依頼体験（聖域の具現化）
1. CTA押下＝**依頼を投函するだけ**（同期実行ゼロ）。
2. トースト「◯◯を依頼しました（取り消し）」＋盤上部の**投げた依頼トレイ**にチケット追加。
3. 記事はバッジ変化し「待機中」へ静かに移動。
4. ループが拾い戻りが届くと、チケット緑点灯＋「戻りあり」へ昇格。
5. 盤最上部に**ループヘルス**「最終巡回◯分前✓ / 停止疑い⚠」常設。

### 公開前ゲート＝先出し→解錠
- draft到着時に `draftQuality.qualityChecks()` 実行→🔴🟡🟢サマリ帯。
- **block>0 → 公開予約ボタンを物理ロック**＋理由をボタン直上にインライン。
- 理由chipに【不足を直すよう依頼】併設（止血をpull依頼へ直結）。
- 全block解消で緑→**解錠アニメ**で活性化。

## 4. 機能の増減

**削る**: カンバン⇄リスト切替 / 表示密度トグル / ブランド配色トグル / 独立「プロンプト」面（ドロワー根拠へ降格） / 7タブ二段ナビ（縦1ページへ）。

**統合**: 本文行コメント＋修正案＋AIアドバイス→単一**校正レーン** / 修正依頼＋構成やり直し＋画像指示→段階文脈のサブアクション / 成績面＋公開キュー面→公開済み・予約まちステーション / 画像指示＋メディアライブラリ→素材レーン（draft時のみ）。

**追加**: 現在地ステッパー＋確信メーター / 投げた依頼トレイ / 公開前ゲート先出し→解錠 / ガード→依頼変換ボタン / Undo付き一括承認（ゲート全通過＋同段階のみ・block自動除外） / ループヘルスインジケータ / 要改稿→idea再投入。

## 6. 操作モデル

- **キーボード**: J/K=記事送り、Enter=ドロワーへ（承認ではない＝誤爆防止）、A=現在段階のプライマリ承認（文脈出し分け）、R=修正依頼、X=却下、E=本文インライン編集、Space=複数選択、Esc=閉。
- **一括**: 同段階＋品質ゲート全通過のみ→まとめて承認。**block記事は自動除外（安全弁）**。
- **⌘K**: 機能ランチャーにせず「記事横断ジャンプ＋段階フィルタ＋一括」に限定。
- **通知**: トースト＋依頼トレイ点灯＋件数バッジで受動的に気づける。Undoは段階遷移のみ（公開予約に適用せず誤公開防止）。
- **a11y**: 段階ステッパー=aria-current、ロック理由=aria-describedby、色のみ依存しないラベル併記、prefers-reduced-motion尊重。

## 7. 承認時に確定した3つの判断

1. **「要対応(横串)」と「段階ステーション」の二重表現** → **残す**（ラベルで割り切り。俯瞰と着地点の両立）。
2. **一括承認の安全境界** → **同段階＋ゲート全通過のみ・block自動除外・Undoは段階遷移のみ** で採用。
3. **プロンプト透明性** → **ドロワー折りたたみへ降格**（監査が重くなれば⌘K経由で復活）。

## 8. ステージ2（ビジュアル方向）への申し送り

1. 盤の段階遷移は framer-motion `layout` で滑らかに（状態変化の可読性に予算）。
2. 色トークンは `STAGE_META.tone`（amber/accent/purple/teal/gray/green）と `--p-*` を流用。配色トグルは廃止しテーマ固定。Teaser新パレット（黒/Deep Blue #11317B/Bright Blue #306EC3/Accent #F6FF54）との整合は要検討。
3. 状態の4色ドット（届いた/処理中/失敗/情報）に視覚予算を集中。
4. **解錠アニメ**（block全解消で公開予約活性化）が信頼体験の見せ場。
5. **確信メーター（6ドット＋3チェック）**の視覚言語を確立。
6. 情報密度の階調（要対応は広く/公開済みは詰める）を密度トークンで（手動トグルの代替）。
7. 新規実装が必要な4コンポーネント: 投げた依頼トレイ / 確信メーター / 左レール段階バッジ / Undo付き一括承認。基盤は既存 `types.ts`/`stages.ts`/`draftQuality.ts`/`reviseStatus`/`imageIntent.ts`/`BodyCommentView`/`ReviseCompareView` に乗る。
