# 記事レビュールーチン 設計書（2026-09-11）

> 目的: 公開済みのコラム・ニュースの改稿候補と、新規記事のネタを、根拠データ付きで毎週 Notion に置く「下ごしらえ」ルーチンと、その数字を決定的に出す集計スクリプトを作る。記事本文の執筆と公開は従来どおり対話と人間が行う。
> 上位の設計: `docs/superpowers/specs/2026-08-05-growth-copilot-design.md`（グロースコパイロット）。本書はその「記事」面の追加仕様であり、同書の原則（本番は人間・提案だけ増やさない・成功指標なき起票の禁止）を引き継ぐ。
> 集計・判定の共通契約: `docs/growth/analysis-contract.md`。記事判定表の正典: `docs/operations/interactive-analysis-runbook.md` ⑦。

## 1. 背景と決定事項

2026-08-04 に「無人生成→後追い検証」の記事パイプラインを負けと判定して廃止した（`docs/growth/playbook.md`）。学びは「人間レビューは生成と同時に走らせる」「提案だけ増える仕組みは死ぬ」。一方で 2026-09-09〜10 の記事分析（判定・改稿案・読者地域・内部リンク）は、毎回その場で書く ad-hoc スクリプトに依存しており再現性が無い。

ブレインストーミング（2026-09-11）で決めたこと:

| 論点 | 決定 | 却下した案 |
|---|---|---|
| ルーチンが記事に対してどこまでやるか | **下ごしらえまで**（改稿候補・新規ネタを根拠と方針付きで Notion に置く。本文は書かない） | 改稿本文まで作る／新規初稿まで無人で書く（廃止した構造に近い） |
| 頻度 | **週1（木曜）**は兆し検知+改稿候補1本+新規ネタ最大2件。**第1木曜**は28日窓の本判定 | 毎週フル判定（同じ結論の繰り返しになる） |
| 実行場所 | **ローカル日次タスク**（モーニングブリーフと同じ枠）。Web 検索・microCMS 読み取り・本番 HTML が使える | クラウド週次ドライバーへの追加（Web 検索と microCMS が使えない）／両方（二重管理） |
| 出力の置き場 | **Notion 記事ネタ案 DB の行 + 週次ブリーフページ**。行は「何をするか」、ブリーフは「なぜそう判断したか」 | DB だけ／リポジトリの markdown（スマホで読めず、対話から拾いにくい） |
| 新規ネタの深さ | **上位1件だけ本格リサーチ**（SERP 上位・一次情報候補・H2 構成案）。残りは軽い起票 | 全件本格リサーチ（読まれない調査ノートが積もる） |
| 作り方 | **集計スクリプト + プロンプト**（案2） | プロンプトだけ（数字の再現性が無い）／Notion 書き込みまでスクリプト化（スキーマ変更で壊れ、基盤が産出を上回る） |

## 2. 全体構成と流れ

```
木曜 07:30 labola-snapshot（既存・ローカル）
木曜 08:00 morning-brief（既存・ローカル）
木曜 08:30 article-review（新設・ローカル週次タスク。第1木曜は月次モード）
   │
   ├─ ① node scripts/analytics/reviewArticles.mjs [--monthly]
   │     GA4 + GSC + 本番 HTML を読み取り → out/article-review/<日付>.json と .md
   ├─ ② AI が JSON を読み、改稿候補 最大1本・新規ネタ 最大2件を選ぶ
   ├─ ③ 選んだ対象の主クエリだけ Web 検索で SERP 上位10を確認（合計5クエリまで）
   ├─ ④ 新規ネタの上位1件だけ本格リサーチ（一次情報候補・H2 構成案・excerpt 案）
   ├─ ⑤ Notion 記事ネタ案 DB: 既存行を更新 / 新規行を「提案中」で作成
   ├─ ⑥ Notion「記事レビュー」配下に週次ブリーフページを1枚作成
   └─ ⑦ 実行結果メッセージ: 結論3行 + ブリーフのリンク
木曜 10:00 weekly-driver（既存・クラウド）: Step R でブリーフの「## 記事アクション」表を収穫し判断部に載せる
```

- **分担**: スクリプトが「数字と判定表の当てはめ」を決定的に出す。AI は「解釈・SERP 比較・文章化・Notion 書き込み」だけを担う。スクリプトは何にも書き込まない（ローカルの `out/` への出力のみ。`out/` は `.gitignore` 済み）。
- **対話との共用**: 対話で「記事分析やろう」と言われたら同じスクリプトを叩き、同じ手順を手動で回す。これまで artifact で共有していた記事レビューは Notion のブリーフページに一本化する。
- **Mac 未起動の木曜**: 走らない。翌日以降に対話で手動実行する（モーニングブリーフと同じ扱い）。

## 3. 集計スクリプトの仕様

既存の作法（純関数モジュール + CLI。`scripts/analytics/articleMetrics.mjs` と `scripts/analytics/query.mjs` の関係）を踏襲する。

|---|---|---|

| `scripts/analytics/articleReview.test.ts` | 純関数のテスト（fixtures で全分岐、カバレッジ100%） | 新規 |
| `scripts/analytics/reviewArticles.mjs` | CLI。認証・取得・ファイル出力のみ。`node scripts/analytics/reviewArticles.mjs [--monthly] [--out out/article-review]` | 新規 |
| `scripts/analytics/reviewArticles.test.ts` | CLI のテスト（MSW） | 新規 |

| `scripts/analytics/query.mjs` | 変更しない。`.env.local` 読み込みと OAuth 取得の関数は `reviewArticles.mjs` に同じ形で持つ（`query.mjs` は export していないため。共通化は本書の範囲外） | 既存・変更なし |
| `scripts/analytics/fixtures/` | 既存ディレクトリに `article-review/` を追加 | 既存に追加 |

### 3.2 取得（すべて読み取り）

| ソース | 取るもの | 窓 |
|---|---|---|
| GA4 | 記事（`/columns/`・`/news/`。`/en/` は locale=en として別記事扱い）の入口セッション日次 | 56日 |
| GA4 | 入口×チャネル、入口×検索エンジン（Organic Search のみ）、入口×都道府県（`region`） | 28日 |
| GA4 | 記事ページの PV・ユーザー・エンゲージ時間、記事内イベント（`reservation_click`・`reserve_entry_click`・`external_link_click`・`instagram_click`・`content_click`）×設置箇所（`customEvent:location`） | 28日 |
| GSC | ページ×クエリ（記事）、ページ×日付（週次推移）、クエリ全体（需要ギャップ用。受けページは ページ×クエリ から最大表示のページを当てる） | 28日 / 56日 |
| 本番サイト HTML | 各記事の `<title>`・`meta description`・本文中のリンク先（内部リンク数の算出用） | 実行時 |
| microCMS 本番の読み取りキー（`GROWTH_MICROCMS_PROD_DOMAIN` と `GROWTH_MICROCMS_PROD_READ_KEY` が `.env.local` にあれば。既存の `MICROCMS_*` は dev サービスを指すため読まない。§7 前提⑤） | 公開日・改稿日（`publishedAt` / `revisedAt`） | 実行時。無ければ GA4 の初出日を代用し `meta.publishedAtSource = "ga4-first-seen"` を記す |

GSC は PT 基準・確定分のみで2日遅れ。窓の終端は「2日前」とし、`meta.windows` に GA4 と GSC の日付を別々に記す（共通契約）。

### 3.3 出力

`out/article-review/YYYY-MM-DD.json` と同名の `.md`（人が読む要約）。

```
{
  meta: { generatedAt, mode: "weekly"|"monthly", windows: { ga4: {...}, gsc: {...} },
          publishedAtSource, errors: [{ source, reason }] },
  articles: [{
    slug, locale, path, title, description, publishedAt, daysSincePublish,
    weeklyEntry: [{ weekStart, sessions }] (8週),
    last28: { entry, prevEntry, pv, users, engagedRate, avgDurationSec },
    channels: { organicSearch, direct, social, referral, other },
    yahooShare, regions: { chibaShare, tokyoShare, top3: [...] },
    cta: { per100pv, byLocation: {...} },
    queries: [{ query, impressions, clicks, ctr, position }] (非指名上位15),
    brandImpressions,
    hint: "too_early"|"title_desc_rewrite"|"body_boost"|"cta_check"|"continue"|"sunset_candidate"|"no_data",
    flags: ["weekly_spike","katakana_gap","no_inbound_links","stale_date_text"]
  }],
  demandGaps: [{ query, impressions, clicks, position, bestPage, bestPagePosition }]
}
```

- `articles[]` は ja・en を別行にする。ブリーフの判定対象は ja のみで、en は数字だけ載せる。
- `demandGaps[]` は非指名で表示 ≥ 30、かつ受けページがホーム（`/`）または受けページの順位 > 8 のクエリ。
- `meta.errors` に失敗した取得を残す。失敗した項目の値は `null`（0 で埋めない）。

### 3.4 判定ヒント（runbook ⑦ の表を上から当て、最初に当たった1つ）

| 順 | ヒント | 条件 |
|---|---|---|
| 1 | `too_early` | 公開14日未満 |
| 2 | `title_desc_rewrite` | 非指名の平均順位 ≤ 5 かつ 非指名 CTR < 5% |
| 3 | `body_boost` | 非指名表示 ≥ 100 かつ 順位 4〜10 |
| 4 | `cta_check` | 入口セッション ≥ 10 かつ CTA < 8 回/100PV |
| 5 | `continue` | 入口セッション ≥ 5 |
| 6 | `sunset_candidate` | 非指名表示 < 10 かつ 入口セッション < 3 |
| 7 | `no_data` | 上のどれにも当たらない、または取得不可で判定に必要な値が `null` |

条件の値はすべて28日窓。`title_desc_rewrite` を当てる前に指名表示を別列で出す（指名クエリはホームがクリックを取るため記事側 CTR が低く出るのが正常。runbook の注意）。

### 3.5 フラグ（ヒントとは独立に付く）

| フラグ | 条件 |
|---|---|
| `weekly_spike` | 直近7日の入口が前7日比 ±30% 超 |
| `katakana_gap` | 非指名上位5クエリに含まれるカタカナ語（例「ハイロックス」）が `<title>` に無い |
| `no_inbound_links` | 他の記事本文からのリンクが0本（本番 HTML のリンク先を集計） |
| `stale_date_text` | 本文に「◯月◯日時点」形の表記があり、その日付が28日超前 |

### 3.6 エラー処理・性能

- 取得は1本ずつ独立させる。1つ失敗しても他は出し、`meta.errors` に残す。失敗があれば終了コード1で JSON は書く（共通契約「失敗を 0 にしない」）。
- 実行時間の目安は GA4 7回・GSC 3回・HTML 最大20本で1分以内。API 呼び出しは 15 秒タイムアウト。

## 4. ルーチンの手順と出力

### 4.1 置き場とスケジュール

- プロンプトの正本: `docs/growth/routines/article-review.md`（新規）。
- ローカルタスク: `~/.claude/scheduled-tasks/article-review/SKILL.md`（新規）。正本へのポインタ+フォールバック+絶対の制約のみ（モーニングブリーフと同じ二重管理なし方式）。
- スケジュール: 木曜 08:30 JST（cron 式 `30 8 * * 4` で登録。§7 前提①・確認済み）。第1木曜（JST で 1〜7 日）は月次モード。実行には最大約10分のジッターが付くため、週次ドライバー（10:00）より前に終わるよう §3.6 の実行時間を守る。

### 4.2 手順

1. **正典を読む**: `analysis-contract.md`、`playbook.md`、`seasonal.md`（3週先読み）、`CLAUDE.md`「記事の対話運用」、Notion 記事ネタ案の「提案中」「下書き作成済み」行、前週のブリーフページ。
2. **スクリプト実行**: `node scripts/analytics/reviewArticles.mjs`（第1木曜は `--monthly`）。`meta.errors` にある項目は「取得不可」と書き、0 や推測で埋めない。スクリプト自体が起動できない場合は Notion に何も書かず、失敗理由だけをメッセージで残して終了する。
3. **候補を選ぶ**:
   - 改稿候補は最大1本。ヒントが `title_desc_rewrite`・`body_boost`・`cta_check` の記事のうち非指名表示が最大のもの。ただし記事ネタ案の「28日判定日」「56日判定日」「90日判定日」のいずれかが未来、または施策提案 DB で「計測中」「判定待ち」の施策に紐づく記事は除外し、「判定待ち」として表に載せる。
   - 新規ネタは最大2件。`demandGaps`、`seasonal.md` のトリガー（3週以内）、HYROX 大会マイルストーンから選ぶ。既存記事または「提案中」「下書き作成済み」の行と検索意図が実質同一なら起票せず、ブリーフに理由を1行書く（CLAUDE.md のカニバリ回避）。
4. **SERP 確認**: 選んだ対象の主クエリ、合計5クエリまで。上位10のタイトルと種別（公式／ポータル／ジム／記事）を記録し、「勝てる角度」を1行で書く。
5. **本格リサーチ（新規の上位1件のみ）**: 一次情報候補の URL、H2 構成案、既存記事との差分、excerpt 案（結論先出し120〜160字）。未確定情報（料金・日程）は「要一次確認」を付け、断定しない。
6. **Notion 記事ネタ案 DB に書く**:
   - 公開済み記事の既存行: 「公開後判定」「成績データ」（1行の要約）「成績更新時刻」を更新。改稿候補には「修正タイトル案」「修正案」（方針。本文は書かない）。
   - 新規ネタ: 「提案中」で新規行。媒体・記事タイプ・コラムカテゴリ・検索意図・根拠・狙う読者・想定CTA・成功指標。上位1件は「構成案」「一次情報メモ」も。
   - 成功指標の既定値: 「公開28日で入口セッション ≥ 5（runbook ⑦ の継続ライン）、56日で狙うクエリの非指名順位 ≤ 10」。狙うクエリの表示数と現状の受けページは「根拠」に書く。判定日は起票時には書かず、公開後に「28日判定日」「56日判定日」「90日判定日」の3列へ公開日+28/56/90日で入れる（既存記事の運用と同じ）。
   - 冪等性: タイトル案が同一の「提案中」行が既にあれば新規行を作らず、その行の「根拠」「成績更新時刻」だけを更新する。公開済み記事の行は常に上書き更新する。
   - 書き込み順は DB 行→ブリーフに固定する。途中で失敗したら残りは書かず、完了分と未完了分をメッセージに列挙する（翌週は冪等ルールにより同じ状態から再開できる）。
   - 対応表: ヒント `continue` → 公開後判定「成功」／`too_early`・判定窓の途中 → 「様子見」／`title_desc_rewrite`・`body_boost`・`cta_check` → 「要改稿」／`sunset_candidate` → 公開後判定は変えず「ステータス」を「クローズ」にし、判定メモに理由を書く。
7. **週次ブリーフ**: Notion「記事レビュー」ページの配下に1枚作成。節は固定: 結論（3行）／**記事アクション表**／記事別の数字／SERP 比較／需要ギャップ／注記（取得不可・並走メモ）。同じ日付のブリーフが既にあれば新規作成せず上書き更新する（同日の再実行・再試行で2枚にしない）。
8. **メッセージ**: 結論3行とブリーフのリンク。

### 4.3 記事アクション表の契約（週次ドライバー Step R が収穫する）

列と語彙を固定する。

| 対象 | 種別 | 理由 | 判定日 | Notion |
|---|---|---|---|---|
| 記事のスラッグまたはネタ名 | `改稿` / `新規` / `看取り` / `判定待ち` / `公開待ち` | 1行 | YYYY-MM-DD または `-` | 行またはページの URL |

`docs/growth/routines/weekly-driver.md` の Step R に「R1b. 記事レビューの収穫」を追加し、当週のブリーフからこの表だけを読み、判断部の「今週のアクション」候補に載せる（本書の実装範囲）。

### 4.4 月次モード（第1木曜）

上に加えて、全記事（ja）の判定表（runbook ⑦ の月初作業の代替）、看取り候補、翌月の執筆枠（最大2本）を出す。判定の確定は対話でオーナーが行い、本番は何も変わらないため 48 時間の自動確定は使わない。`docs/operations/interactive-analysis-runbook.md` ⑥⑦ にこのルーチンへの参照を1行足す。

## 5. ガードレール

- ルーチンは microCMS に書かない（読み取りキーでの読み取りのみ）。本文・下書きを作らない。コード変更・PR も作らない。
- Notion への書き込みは記事ネタ案 DB と「記事レビュー」配下のブリーフだけ。施策提案 DB は判定窓の除外判定（§4.2 手順3）のための読み取りのみで、書き込まない。予約台帳・会員台帳は読まない（個人情報は経路に入らない）。
- 1回の実行で起票するのは改稿1本+新規2件まで。超えた候補は「次週の候補」としてブリーフに1行で残す。
- 起票の必須条件: 狙うクエリの表示数と現状の受けページ、カニバリ判定、成功指標（§4.2 手順6の既定値）。書けないネタは起票しない（playbook「成功指標・閾値・検証日が決まらない施策は起票しない」の記事版）。
- 判定窓の途中にある記事は改稿候補にしない。外部要因で交絡した場合は「判定不能・ベースライン再設定」の提案に留める。
- 未確定情報は「要一次確認」を付け、断定で書かない。
- 実行が失敗した日は何も書かず、失敗理由だけメッセージで残す。
- Notion の読み取りは検索・ビュー読み取りを基本とし、SQL（`query_data_sources`）は使えたときだけ使う（既存ルーチンと同じ運用。§7 前提②）。

## 6. テストと並走

- 純関数: fixtures（`scripts/analytics/fixtures/article-review/`）で判定ヒント7種の全分岐、フラグ4種、需要ギャップ抽出、週次集計、指名除外、前期なし・取得不可の扱いを網羅する。カバレッジ100%（CI の閾値）。
- CLI: MSW で「正常」「GSC 失敗で部分出力+終了コード1」「microCMS キー無しで GA4 初出日代用」「記事0件」の4ケース。実 API は叩かない。`.env.local` は読まず一時ファイルを使う（`query.test.ts` と同じ方式）。
- 並走: 初回の2週間は、ルーチンの出力と私が対話で出す判定を突き合わせ、差分をブリーフの「注記」に「並走メモ」として残す。差分の原因がスクリプト側なら修正、解釈側なら正本のプロンプトを直す。並走の終了条件は「2週連続で、ルーチンの改稿候補と新規ネタの選択が対話の判定と一致すること」。不一致なら原因を直してもう1週延ばす（最長4週。4週で一致しなければ §8 の判定を前倒しして設計に戻す）。

## 7. 前提（実装前に確認する）

| # | 前提 | 確認方法 | 外れたときの扱い |
|---|---|---|---|
| ① | ローカルの scheduled-tasks は cron 式で登録され（例: morning-brief は `0 8 * * *`）、木曜のみの `30 8 * * 4` を指定できる。実行には最大約10分のジッターが付く | **確認済み**（2026-09-11、`list_scheduled_tasks` の登録内容） | ジッター込みで週次ドライバー 10:00 より前に終わるよう、§3.6 の実行時間を超えたら SERP 確認のクエリ数を減らす |

## 8. 成功条件（12週後にこの仕組み自体を判定する）

- 起票した改稿・新規のうち、対話で実行に至った割合が 50% 以上（「提案だけ増える」構図の検知）。
- 記事の非指名入口セッション（28日窓、ja 記事1本あたりの中央値）が開始時点比で増えている。
- オーナーが木曜に読む時間が5分以内（ブリーフの結論3行で判断が完結する）。
- Mac 未起動などで欠けた週が 12 週中 4 週を超えたら、数字部分だけクラウド実行へ移す再設計を検討する。
