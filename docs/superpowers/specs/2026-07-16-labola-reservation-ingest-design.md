## 1. 位置づけと目的

**本基盤は記事グロース専用ではない。** THE PICKLE BANG THEORY の意思決定全般 — 記事・料金・プログラム編成・販促・CRM・B2B営業・設備・財務 — が**同じ一次データと同じ統計ガードレールの上で行われる**ための経営データ基盤であり、記事グロースループはその消費者の一つに過ぎない。「記事特化」でも漠然とした「ビジネス特化」でもなく、**意思決定特化**: どんな判断にも「根拠となる実測値」と「その確からしさ(n・信頼区間)」を添えられる状態を作る。

消費者(現時点):
① 人間の判断(経営ボード・LINEダイジェスト)
② KPI管理(実予約の真値→KPIツリー)
③ AI記事ループ(ネタ選定・成功指標・改稿判定・学習ログ)
④ AI施策提案(料金・プログラム・販促などの施策カード §11)
将来: freee会計との突合(損益・損益分岐稼働率)、資金調達・報告資料、SNS/検索データとの統合コックピット。

目的:

1. 実予約の**真値**をKPIツリーへ供給する(北極星)。
2. ラボーラCSV群を仮名化イベントレベルで正準化し、**過去に遡って任意の分析ができる資産**として蓄積する。
3. **小さな変化を機械が拾う**: 人間がCSVを眺めても気づけない初出・変化点・逸脱を、統計的裏付き「気づき」として毎週自動検出し、LINEとダッシュボードに届ける。
4. タグ面(予約画面コンバージョンタグ+GA4クロスドメイン)で**記事→予約完了の帰属**を取る。

## 2. 全体アーキテクチャ

```
【自宅PC】
ラボーラCSV一式(Shift_JIS・PII入り) → ドロップディレクトリ(GROWTH_LABOLA_DROP_DIR)
  ↓ npm run growth:ingest(週次。cron+フォルダ監視で自動化可)
  ├─ ヘッダー署名でCSV種別判定(§4) → SJISデコード → zod検証 → テスト予約除外
  ├─ 【PII境界】仮名化・粗視化(§6)。PIIはこのプロセスのメモリ内で消滅
  ├─ (1) 正準データセット更新: data/reservations/canonical/*.jsonl(全履歴・仮名化済み)
  ├─ (2) インサイトエンジン実行: 集計カタログ(§5) + 気づき検出(§7)
  ├─ (3) スナップショットバンドル生成: snapshot-YYYY-MM-DD.json(集計+気づき+小型時系列)
  ├─ (4) POST /api/growth/analytics/snapshot(Bearer) → Vercel Blob(private)
  ├─ (5) LINE週次ダイジェスト送信(実予約サマリ+気づきTop N)
  └─ (6) 備考欄レビューMD出力(人間専用・AI非投入)
metrics-cli(GA4/GSC取得)は正準データセットを直接読み、記事別Notionミラーへ実予約状態を書く(従来の役割を維持、CSV/sidecar読み取りは削除)

【Vercel(承認画面と同居)】
/api/growth/analytics/snapshot  … PCからの受領・Blob保存(強Bearer+レート制限)
/growth/analytics               … 分析ボード(§8。承認画面と同じ認証の内側)
                                   表示経路はBlobスナップショット読み取り専用(GA4/microCMS/Notionを叩かない)
```

設計原則は既存正典を踏襲する: pull型の趣旨(重い処理はPC側)/公開系操作なし(本基盤は読み取り分析のみ)/純ロジック分離/欠落耐性/失敗を沈黙させない。

## 3. 運用(週次ルーチンを5分以内に)

1. **エクスポート(人間・約2分)**: ラボーラ管理画面から全期間指定なしで一括ダウンロード(予約一覧詳細は必須。顧客・会員・売上・売上サマリ・スクール/イベント/個人参加・予約不可は推奨)。ダウンロード先=ドロップディレクトリ。
2. **取り込み(自動)**: `npm run growth:ingest`。フォルダ監視モード(`--watch` または PC cron)なら置くだけで実行。冪等(同一入力の再実行は同一結果)。`GROWTH_DRYRUN=1` で書き込みなし検証。
3. **受け取り(自動)**: LINEに「今週の実予約 n件(累積N)/気づき◯件(上位3件本文)/ダッシュボード更新済み」。失敗時は工程名+再開コマンド付きでLINE通知(既存原則)。
4. **鮮度の見張り(自動)**: 最新スナップショットが7日を超えたら、ダッシュボードに「データが古い」バナー+LINEリマインド(エクスポート忘れ防止)。
5. 月次: ダッシュボードでトレンド確認。四半期: KPI基準値の見直し(60-kpi-tree の既定に従う)。

## 4. 入力: CSV種別判定と利用列

ファイル名に依存せず**ヘッダー行の署名**で判定。同種別が複数あれば mtime 最新を採用し警告。文字コードは Shift_JIS(CP932)、`TextDecoder("shift_jis")` でデコード(不能バイトはエラー停止)。

| 種別 | 判定署名(先頭列) | 必須/任意 |
|---|---|---|
| 予約一覧詳細 | `予約番号,予約内容,日付,開始時間` | **必須** |
| 顧客一覧詳細 | `登録日,顧客タイプ,登録ステータス` | 任意 |
| 会員一覧詳細 | `登録日,会員タイプ,登録ステータス` | 任意 |
| 売上明細 | `売上日時,分類,品目` | 任意 |
| 売上サマリ | `売上日,レンタルスペース` | 任意 |
| スクール/イベント/個人参加一覧 | `名称,カテゴリ,スポーツ,開催日` | 任意 |
| 予約不可一覧 | `日付,開始時間,終了時間,スペース` | 任意 |
| MINERVA | 先頭行 `対象期間` | 任意(自前集計との突合検証用) |

- 任意CSVが欠けても停止しない。依存する集計・気づきは `missing` を記録(欠落耐性)。
- `予約ステータス` 写像: `予約完了→confirmed` / `キャンセル→cancelled`。**未知値は即エラー停止**(写像は明示的に増やす)。
- テスト予約除外: `scripts/growth/assets/reservation-exclusions.json`(メール完全一致+名前部分一致)。除外件数は meta に記録。
- エクスポートは**毎回全期間**が前提。収録範囲メタ(`coverageStart=2026-06-01` 固定env / `coverageEnd=予約CSVファイル更新時刻(sourceSyncedAt)のJST日付`)を正準データセットに持たせる。取り込み実行日ではなくCSVのmtimeを終端にすることで、古いCSVの再取り込みが鮮度・収録範囲を偽装できない(レビューR3-01/R4-01対応)。分析窓・週次系列・鮮度判定はすべて `sourceSyncedAt`/coverage を基準にする。CSV内の受付日時の最古/最新と矛盾したら警告。

## 5. 正準データセットとスナップショット

### 5.1 正準データセット(イベントレベル・仮名化済み・PC内)

`GROWTH_RESERVATION_DATA_DIR/canonical/` に JSONL で保持。**集計前の粒度を保存する**ことで、将来の新しい問いに再エクスポートなしで答える。

- `reservations.jsonl`: 1行=1予約。`reservation_id, booked_at, use_date, start, end, category, space, status, accept_status, payment_status, payment_method, plan, amount, party_size, channel(user_sp|user_pc|admin), customer_type, pseudo_id, ward, age_band, gender, occupation_group, has_remarks`
- `customers.jsonl`: `pseudo_id, first_seen, customer_type, member_no_hash, registered_at, ward, age_band, gender, occupation_group, last_use_by_category`
- `programs.jsonl`: スクール/イベント/個人参加の回別 `name, held_on, start, end, capacity, accept_from_visitor/member, status`
- `blocked_slots.jsonl` / `sales_daily.jsonl`(見込みフラグ付き)
- `meta.json`: coverage・入力ファイル・除外件数・スキーマバージョン

各実行時に全量再構築(入力が全期間エクスポートなので差分管理不要=冪等)。実行ごとの meta 履歴は `runs/` に残す。

### 5.2 スナップショットバンドル(配信用)

`snapshot-YYYY-MM-DD.json`(zodスキーマ)。**個票なし・全て集計値**。内容: `meta` / `kpi`(北極星系)/ `catalog`(下表)/ `insights`(§7)/ `series`(ダッシュボード描画用の小型時系列: 週次予約数・売上・セルフ比率・捕捉率等、各≤100点)。ローカル蓄積+Vercel BlobへPOST。過去分は消さない(ペースカーブの原資)。

### 5.3 集計カタログ

**A. 獲得**: セルフ予約比率(スマホ/PC/管理者代行)・顧客タイプ別予約数・(P3以降)記事別予約完了/チャネル別CVR/画面別離脱率/捕捉率。
**B. 需要とイールド**: 曜日×時間帯×カテゴリー需要ヒートマップ/リードタイム分布(中央値・p25/p75)/RevPACH(予約不可枠を除いた実効コート時間あたり売上)/キャンセル率(リードタイム帯別)/プログラム回別埋まり率と**満枠到達速度**(受付開始→満枠時間)/将来28日の on-the-books とブッキングペースカーブ(履歴比較)/売上パイプライン(見込み行、前回スナップショット比の毀損検知含む)。
**C. 顧客**: ビジター→会員転換率・転換日数/リピート(初回→2回目転換率・来店間隔中央値・回数分布)/カテゴリー間クロスセルマトリクス/初回利用月コホート(人数・残存・累積売上=簡易LTV)/商圏(市区町村別)/年代×性別×顧客タイプ分布・職業上位。
**D. 運用・お金**: 未収金(入金待ち件数・金額・経過日数帯)/支払い方法構成/予約不可枠内訳(貸切による提供停止コマの機会費用)。

## 6. PII境界(絶対条件)

- PII生値(氏名・ふりがな・メール・電話・番地以下住所・生年月日)は ingest プロセスのメモリ内のみ。正準データセット・スナップショット・Blob・Notion・LINE・AIプロンプトのどこにも書かない。
- 仮名ID: `HMAC-SHA256(小文字化メール, GROWTH_ANALYTICS_HASH_KEY)` 先頭16hex。メール欠落時は会員番号ハッシュ、両方無ければ突合対象外。キーは server-only env。
- 住所→市区町村 / 生年月日→年代(10歳刻み)/ 職業→粗いグループ(会社員・医療・学生・経営者・その他)。
- **公開面(Notionレポート・AI入力・LINE)は k=3 未満のセグメントを抑制**。認証済みダッシュボードはオーナー自身の業務データのため k 制約を緩和するが、氏名等は元から存在しない。
- 備考欄はB2B需要シグナルの宝(実例:「16人でイベント開催したい」)だが氏名混入があり得るため、`remarks-review-*.md`(人間専用)にのみ出力。ダッシュボードには件数のみ表示。

## 7. 気づき検出エンジン(本設計の心臓部)

毎回の ingest で正準データセット+スナップショット履歴に対して検出器を全走査し、`insights[]` を生成する。**「小さな数字の変化を見逃さない」をルール+統計検定で機械化**する。

### 7.1 気づきオブジェクト

`{ id, detector, severity: info|notice|alert, title, body, evidence: {n, value, baseline, ci|p}, label: 有意|観察, first_seen, status: new|recurring }`
同一気づきは `id`(検出器+対象キー)で重複排除し、`first_seen` を保持。新規のみLINEに載せ、ダッシュボードには全量。

### 7.2 検出器カタログ

| # | 検出器 | 何を拾うか | 統計・判定 |
|---|---|---|---|
| D1 | 初出検知 | 新しい市区町村からの初予約、新職業グループ、新チーム名、最遠来訪更新、新カテゴリー組合せの初利用 | 集合差分(統計不要。小さい今こそ1件が意味を持つ) |
| D2 | 件数変化点 | 週次予約数・カテゴリー別件数の急変 | Poisson exact test(前4週平均を基準、p<0.05で「有意」、それ未満は「観察」) |
| D3 | 率の変化 | キャンセル率・セルフ予約比率・ビジター比率のシフト | Wilson 95%CI の非重複判定 |
| D4 | リードタイム変化 | 予約が入るタイミングの前倒し/直前化 | 中央値±MAD、4週窓比較 |
| D5 | 満枠速度 | プログラムが過去より速く/遅く埋まる | 受付開始→満枠時間の過去回比較(最速更新は即 notice) |
| D6 | ペース逸脱 | 将来週の on-the-books が過去同時点より弱い/強い | スナップショット履歴の同 days-out 比較(履歴6週未満は `collecting`) |
| D7 | ライフサイクル事象 | 初のリピート発生、ビジター→会員転換、コホート初回2回目転換 | 事象検知(n が小さいうちは個別事象が気づき:「6月コホートから初のリピート」) |
| D8 | 休眠リスク | 常連(3回以上)の来店間隔が個人中央値×2超過 | 個人別間隔中央値(該当者は仮名IDと直近利用のみ表示) |
| D9 | パイプライン毀損 | 見込み売上が前回スナップショット比で減少(キャンセル起因) | スナップショット差分 |
| D10 | 未収金滞留 | 入金待ちが14日超 | 閾値 |
| D11 | 計測健全性 | GA4捕捉率の急落(**タグ破損の自動検知**)、CSV鮮度7日超、必須CSV欠落、種別行数の異常減 | 捕捉率はD3同様CI、他は閾値 |
| D12 | 需要シグナル | 備考欄の新規問い合わせ(件数のみ。本文は人間レビューMDへ) | 新規行検知 |
| D13 | キャンセル再販 | キャンセル枠が利用日までに再予約されたか(再販率・所要時間) | 枠キー(日付×時間×スペース)の突合 |

### 7.3 誤検知との付き合い方

- すべての気づきに `n` と根拠(CI/p値/基準値)を必ず添付。n<10 由来は自動的に「観察」ラベル。
- 週あたりLINE掲載は severity 順に最大5件(残りはダッシュボード)。
- 検出器はすべて純ロジック(`insightDetectors/` 配下に1検出器1ファイル)+ 個別テスト。閾値は定数ファイルに集約し、チューニング履歴をコメントでなくgitで追う。

## 8. UI: 経営ボード `/growth/analytics`

承認画面と同じ認証(APPROVE_AUTH)の内側に新設。**Blobスナップショット読み取り専用**(UIからGA4/microCMS/Notionを叩かない)。ブランドは承認画面に合わせダーク+アクセント。モバイル閲覧を第一級で考慮(オーナーはスマホで見る)。

### 8.1 レイアウト(上から)

1. **KPIヘッダー**: 北極星カード群 — 実予約(今週/累積、スパークライン付き)・Web獲得予約(セルフ予約)・売上(今週/見込み28日)・稼働率。各カードは4週移動平均の向きを矢印表示。n<10 の前週比%は出さない(実数+累積)。
2. **気づきフィード**: §7 の insights を新しい順にカード表示。severity バッジ(info/notice/alert)、「有意/観察」ラベル、根拠チップ(n=、CI)。alert(タグ破損・鮮度切れ)は最上部固定。
3. **ファネル**(P3解禁): 記事セッション→予約クリック→labola入力→確認→完了→実予約(真値)。捕捉率を注記。段間の離脱%。
4. **需要ヒートマップ**: 曜日×時間帯のコマ数(カテゴリー切替タブ)。予約不可枠は網掛け。
5. **ブッキングペースカーブ**(履歴6週で解禁、それまで「収集中」): 今後4週の各週について「利用日N日前時点の埋まり率」を過去実績帯(min-max)と重ね描き。弱い週が一目で分かる。
6. **商圏**: 市区町村別の顧客数・予約数 横棒。初出の区はNEWバッジ(D1連動)。
7. **顧客**: コホート残存表(初回月×経過月)・ビジター→会員転換・クロスセルマトリクス・年代×性別分布。
8. **プログラム**: 回別埋まり率と満枠到達速度のランキング。
9. **お金**: 売上パイプライン(確定+見込みの積み上げ)・未収金・支払い方法構成。
10. フッター: データ鮮度(スナップショット日時)・入力ファイル内訳・除外件数(meta)。

### 8.2 実装方針

- 依存追加なしを基本: チャートは軽量な自前SVG(スパークライン・棒・ヒートマップ程度なら既存スタックで十分。Framer Motionは既にある)。饱和したライブラリ導入はP4で再検討。
- スナップショット一覧は Blob の list + 最新 fetch。履歴セレクタで過去週の表示も可(ペースカーブは履歴を内部利用)。
- `snapshot` zodスキーマは UI/CLI で共有(`src/lib/growth/` 再エクスポート)。
- 鮮度7日超は全画面バナー。`collecting` セクションは理由文言付きプレースホルダー(早すぎる結論を構造的に防ぐ§9)。

### 8.3 API

- `POST /api/growth/analytics/snapshot`: PCからの受領。`Authorization: Bearer GROWTH_ANALYTICS_INGEST_TOKEN`(承認画面ユーザートークンとは別の強ランダム値)。zod検証→Vercel Blob(private, `analytics/snapshot-YYYY-MM-DD.json`)。既存 authRateLimit を適用。5MB上限。
- `GET` 系はサーバーコンポーネントから直接 Blob SDK で読む(公開APIは作らない)。

## 9. 統計ガードレール(公開面・AI面に適用)

1. 率には Wilson 95%CI を併記。2. n<10 の前週比%は出力禁止(実数+4週累計)。3. 主要指標は累積カーブを第一表示。4. 履歴6週未満の比較分析は `collecting`。5. 公開面は k=3 抑制。6. 週次レポート文面には「n=◯のため参考値」を機械付与し、断定回避の正典(facility-context doNotWrite)に従う。実装は `reservationStats.ts` に集約し、レポート生成プロンプトにも明記。

## 10. タグ面(P3): 予約ファネル計測と記事帰属

ラボーラ管理画面「システム設定>予約サービス>予約画面」の**画面別コンバージョンタグ欄**(情報入/内容確認/仮予約/予約完了、任意タグ貼り付け)を確認済み。

- 4画面に自社サイトと同一測定IDの gtag.js + 画面別イベント: `labola_step_input` / `labola_step_confirm` / `labola_reserve_pending` / `labola_reserve_complete`(キーイベント登録)。
- GA4管理>データストリーム>タグ設定>ドメインに `yoyaku.labola.jp` を追加(クロスドメイン)。
- metrics-cli 拡張: landingPage×event レポートで記事別予約完了を取得。既存の予約意図(reservation_click+reserve_entry_click)の定義は変えず、**別バケット**として扱う。KPIツリーに「予約完了(GA4・捕捉率付き)」層を追記。
- 捕捉率 = GA4完了 ÷ 正準データセットのセルフ予約数(同期間)。D11がタグ破損を自動検知。
- 未確定: タグ欄の `<script>` サニタイズ有無(不可なら Measurement Protocol ピクセルにフォールバック)/プログラム系フローの同等欄有無 — 設定作業時に実地確認。

### P3a(設置フェーズ)確定事項 — 2026-07-18

- 進め方は2段階: **P3a**(貼り付け用タグ+設置手順書→人間が設置・実地確認)→ **P3b**(確定した挙動に合わせて metrics-cli 拡張・ファネル・捕捉率・D11 を実装)。
- page_view は**デフォルトのまま送る**(クロスドメインのセッション接続の確実性優先)。labola の URL が topPages 等に混入する問題は P3b の metrics-cli 側でフィルタする。

## 11. AI・施策提案への接続(コンテンツと経営施策の両方)

データ基盤(P1〜P2)だけでは、記事ネタ提案・advise・週次レポートの質は自動では上がらない。以下の経路で明示的に接続する。

### 経路1: 週次レポート(Notion)

- スナップショット最新を読み「予約分析」セクションを追加。**数値と文面部品はコード側で生成**(§9のガードレール適用済み: CI併記・n注記・k=3抑制)。AIは並べ替え・要約のみを行い、数値の再計算や断定はさせない。

### 経路2: 記事ネタ提案への「データ根拠パック」注入

- スナップショットから公開面フィルタ済みの **`publicFacingPack`**(純ロジックで生成)を提案生成プロンプトに注入する。内容: 新規気づき(公開面適格のみ)・商圏上位と初出エリア・プログラム埋まり率・ペルソナ分布・リードタイム中央値。
- 提案カードには **根拠(evidence)欄を必須化**: 「葛飾区から初予約(n=1・観察)→ ローカル記事候補」「ビギナークラス埋まり17% → 不安解消記事」のように、どのデータがそのネタを支持するかを明示。根拠なしの提案も許すが「根拠なし」ラベルを付ける。
- ネタ変換の型: D1初出商圏→ローカルSEO記事 / D5満枠速度→人気枠・増枠の告知記事 / プログラム閑散→不安解消・体験記事 / D12備考問い合わせ→団体利用ガイド記事。

### 経路3: 成功指標の実測化

- 記事ごとの `成功指標`(Notion)の下書きを、60-kpi-tree の型別目安 × 実データ(現状の予約意図・実予約水準)から自動生成する。「実測に照らして達成可能な目標」になる。

### 経路4: 改稿判定・学習ログの真値化(P3後)

- 記事別の予約完了(GA4帰属)と実予約(真値)が取れると、metricsReview の改稿判定と SI1 学習ログの成果ラベルが「views/クリック」から「予約」ベースに強化される。「どんな記事が予約を生むか」の学習が回り始める。

### 経路5: 施策提案カード(記事以外の経営施策)

- `publicFacingPack` を記事ネタ専用にせず、**施策提案カード**の生成にも使う。週次で数枚、承認画面の提案欄に記事ネタと並べて提示する。
- カードの構造: `施策種別(料金 / プログラム / 販促 / CRM / B2B / 設備・運用 / 財務)・提案本文・根拠(気づきID+n+CI)・推定インパクト・最小実験の設計(1変数・4週窓・判定条件)`。
- 例: 「D5: 早朝ピックルが受付48hで満枠(過去最速)→ 同条件で木曜以外にも増枠。4週後の埋まり率で判定」「D13: 前日キャンセルの再販率20% → キャンセル期限を48時間前に変更する案。導入前後4週のキャンセル率と稼働で判定」「ビギナークラス埋まり17% × 経験者満枠 → 体験会の新設(記事ネタとセットで提案)」。
- **実行判断・実施は常に人間**。AIは根拠付きの選択肢を出すだけ(既存の設計思想と同じ)。料金など不可逆性の高い施策カードには「有意/観察」ラベルの明示を必須にし、「観察」のみを根拠とする値上げ・ポリシー厳格化は提案文中に注意書きを自動付与する。
- 施策カードの採否・結果は学習ログ(SI1)に記録し、「どの種類の根拠が採用されやすく、成果につながったか」を蓄積する。

### 制約(正典優先)

- 記事**本文**へのデータ利用は facility-context の doNotWrite を優先。個票・n<10 の断定・金額の詳細は本文に書かない。書けるのは「早朝枠は満席が続いています」等の定性事実のみで、その判定(満枠が2回以上継続 等)もコード側ガードレールの通過を条件にする。
- `publicFacingPack` の生成は P1 に含め(スナップショットと同時出力)、各ループのプロンプト改修は P5 で行う。
