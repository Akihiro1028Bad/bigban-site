## 1. 背景・目的

### 1.1 監査3本の要約

記事品質を3つの視点で監査した(2026-07-05・Opus)。総括すると、**ガードレール(やってはいけないこと)は業界水準超えだが、「プロが良い記事を能動的に作る」正のドライバーが弱く、事故らない凡庸な記事を安定生産する設計になっている**。加えて、下書き段階では必須の AI 免責注記が**公開時に除去されず本番に残る設計穴**、および**学習ループが却下理由をコードで供給していないバグ**が見つかった。

| 監査 | 対象 | 総評 |
|---|---|---|
| **①プロンプト/文体** | `drafts.md`・`examples/*`・`growth-article-style.md`・`facility-context.json` | few-shot 例が「凡庸さのお手本」になり AI がそれを上限として学習。§11 ルブリックが「自己採点せよ」で終わり生成に接続されていない。E-E-A-T の一次情報が執筆 AI の創作に倒れる矛盾。 |
| **②実記事のプロ批評** | 公開済み記事「市川でピックルボールができる場所と、屋内専用という選び方」(唯一の本文入り記事) | AI 記事として上位(68点)だが、全編が説明で情景・人・体験がゼロ、同型段落の反復(AI の指紋)、ヘッジ過多で背中を押しきれない。**公開記事に AI 免責注記が残存(公開バグ)**。 |
| **③週次/ネタ選定** | `weekly.md`・runbook・`existing.ts`・`metricsReview.ts` | 執筆段階の品質担保は業界水準超え。一方、入口(ネタ選定・構成案・学習ループ)に構造的穴。**`ideaLines()` が却下理由を週次に渡していない(コードバグ相当)**。 |

### 1.3 目的

1. **設計穴を塞ぐ(即対応)**: 公開記事から AI 免責注記を除去する純ロジックを両公開経路に挟む(S1)。学習ループの却下理由をコードで供給する(S2)。

## 3. 即対応の詳細設計

### 3.1 即対応1: AI 注記の公開時除去

#### 3.1.1 設計穴の正確な把握

- 文体ガイド §5 は「末尾に必ず『※この記事はAIが作成した下書きです。公開前に内容をご確認ください。』」を要求する。
- `src/app/growth/approve/draftQuality.ts` の `DISCLAIMER_MARK = "AIが作成した下書き"` を使い、`draftQuality` は免責文の**欠落を block**(下書き段階では必須)。`publishGate.ts`(`evaluatePublishGate`)も同じ block を投入前に適用する。
- **しかし公開フローには、公開時に本文から注記段落を除去する処理が一切無い**。結果、免責注記が本番記事に残る(監査②の⚠️で実証)。「下書きでは必須・公開では除去」という2状態を、除去側だけ実装していない。

#### 3.1.2 除去純ロジックの仕様 `removeAiDisclaimer(bodyHtml)`

新設: `scripts/growth/aiDisclaimer.ts`(＋ `src/lib/growth/aiDisclaimer.ts` で `export * from "../../../scripts/growth/aiDisclaimer"`)。DOM/IO 非依存の決定的純ロジック。既存 `draftQuality.ts` の `DISCLAIMER_MARK` を**単一ソース**として共有する(重複定義しない。§3.1.3 で export 化)。

```
export function removeAiDisclaimer(bodyHtml: string): { body: string; removed: boolean }
```

- **入力**: 下書き本文 HTML(Notion `下書き本文HTML` ミラー由来。両経路とも既に取得済み — API route は `draftBodyOf(page)`、CLI は `richTextOf(page, "下書き本文HTML")`)。
- **除去対象**: `DISCLAIMER_MARK`(「AIが作成した下書き」)を含む**トップレベルブロック要素1つ**(通常は末尾の `<p>※この記事はAIが作成した下書きです。公開前に内容をご確認ください。</p>`)。判定はマーク文字列の**部分一致**で行い、`draftQuality` の存在判定(`plain.includes(DISCLAIMER_MARK)`)と対称にする。
- **除去範囲の厳密化(過剰除去の防止)**:
  - マーク文字列を含む**最小の外側ブロックタグ**(`<p>…</p>`/`<div>…</div>` 等)を、その開閉タグごと1つだけ除去する。マークがプレーンテキストで裸に書かれている場合は、その行(直近の `<br>` またはブロック境界で区切られた区間)を除去する。
  - **本文中の他段落・見出し・画像・リンクは一切変更しない**(免責段落以外を削らない)。
  - 除去後に残った**末尾の空ブロック・連続空白**は畳む(`<p></p>` や余分な改行を残さない)。
- **戻り値**: `{ body: 除去後HTML, removed: 除去したか }`。`removed=false`(マーク不在)なら `body` は入力と同一を返す(冪等)。
- **冪等性**: 既に除去済み(マーク不在)の本文を渡しても無変更で返す。二重公開・再公開でも安全。
- **複数マッチ**: 万一マークを含むブロックが複数ある場合はすべて除去する(通常は1つ)。

**設計上の注意**:
- LLM を呼ばない決定的ロジック(テスト可能・公開直前の軽量処理)。
- HTML パースは既存の軽量なタグ処理方針に合わせる(`draftQuality.ts` の `stripTags` と同系の正規表現ベース、またはトップレベルブロック分割の純ロジック)。**過剰除去を避けるため、マークを含むブロックだけを対象にする**保守的な実装にする。実装時にトップレベルブロック分割の既存ユーティリティ(`decorate.ts` の `splitTopLevelBlocks` 相当があれば再利用)を確認する。

#### 3.1.3 `DISCLAIMER_MARK` の export 化(単一ソース維持)

`src/app/growth/approve/draftQuality.ts` の `DISCLAIMER_MARK` を **export** し、`aiDisclaimer.ts` はこれを import して使う。除去(公開時)と欠落検出(下書き時)が**同じ定数**を見ることで、片方だけ表記が変わって不整合になる事故を防ぐ。

- 変更前: `const DISCLAIMER_MARK = "AIが作成した下書き";`(モジュール内 private)
- 変更後: `export const DISCLAIMER_MARK = "AIが作成した下書き";`
- `aiDisclaimer.ts`(scripts 側)は `src/app/growth/approve/draftQuality` から `DISCLAIMER_MARK` を import する(`articleEval.ts` が `../../src/app/growth/approve/draftQuality` を import している前例あり=同じ依存方向で問題ない)。

#### 3.1.4 両公開経路の結線点

両経路とも、**公開直前に既に `patchDraft(endpoint, contentId, {...}, contentOpts)` を呼んでタイトルを microCMS 下書きへ最終同期している**(#176)。この既存の `patchDraft` 呼び出しに、除去済み本文を**同じ PATCH で相乗り**させる(公開直前の1回で本文も確定)。microCMS の本文フィールドキーは `bodyHtml`(create 時の payload と同じ)。

**(a) 公開 API route — `src/app/api/growth/publish/route.ts`**

- 現状(L129-133):
  ```
  const title = ideaTitleOf(page).trim();
  if (title) {
    await patchDraft(endpoint, contentId, { title }, contentOpts);
  }
  await publishContent(endpoint, contentId, microOpts);
  ```
- 変更後(方針): 公開前検証(L114 の本文非空チェック)で既に取得している `draftBodyOf(page)` に `removeAiDisclaimer` を適用し、除去した場合のみ `bodyHtml` を PATCH に含める。
  ```
  const rawBody = draftBodyOf(page);
  const { body: cleanBody, removed } = removeAiDisclaimer(rawBody);
  const patch: Record<string, unknown> = {};
  const title = ideaTitleOf(page).trim();
  if (title) patch.title = title;
  if (removed) patch.bodyHtml = cleanBody;
  if (Object.keys(patch).length > 0) {
    await patchDraft(endpoint, contentId, patch, contentOpts);
  }
  await publishContent(endpoint, contentId, microOpts);
  ```
  - `removed=false`(注記が無い/既除去)なら本文 PATCH はしない(不要な書き込みを避け冪等)。
  - title 空・本文無変更の両方なら `patchDraft` 自体を呼ばない(既存の title 空スキップと整合)。
- **Notion ミラー(`下書き本文HTML`)の扱い**: 本 spec では**触らない**。除去は「公開する microCMS 本文」に対してのみ行い、Notion 側ミラーは下書きの記録として注記付きのまま残す(再編集・再公開の余地を残す。過剰なミラー同期は今回のスコープ外)。承認画面の品質チェックが Notion ミラーを読んでいるため、ミラーから注記を消すと下書き段階の block が誤発火するリスクがあり、**ミラーは変更しないのが安全**。

**(b) 予約公開 CLI — `scripts/growth/publish-due-cli.ts`**

- 現状(L154-157):
  ```
  if (title) await patchDraft(ENDPOINT, contentId, { title }, contentOpts);
  await publishContent(ENDPOINT, contentId, managementOpts);
  ```
- 変更後(方針): 直前で既に読んでいる `richTextOf(page, "下書き本文HTML")`(L85 `bodyHtml` 相当を再利用)に `removeAiDisclaimer` を適用し、除去分を `patchDraft` に相乗りさせる。API route と**同じロジック**を通す(`removeAiDisclaimer` は共有純ロジック)。
  ```
  const rawBody = richTextOf(page, "下書き本文HTML");
  const { body: cleanBody, removed } = removeAiDisclaimer(rawBody);
  const patch: Record<string, unknown> = {};
  if (title) patch.title = title;
  if (removed) patch.bodyHtml = cleanBody;
  if (Object.keys(patch).length > 0) await patchDraft(ENDPOINT, contentId, patch, contentOpts);
  await publishContent(ENDPOINT, contentId, managementOpts);
  ```
  - `GROWTH_DRYRUN=1` では従来どおり公開せず対象表示のみ(除去は行うが PATCH しない=挙動を壊さない)。

**両経路の一貫性**: 除去ロジックは `removeAiDisclaimer` の**1箇所に集約**し、route と CLI はそれを呼ぶだけ(重複実装しない)。これにより「片方だけ除去する」不整合を構造的に防ぐ。

#### 3.1.5 既公開1記事の修正手順(運用・仕様に記載)

既に公開済みの記事「市川でピックルボールができる場所と、屋内専用という選び方」には注記が残存している。これは**コードの遡及修正では直さず、人間承認のもと運用で修正**する(公開記事の本文書き換えは取り消しづらい外向き操作のため)。

1. オーナーが対象記事の microCMS 本文を確認し、末尾の注記段落(`※この記事はAIが作成した下書きです。〜`)を特定する。
2. **人間立会いのもと**、microCMS 管理画面または承認画面の手動リッチ編集(`/api/growth/draft/edit`)で注記段落を削除して**再保存**する(手動編集は認可済み経路)。
3. 保存後、公開状態を確認する(microCMS で公開のまま本文が更新されること)。
4. 修正後の記事に注記が無いことを目視確認する。

### 3.2 即対応2: 学習ループの却下理由バグ

#### 3.2.1 バグの正確な把握

#### 3.2.2 記事ネタ案 DB の理由プロパティ(現物確認に基づく設計判断)

現物確認の結果:
- 記事ネタ案 DB には**学習ループ用の「公開後判定」select が既存**(`docs/operations/growth/40-notion-props.md` の「学習ループ(#221)」節: `未判定`/`成功`/`様子見`/`要改稿`)。これは公開後の記事評価に使う。
- 却下/見送り時点の**却下理由を書く専用プロパティは存在しない**。既存の `判定メモ` はマイルストーン用に別ラベルで存在するとの指示だが、記事ネタ案 DB の現行 props 一覧(40-notion-props.md)には却下理由の rich_text は載っていない。

**設計判断**: 記事ネタ案 DB に **`却下理由` rich_text プロパティを新設**する(推奨案を採用)。理由:
- `proposalLines()` が参照する `判断者メモ`(施策提案 DB)と役割対称にでき、`ideaLines()` の対称化が素直になる。
- `公開後判定=要改稿` の行に添える「なぜ改稿が要るか」も同じ `却下理由` に書けば、却下/見送り/要改稿の3系統の理由を1プロパティで統一供給できる。
- マイルストーン用の `判定メモ` に相乗りさせると意味が混線するため、専用プロパティを分ける方が学習ループの信号が濁らない。

| プロパティ | 型 | 用途 |
|---|---|---|
| `却下理由` | rich_text | 記事ネタ案を却下/見送り/要改稿と判断した理由(人が記入)。`ideaLines()` が学習ループの入力として併記する。**未追加でも欠落耐性で動く**(空なら理由なしで従来どおりタイトルのみ)。 |

- **前提条件**: このプロパティ新設は**オーナー(メインセッション)が Notion MCP で実施**する(§6)。コードは欠落耐性(未追加でも `ideaLines()` は理由なしで従来出力・沈黙落ちしない)。

#### 3.2.3 `ideaLines()` の対称化(出力形式)

`proposalLines()` と同じ流儀にする。却下/見送り、および `公開後判定=要改稿` の行に理由を併記する。

- **変更前**(現行):
  ```
  - [<対象週開始> | <status>] <タイトル案>
  ```
- **変更後**(方針・`proposalLines` と対称):
  ```
  - [<対象週開始> | <status>] <タイトル案>
    - 却下理由: <却下理由>            ← status が 却下/見送り のとき
  ```
  さらに `公開後判定=要改稿` の行:
  ```
  - [<対象週開始> | <status>] <タイトル案>
    - 公開後判定: 要改稿 / 却下理由: <却下理由>
  ```
- **併記の条件(決定的ルール)**:
  - `status ∈ {却下, 見送り}` のとき: `却下理由` が非空なら `- 却下理由: <理由>` を1行足す。
  - `公開後判定 == 要改稿` のとき(status が公開済み等でも): `- 公開後判定: 要改稿` を出し、`却下理由` が非空ならスラッシュで理由を続ける。
  - `却下理由` が空・`公開後判定` が要改稿以外なら、従来どおりヘッダ行のみ(欠落耐性)。
- **既存挙動の維持**: `対象週開始`・`status`・`タイトル案` のヘッダ行は現状のまま。理由は**サブ行(2スペースインデント)**で足す(`proposalLines` の `\n  - ...` と同じ整形)。
- `ideaLines()` は `公開後判定` select と `却下理由` rich_text を読むため、`existing.ts` に `selectName`/`richText` ヘルパー(既存)を使う(新規ヘルパーは不要)。

#### 3.2.4 `weekly.md` の変更方針(「避ける学習」の格上げ)

## 5. 品質ゲートの新仕様(数値ゲート)

> 監査① C-2 の中核。§11 ルブリックを「自己採点で終わる」状態から「生成プロセスに接続された数値ゲート」に格上げする。**本 spec ではプロンプト上の合否ルールとして導入**する(§4.2)。スコアの機械記録・集計はセルフチューニングループ(SI1/SI2)へ接続する後続タスク(§5.4)。

### 5.1 採点軸と JSON 形式

編集者エージェントが最終 HTML を出す前に、§11 の中でも**具体性・独自視点・翻訳調/AI 臭**の3軸を0〜5で採点し、**JSON で残す**(編集者の報告に含める)。

```json
{
  "quality_score": {
    "concreteness": 3,        // 具体性: 数値・固有名詞・手順・FAQ が段落単位で入っているか
    "originality": 2,         // 独自視点: §16-1 の記事タイプ別一次情報が入っているか
    "no_ai_smell": 4,         // 翻訳調・AI臭: §14 の5パターンの残存度(残存が多いほど低い)
    "block_reasons": [
      { "axis": "originality", "score": 2, "quote": "<本文の該当箇所を1つ以上引用>", "reason": "一次情報が1つも無く一般論で終わっている" }
    ]
  }
}
```

- **他の §11 軸(検索意図の網羅・構成・読みやすさ・正確性・NG なし・リンク/数値/タイトル)** は既存どおり合否チェック(この3軸だけ数値化して block ゲートにする=監査① C-2 が最重視する軸)。

### 5.2 閾値(block 条件)

次の**いずれか**に該当したら**下書き化を保留(block)**する(監査① C-2 の確定案):

| 条件 | block トリガー |
|---|---|
| ① 具体性 ≤ 2 | 数値・固有名詞・手順・FAQ のいずれも段落単位で入っていない |
| ② 独自視点 ≤ 2 | §16-1 の記事タイプ別一次情報が1つも入っていない |
| ③ 翻訳調・AI 臭 ≤ 2 | §14 の5パターンのうち2つ以上が本文に残存 |

- **減点理由には本文の該当箇所を1つ以上引用**する(`block_reasons[].quote`)。抽象的指摘(「具体性が足りない」だけ)は禁止(監査① C-2)。

### 5.3 差し戻しループ

- block に該当したら **引用付き修正指示 → 執筆担当が修正(最大2周)**(既存の手順2-4 の2周ループに乗せる)。
- 2周しても block が残る場合は**下書き化を保留**し、`block_reasons` を明記して報告する(その記事の `ステータス` は「生成中」のまま=次回再実行で拾い直す=既存の冪等挙動)。
- **編集者の報告に §11 スコア(`quality_score`)を含めることを必須化**する(監査① C-2)。

### 5.4 コード側の機械ゲートとの関係(境界の明示)

- **今回導入するのはプロンプト上の合否ルール**(編集者エージェントが §5 の JSON を出し、閾値で自己 block する)。`draftQuality`/`publishGate`(コードの機械ゲート)は**形式チェック(免責文・断定・壊れリンク)を引き続き担当**し、**数値スコアの機械判定は今回コードに入れない**(具体性・独自視点・AI 臭は決定的正規表現では正しく測れず、LLM 判定=編集者エージェントの領分)。
- スコア JSON の**記録・週次集計**(「独自視点が毎回低い」等の傾向分析)は、セルフチューニングループ設計(`2026-07-05-growth-self-tuning-loop-design.md`)の学習ログ基盤に**後続タスクで接続**する(§8 で引き継ぐ)。本 spec ではスコアを編集者の報告に載せる要件までを定義する。

### 7.2 プロンプト変更の検証方法(次回下書き生成での確認観点)

プロンプト・文体ガイド・few-shot 例の変更はユニットテストで測れない。**次回の下書きモード実行で生成された記事**を、以下の観点で人が確認する(監査②の批評軸を流用)。

|---|---|

| CTA | 予約導線の直前に「持ち物ゼロ」の一押しがあるか。煽っていないか(②) |

## 9. 効果測定(学習ログ・公開後判定との接続)

改善の効果は、セルフチューニングループの学習ログ(SI1)と既存の公開後判定を指標にする。

- **編集イベントの region/headline 傾向(SI1)**: セルフチューニングループの `編集` イベント(手動リッチ編集の前後差分要約)を効果確認に使う。フェーズA が効いていれば、**同じ region(導入・見出し・本文)が毎回直される傾向が減る**はず(例: リードの型を入れたので「導入を短縮/修正」編集が減る、段落リズム反復禁止が効けば「言い換え」編集が減る)。SI1 の学習ログが入った後、weekly のシステム振り返り(SI2)がこの減少を観測する。
- **公開後判定(既存)**: 記事ネタ案の `公開後判定`(未判定/成功/様子見/要改稿)を突き合わせ、**`要改稿` が減り `成功` が増える**方向を確認する。即対応2 で `却下理由`/`公開後判定=要改稿` が weekly に供給されるようになったので、要改稿の理由を一般化して次サイクルの品質に反映する弧が閉じる。
- **数値ゲートのスコア推移(§5)**: 編集者の報告に載る `quality_score`(具体性・独自視点・AI 臭)を、SI1 の学習ログに接続できれば(§5.4・後続タスク)、**スコアの週次推移**を効果指標にできる。本 spec ではスコアを報告に載せる要件までを定義し、機械集計は後続へ送る。
- **再監査(即時)**: 監査②の「本文入り記事1本(68点)」を基準に、フェーズA 後の次回生成記事を同じ批評軸(§7.2)で再監査し、リード・具体性・段落リズム・ヘッジ・CTA・E-E-A-T の各点で改善を確認する。
