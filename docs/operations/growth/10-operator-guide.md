# グロースループ 日常運用ガイド(人間向け)

> このファイルは**人間(オーナー／スタッフ)向けの日常運用手順**。週次サイクルを最初から最後まで(承認→下書き→公開→レビュー)通しで回すための1本。初期構築(自宅PCのタスク登録・環境変数・LINE 承認)は [01-setup-guide.md](01-setup-guide.md)、AI 実行時の内部手順は [growth-weekly-runbook.md](../growth-weekly-runbook.md) を見る。設計の詳細はリンク先に譲り、ここは「**いつ・何を・どう操作すると・何が起きるか**」だけを書く。

このガイドを読めば、設計の中身を知らなくても週次サイクルを回せる。分からなくなったら各節末の「詳細リンク」を開く。

## 0. 登場人物と役割(30秒で全体像)

グロースループは3つの場所で動く。あなたが操作するのは主に**承認画面**と**Notion**だけ。重い処理は全部**自宅PC**が自動で拾う。

| 場所 | 誰が触るか | 何をするか |
|---|---|---|
| **承認画面**(`/growth/approve`) | あなた(ブラウザ) | 記事ネタの承認/却下、修正依頼、画像の再生成依頼、公開 |
| **Notion**(3つの DB) | あなた(手入力欄) | 却下理由・一次情報メモ・公開後判定・実KPI(予約/SNS/口コミ) |
| **自宅PC**(常時稼働) | 触らない(自動) | 週次分析・下書き生成・画像生成・公開・計測を裏で実行 |

> 大原則(pull 型): AI生成や画像作成の依頼は Notion に書き、自宅PCが5〜15分間隔で拾う。公開だけは別で、再認証した人間が即時公開または予約公開の権限を明示的に付与する。だからAI処理を「依頼したのに変わらない」ときは、まず自宅PCが動いているかを疑う(→ [7. トラブルシュート](#7-トラブルシュート))。

### 公開権限の3つの概念

- **AI生成**: 記事案・構成・本文・画像を作る工程。AIの自律判断だけで公開しない。記事案の承認は下書き生成の許可であり、承認直後には公開されない。公開には別途公開操作が必要。
- **即時公開**: 人間が再認証後に公開キューで「今すぐ公開」を選び、公開権限を付与する。公開APIが段階ガードを再検証して決定的に公開する。
- **予約公開**: 人間が再認証後に日時を指定し、将来の公開権限を付与する。非AI workerの `npm run growth:publish-due` は実行開始時に到来予約を取得し、公開直前ゲートを通して決定的に公開・LINE通知する。予約解除が確実に有効なのはworkerの対象取得前までで、実行中は間に合わない場合がある。

## 1. 週次サイクルの通し図解

木曜の朝、自宅PCが自動で週次分析を回すところから1週間が始まる。あなたの操作は「承認」「公開」「レビュー記入」の3か所だけ。

```
┌──────────────────────────────────────────────────────────────────┐
│ 木曜 朝(自動・自宅PC)                                            │
│   growth:weekly が走る                                            │
│   → GA4/GSC を分析 → Notion「週次グロースレポート」に1ページ追加  │
│   → 「記事ネタ案」DB に記事案(提案中)/「施策提案」DB に施策(未処理)│
│   → 完了を LINE 通知(直近7日の失敗件数も表示)                    │
└───────────────────────────────┬──────────────────────────────────┘
                                 │ LINE の通知を見る
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│ あなた:承認画面(/growth/approve)で承認/却下                    │
│   記事ネタ → 承認 = 生成のゴーサイン / 却下 = 却下理由を書く      │
│   (任意)構成案・タイトルに修正依頼、施策提案も承認/却下          │
└───────────────────────────────┬──────────────────────────────────┘
                                 │ 承認した記事は「生成待ち」列へ
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│ 自宅PC:下書きモード(growth:drafts)を実行                       │
│   承認済みネタを拾う → 本文執筆 → 本文画像・アイキャッチ生成      │
│   → microCMS に「下書き」作成(公開はしない)→ 承認画面で確認      │
└───────────────────────────────┬──────────────────────────────────┘
                                 │ 承認画面「下書き」列に並ぶ
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│ あなた:下書きプレビューで確認・仕上げ(任意)                    │
│   直接編集 / アイキャッチ再生成 / 本文画像再生成・差し替え        │
│   / スタイリング・アドバイス / 装飾アシスタント                  │
└───────────────────────────────┬──────────────────────────────────┘
                                 │ OK なら
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│ あなた:公開キューで公開(今すぐ / 予約)                         │
│   「公開OK ◯件を今すぐ公開」or 時刻を選んで予約                   │
│   → 予約は自宅PC(growth:publish-due)が到来時刻に自動公開        │
└───────────────────────────────┬──────────────────────────────────┘
                                 │ 公開後
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│ 自宅PC:計測(growth:metrics)+ レビュー抽出(growth:review-due) │
│   GA4 成績を成績ボードに反映 / 公開28・56・90日で判定メモ候補     │
│ あなた:成績ボードを見る / Notion『公開後判定』を最終決定         │
└──────────────────────────────────────────────────────────────────┘
```

**あなたが必ずやる3つ**: ①承認画面で承認/却下 ②公開キューで公開 ③公開後に `公開後判定` を記入。それ以外(仕上げ・修正依頼)は任意。

## 2. 承認画面の使い方(機能ごと:いつ・どう押すと・何が起きるか)

承認画面(`/growth/approve`)は**パイプライン盤**。記事ネタが `提案中 → 生成待ち → 生成中 → 下書き` と左から右へ流れる。**承認=生成のゴーサイン**。

> 便利操作: キーボード `j/k` で移動・`a` 承認・`r` 却下・`e` 詳細・`/` 検索。⌘K でコマンドパレット。チェックで一括選択→一括承認/却下も可(すべて可視ボタンと二重化されているのでキーボードは必須ではない)。

### 2-1. 記事ネタの承認 / 却下

- **いつ**: 木曜の週次通知が来たあと。「提案中」列の記事カードを見て判断する。
- **承認**: カードで「承認」。記事は「生成待ち」列へ動く。次に自宅PCの下書きモードが走ると「生成中」→「下書き」へ進む。
- **却下**: 「却下」。このとき **Notion「記事ネタ案」DB の `却下理由` に理由を書く**のが重要。
  - **なぜ書くか**: `却下理由` は週次モードの**学習ループの入力**になる。次回以降、オーナーが嫌う方向・効かなかった切り口を AI が繰り返さなくなる。
  - **書き方**: 一言でよいが「何が理由か」を具体的に。例「料金に触れる案は不可(未確定のため)」「地域の指名検索狙いは既に十分」「トーンが安っぽい」。空欄だと学習に効かない。

### 2-2. 構成案・タイトルへの修正依頼(#40 / #139B)

生成前の記事ネタの**構成案(見出しアウトライン)**やタイトルを AI に直させたいとき。

- **いつ**: 承認する前、構成案が気に入らないとき。
- **どう**: 記事詳細パネルで、構成案の各行にコメント、または「タイトルについて(AIに修正を依頼)」枠に指示を書いて「修正を依頼」。**構成案だけ・タイトルだけ・両方**どれでもよい。
- **何が起きるか**: 自宅PCの修正ループ(`growth:revise-loop`)が5分間隔で拾い、指示が来た方だけを直して「提示中」にする。あなたは承認画面で**元 vs 新**を見比べて「反映」か「やり直し(再コメント)」。通常運用では LINE は鳴らない。
- **注意**: 修正中(依頼中/処理中/提示中)の記事は**承認/却下が一時的に無効**(古い構成案での誤承認を防ぐ)。反映かやり直しで解除される。

### 2-3. アイキャッチの再生成 / 差し替え(#144 / #143)

下書きができたあと、記事トップの大きな画像(アイキャッチ)を作り直す・入れ替える。

- **再生成(AI)**: 下書きプレビューで「AIで再生成」→ 指示(任意)→「再生成を依頼」。自宅PCの画像ループ(`growth:regen-loop`)が新しいアイキャッチを作り直し、下書きに差し替える。通常運用では LINE は鳴らないため、承認画面を再読み込みして確認する。
- **差し替え(手動)**: メディアから選ぶ/アップロードして入れ替える(AI を使わず即時)。
- **前提**: 下書きが未作成(`下書きID` なし)の記事は依頼できない。

### 2-4. 本文画像の再生成 / 差し替え / 挿入(#156 / #145)

本文中の画像を1枚単位で扱う。

- **どう**: 下書きプレビューの本文画像一覧で、各画像の「AIで再生成」→ 指示(任意・例「もっと明るく」「図解で」)→「再生成を依頼」。差し替え(手動)・新規挿入も同じ場所から。
- **何が起きるか**: 自宅PCの本文画像ループ(`growth:regen-body-loop`)が**その1枚だけ**作り直し、本文の当該画像を差し替える。通常運用では LINE は鳴らないため、承認画面を再読み込みして確認する。
- **注意**: 依頼後に本文を編集して対象の画像が消えると、差し替え先が見つからず失敗としてログに残る(沈黙させない)。本文編集と画像再生成は同時に走らせない。

### 2-5. スタイリング・アドバイス(#146)

下書きの文章を、文体ガイドに照らして**具体的に助言**してもらう(○×ではなく理由と改善案)。

- **どう**: 下書きプレビューの「スタイリング・アドバイス」カード → 見てほしい点(任意)→「アドバイスを依頼」。
- **何が起きるか**: 自宅PCのアドバイスループ(`growth:advise-loop`)が本文を分析し、総評+強み+直すべき点(引用+理由+修正案)を返して表示。**主観的な点数は付けず、本文も自動で書き換わらない**(read-only)。直したければ下の編集・修正導線で自分で反映。「閉じる」でクリア。

### 2-6. 装飾アシスタント / アドバイス反映 / 本文コメント→AI修正(#147 / #165 / #182)

本文に手を入れて仕上げる系。

- **装飾アシスタント(#147)**: 「装飾を提案」→ 自宅PC(`growth:decorate-loop`)が箇所ごとに装飾提案(足す/直す/消す)を返す。あなたが提案ごとに **採用/却下**(before/after 付き)→「採用分を反映」で採用したものだけ本文へ入る。
- **アドバイス反映(#165)**: 2-5 のアドバイスで示された修正案を、承認画面から本文へ反映する(自宅PC `growth:advise-apply-loop` が反映案を作り、反映は承認画面側)。
- **本文コメント→AI修正(#182)**: 本文にインラインでコメントを付けると、自宅PC(`growth:comment-revise-loop`)がコメントされた文を含むブロックだけを直す案を作り、承認画面で反映。
- **共通**: いずれも安全のため AI は「どこを・どう」だけを返し、生の HTML は出さない(システム側が決定的に生成)。

### 2-7. 公開予約 / 一括公開(#H24 / #H23)

記事タブ上部の折りたたみ「公開キュー」から。詳細は [5. 計測ループと公開キュー](#5-計測ループと公開キュー)。

- **一括公開**: 「公開OK ◯件を今すぐ公開」で、公開できる記事(green)をまとめて公開。
- **予約公開**: 時刻を選んで「この時刻に予約」。**この時点では公開されない**が、将来の公開権限は付与される。到来時刻に自宅PCの非AI worker(`growth:publish-due`)が対象を取得し、公開直前ゲートを通して公開。解除はworkerが対象を取得する前まで有効で、実行中は間に合わない場合がある。

> 承認画面の各機能が使う Notion プロパティの正確な定義は [40-notion-props.md](40-notion-props.md)。各ループの内部仕様は [30-loops.md](30-loops.md)。

## 3. 自宅PC側の AI ループの回し方

初期構築で、これらは自動起動されるよう設定済みのはず(→ [01-setup-guide.md](01-setup-guide.md) 手順8)。**推奨は常駐デーモン `npm run growth:daemon` を起動しておくだけ**で、下記のプル型ループ＋公開キュー＋滞留検知＋日次計測＋週次レビューをまとめて自動巡回する(依頼は押してから最大1〜2分で拾われる)。ここでは「どの依頼がどのコマンドで処理されるか」「手で動かすとき何に注意するか」を運用者目線で示す。

### 3-1. 依頼種別 → コマンド 対応表(package.json で実在確認済み)

`npm run <コマンド>` で起動する。承認画面から依頼した内容を、対応する自宅PCのループが拾う。

| 依頼種別(承認画面で何をしたか) | コマンド | AI課金 |
|---|---|---|
| 記事下書きの生成(承認済みネタを記事化) | `growth:drafts` / `growth:drafts-auto` | サブスク(追加課金なし) |
| 施策の成果物化(承認済み施策を文案/仕様化) | `growth:initiatives` / `growth:initiatives-auto` | サブスク(追加課金なし) |
| アイキャッチ AI 再生成(#144) | `growth:regen-loop` | サブスク+**画像生成(OpenAI)課金あり** |
| 本文画像 AI 再生成/挿入(#156) | `growth:regen-body-loop` | サブスク+**画像生成(OpenAI)課金あり** |
| スタイリング・アドバイス(#146・read-only) | `growth:advise-loop` | サブスク(追加課金なし) |
| アドバイス採用→本文反映(#165) | `growth:advise-apply-loop` | サブスク(追加課金なし) |
| 本文コメント→AI修正(#182) | `growth:comment-revise-loop` | サブスク(追加課金なし) |
| 構成案/タイトルの修正(#40 / #139B) | `growth:revise-loop` | サブスク(追加課金なし) |
| 装飾提案(#147) | `growth:decorate-loop` | サブスク(追加課金なし) |
| 週次分析→レポート+提案(自動・木曜) | `growth:weekly` | サブスク(追加課金なし) |

> 「サブスク」= 既定の Claude 運用では自宅PCの `claude` サブスクリプションで推論するため API 追加課金なし。Codex 併用時は Codex 側の利用条件に従う。「画像生成課金あり」= アイキャッチ/本文画像は OpenAI 画像生成 API を使うため、再生成のたびに実費がかかる(むやみに連打しない)。

### 3-2. 5分間隔・1日上限・lock 共有の運用

共有 lock は PID 文字列ではなく JSON lease で、手動下書きも対象。ローカル PID が生存中でも heartbeat が15分止まれば回収し、旧ジョブは子孫を含む単一プロセスグループごと停止する。timeout 通知（P1 critical）は `GROWTH_NOTIFY_LEVEL=weekly-only` でも送信され、記載された再開コマンドを使う。

修正・画像再生成・アドバイス・装飾の**プル型ループ7種**(`revise` / `regen` / `regen-body` / `advise` / `decorate` / `apply` / `comment-revise`)は、次の共通ルールで動く。下書き自動生成を有効にした場合の `drafts-auto`、施策自動成果物化を有効にした場合の `initiatives-auto` も、同じ lock/上限で逐次処理される:

- **5分間隔**で起動する(タスクスケジューラの「繰り返し間隔=5分・継続時間=無期限」で登録)。依頼を書いてから最大5分で拾われる。
- **同時に1つだけ**動く(lock 共有)。7ループは1つのロックファイルを共有するので、複数の依頼が来ても順番に処理され二重起動しない。すでに実行中なら「既に実行中のためスキップ」して次の起動を待つ。
- **1日の実行上限**は既定50回(`GROWTH_REVISE_DAILY_CAP` で変更可)。これは headless agent を起動して実際に依頼を処理した回数の上限で、依頼なしの空振りポーリングは数えない。上限に達すると「本日の実行上限に達したためスキップ」する。
- 自動 pull は weekly のみ。各ループやデーモンにコード更新を反映したい場合は、自宅PCで手動 `git pull --ff-only` するか、デーモンを再起動する。
- 下書き自動生成は未設定でも有効。既定5分間隔で「承認済み/生成中 かつ 下書きID未作成」を `peek` し、対象がある時だけ `growth:drafts` 相当を起動する。止める場合だけ `GROWTH_DRAFTS_AUTO=0`。
- 施策自動成果物化も未設定で有効。既定5分間隔で「承認済み」の施策を `peek` し、対象がある時だけ `growth:initiatives` 相当を起動する。止める場合だけ `GROWTH_INITIATIVES_AUTO=0`。

> ループの内部仕様・純ロジックの所在は [30-loops.md](30-loops.md)。タスク登録の具体手順は [01-setup-guide.md](01-setup-guide.md) 手順8。

### 3-3. 純データ結線(AI を使わないコマンド)

以下は headless agent を使わず、GA4/microCMS/Notion をつなぐだけ。通常は `growth:daemon` が記載間隔で自動実行するため、個別のWindowsタスク登録は不要。調査・再実行時だけ手動で呼ぶ。

| コマンド | 何をするか | 実行頻度の目安 |
|---|---|---|
| `growth:metrics` | GA4 成績を成績ボードに反映(計測ループ #C4) | デーモンが24時間ごと |
| `growth:publish-due` | 予約公開の到来分を公開(#H24) | 5〜15分間隔 |
| `growth:review-due` | 公開28/56/90日の記事の判定メモ候補を作る | デーモンが7日ごと |
| `growth:proposal-review-due` | 施策の検証予定日到来分を拾う | デーモンが7日ごと |
| `growth:stall-check` | 生成待ち/生成中の滞留・wedge を検知して通知 | 15分間隔 |

いずれも `GROWTH_DRYRUN=1` を付けると Notion に書かず対象だけ表示できる(動作確認用)。

## 4. Notion の人手入力欄の使い方

AI と自動計測では埋められない情報は、あなたが Notion に手で書く。**各欄の正確な型・定義は [40-notion-props.md](40-notion-props.md) が正典**。ここは「運用者が何を書くか」だけ。

### 4-1. 「記事ネタ案」DB(記事にまつわる手入力)

| 欄 | いつ書くか | 何を書くか |
|---|---|---|
| `却下理由` | 記事ネタを却下/見送り/要改稿にしたとき | 却下の理由を具体的に(→ 学習ループの入力・[2-1](#2-1-記事ネタの承認--却下)) |
| `一次情報メモ` | その記事に使える現場の一次情報があるとき | スタッフが見聞きした施設の実際(初回の人がつまずく所・当日の空気・実施済みイベントの事後ルポ 等)。**執筆 AI はここに書かれた記述だけを体験談として使う**。未記入なら AI は体験談を書かず確定事実で代替 |
| `公開後判定` | 公開後、判定メモ候補が出たとき | 記事の最終評価を人が決める:`成功` / `様子見` / `要改稿`(未判定のまま放置しない)。AI(review-due)は候補メモを書くだけで、この最終判定は上書きしない |

### 4-2. 「週次グロースレポート」DB(オーナー手入力の実KPI)

GA4/GSC では見えない**実 KPI** を、オーナーが週次で数分入力する。週次モードがこれを分析の分母に取り込む。

| 欄 | 入力元(どこを見て入れるか) |
|---|---|
| `予約件数` | 予約サービス(RESERVA / labola)の当週予約数 |
| `LINE友だち数` | LINE 公式アカウント管理画面の友だち数 |
| `IGフォロワー数` | Instagram プロフィールのフォロワー数 |
| `口コミ件数` | Google ビジネスプロフィールのクチコミ総数 |
| `口コミ平均評価` | 同 平均評価(例 4.6) |

- **入力タイミング**: 木曜の週次実行の**前**に。対象週の行が無ければ、`対象週開始`=当週(対象週の開始日)にした行を新規作成し、数字だけ入れる(`レポート` 本文は空でよい=週次モードが後で本文を作る)。
- **重要な注意**: `対象週開始` を当週に正しく合わせること。日付がズレていると週次分析に載らず、**エラーも出ずに黙って未反映**になる。
- すべて任意。一部だけ・全部未入力でも週次は壊れない(入力済みの指標だけ使う)。手順の詳細は [60-kpi-tree.md](60-kpi-tree.md) §7。

### 4-3. 「施策提案」DB(記事以外の施策の仮説と検証)

記事以外の施策(MEO・サイト表示内容・サイトデザイン・追加機能・イベント)は「施策提案」DB で扱う。

| 欄 | 誰が書くか | 何を書くか |
|---|---|---|
| `仮説` | 週次モードが自動 | この施策で何がどう良くなるか+根拠 |
| `成功指標` | 週次モードが自動 | 効いたと判断する基準と測る面(GA4/GSC/GBP/予約 等) |
| `検証予定日` | 週次モードが自動 | 成功指標を突き合わせる予定日(`growth:proposal-review-due` がこの日で到来判定) |
| `検証メモ` | **自動**(施策版 review-due が書く) | 検証予定日が来たときの判定メモ候補。人の判断の足場。手で埋めなくてよい |
| `検証結果` | **あなたが最終決定** | `効果あり` / `効果なし` / `不明` / `未検証`。人が下す最終判定。次回週次の「避ける学習」の入力になる |

> `検証メモ`(自動)と `検証結果`(人の最終判定)は別欄。AI は `検証メモ` に候補を書くだけで `検証結果` は触らない。各欄の型は [40-notion-props.md](40-notion-props.md)。

## 5. 計測ループと公開キュー

### 5-1. 公開キュー(#H23 一括公開 / #H24 予約公開)

記事タブ上部の折りたたみ「公開キュー」で、下書き済み記事を扱う。

- **例外管理型**: キューが下書きを「公開OK(green)」と「要対応(例外・理由付き)」に自動で振り分ける。公開できない理由(アイキャッチ未設定 / 本文が空)が出た記事だけ個別に直せばよい。
- **一括公開**: 「公開OK ◯件を今すぐ公開」で green をまとめて公開(冪等)。
- **予約公開**: 時刻を選んで「この時刻に予約」→ 各 green 記事に予約時刻が入り、将来の公開権限が付与される。「解除」が確実に有効なのはworkerの対象取得前までで、実行中は間に合わない場合がある。実際の公開は自宅PCの非AI worker `growth:publish-due` が取得済み対象を公開直前ゲートで検証して公開し、成功時にLINE通知する。
- **安全**: 予約後に公開できない状態(アイキャッチ/本文欠落)になった記事は、`publish-due` が公開せずスキップする。生成中/公開済みは二重公開ガードで弾かれる。

### 5-2. 計測ループ(#C4 成績ボード)

公開記事が実際どれだけ読まれたかを、承認画面「記事」タブ上部の「**成績ボード**」で見る。

- 自宅PCの `growth:metrics`(1日1回)が GA4 から表示数・ユーザー数・前週比を取り、Notion にミラーする。成績ボードの表示経路はそのミラーを読み取るだけ。
- 計測データが無いうちは「まだ計測データがありません」と出る(実行後に反映)。
- 記事別ランキング(表示数降順+前週比)が見えるので、どの記事が伸びているかが分かる。
- `0` は実測0流入、`GA4パス不一致` は行なしを明示的0で保存した状態（28日後は改稿判定対象）、`GA4取得失敗` と `—` は取得不能で集計・改稿判定の対象外。後者は0流入と読み違えず、OAuth/GA4を確認する。

> 実装の詳細・KPI との対応は [50-publish-metrics.md](50-publish-metrics.md) と [60-kpi-tree.md](60-kpi-tree.md)。

### 5-3. 公開後レビュー(review-due)

- 自宅PCの `growth:review-due`(週1回)が、公開**28/56/90日**が来た記事を拾い、成績データから `判定メモ` 候補を書く。通常運用では LINE は鳴らないため、承認画面/Notion で確認する。
- あなたは承認画面/Notion で `判定メモ` を見て `公開後判定`(成功/様子見/要改稿)を最終決定する([4-1](#4-1-記事ネタ案db記事にまつわる手入力))。要改稿なら構成案修正ループや再下書きへ。

## 6. 学習ログ(セルフチューニング)

自宅PCが、手動編集・アドバイス採用・画像試行・工程失敗を「学習ログ」DB に**自動で追記**する(あなたの操作は不要)。週次モードがこれを読んで自己改善に使う。

- あなたが特に何かする必要はない。**追記専用の台帳**で、既存行の更新・削除はしない。
- 「学習ログ」DB が未設定(`GROWTH_LEARNING_LOG_DS` 未設定)なら、この記録は静かにスキップされ運用は壊れない。
- 詳細は [70-self-tuning.md](70-self-tuning.md)。

## 7. トラブルシュート

グロースループは**失敗を沈黙させない**設計。通常ループのハード失敗は `data/growth-failures.log` に構造化追記され、次の週次 LINE に「今週の失敗 ◯件」と出る。通常の直接通知は週次モード自身の失敗に絞るが、例外として `publish-due` の成功通知・失敗通知と、#283 の timeout critical通知も LINE に直接届く。落ち着いて次を確認する。

### 7-1. 週次の失敗通知/失敗サマリを見たら

週次失敗通知にはログの場所が、週次サマリには直近7日の失敗件数が書かれている。基本の対処:

1. 自宅PCで `data/growth-failures.log` と該当タスクの `data\*.log` を開き、**source** と **resume** を見る(例 `source=revise` / `source=pull` / `source=weekly`)。
2. `resume=` のコマンドを自宅PCで実行する(例 `npm run growth:revise-loop`)。設計上、**冪等に再開**できる(途中まで進んだ処理は重複せず、続きから安全にやり直せる)。
3. 直らなければ、同じ行の `exit=` と `detail=`、該当タスクログの末尾を確認する。

### 7-2. 「依頼したのに変わらない」

pull 型なので、依頼は自宅PCが拾って初めて処理される。次の順で疑う:

1. **自宅PCが起動しているか**(スリープ・シャットダウンで拾われない)。
2. **タスクスケジューラのループが動いているか**。プル型ループは5分間隔なので、最大5分は待つ。
3. それでも来ないときは、対応するコマンドを手で1回実行してログを見る。

### 7-3. 滞留検知(stall-check)

- 自宅PCの `growth:stall-check`(15分間隔)が、生成待ち/生成中のまま15分以上止まっている記事や、依頼が拾われず詰まった(wedge)ループを検知してログに残す。LINE は `GROWTH_NOTIFY_LEVEL=all` の検証時だけ送る。
- 「生成中のまま進まない」記事は、次回 `growth:drafts` が冪等に拾い直す。手で `npm run growth:drafts` を実行してもよい。
- 動作確認: `GROWTH_DRYRUN=1 npm run growth:stall-check`(送信せず対象だけ表示)。

### 7-4. 動作確認したいだけのとき

いずれのコマンドも `GROWTH_DRYRUN=1` を付ければ、実際の書き込み・生成・送信をせず「何が起きるか」だけ確認できる。まず dry-run で試すのが安全。

## 8. 絶対にやってはいけないこと(全モード共通)

詳細は [00-canon.md](00-canon.md)。運用者として最低限これだけは守る:

- **本番を勝手に公開しない**。AI は下書きまで。公開は人間が公開キューで行う。
- **git push / commit を AI にさせない**(自宅PCのランチャーが明示的に拒否している)。手でも承認済みの手順以外は push しない。
- **未確定情報(料金・正確な所要分・未確定の日時)を断定しない**。記事に混ざっていたら「最新情報をご確認ください」に直す。営業時間 6:00-23:00・コート3面・デコターフは公表済みの確定事実なので断定してよい。
- **失敗を沈黙させない**。通常ループの失敗は `data/growth-failures.log` とタスクログに残し、週次 LINE の失敗サマリを見たら source/resume で対処する。

## 予約CSVの運用（#280）

ラボーラ管理画面から全期間CSVを `GROWTH_LABOLA_DROP_DIR` へ置き、週次計測前に `npm run growth:ingest` を実行する。取り込みはPIIを除去した正準データセットと収録範囲を `GROWTH_RESERVATION_DATA_DIR/canonical/` に生成し、`growth:metrics` がここを読む。current/priorの片方でも収録範囲外なら0件ではなく未取得になる。7日超のデータは古いと表示されるため件数は参考値に留め、予約意図を代理指標として扱う。CSVを用意できない週は既存の「予約件数」手入力をfallbackにし、推測帰属はしない。
