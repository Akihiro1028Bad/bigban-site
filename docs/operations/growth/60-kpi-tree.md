# KPIツリー定義(北極星→記事KPI)と週次レポート経営サマリ

> 「記事投資が予約を生んだか」に答えるための KPI ツリー。共通原則・絶対禁止は [00-canon.md](00-canon.md)、計測ループの実装は [50-publish-metrics.md](50-publish-metrics.md)、Notion プロパティは [40-notion-props.md](40-notion-props.md)。
> 設計の出典: 設計書 `docs/superpowers/specs/2026-07-03-growth-loop-tobe-redesign.md` P2⑧(経営レビュー §3.5「KPIツリー未定義=最大の穴」への回答)。
> **前提**: 実予約は予約CSV（または同週手入力）、予約意図はGA4の `reservation_click + reserve_entry_click`、SNSはLINE/Instagram、その他CTAは別指標として扱う。GA4側のkey event設定はrunbook「GA4 keyEvents 設定手順」を参照。

## 1. 北極星KPI(事業ゴール)

来店ビジネスの最終ゴールは**実予約・来店**。クリックは予約そのものではなく先行指標として分離する。

| 北極星(主) | 補助(先行指標) |
|---|---|
| **月間実予約数** | 予約意図 / LINEクリック / Instagramクリック / その他CTA / 「本八幡・市川 ピックルボール」等の**指名・ローカル検索インプレッション** |

- 主KPI=予約サービスCSVまたは同週手入力の**実予約数**。記事帰属がある場合は記事別、無い場合は施設全体として扱い、推測帰属しない。
- CSVが古い、欠損、current/priorの収録範囲不足なら実予約を判断に使わず、予約意図を代理指標と明記する。
- 予約意図・SNS・その他CTA・指名/ローカル検索は**予約より手前**の先行指標であり、互いに合算して実予約へ変換しない。

## 2. ツリー分解(北極星 ← 中間KPI ← 記事KPI)

上の階層は下の階層の**積み上げ**。下から順に、各階層の**データ源**と**見る場所**を明記する。

```
北極星: 月間実予約数（記事帰属あり／施設全体）
  ├─ 予約完了(GA4・捕捉率付き): labola_reserve_complete(+_program)（真値=CSVの参考。記事帰属の実測）
  ├─ 予約意図KPI: reservation_click + reserve_entry_click（実予約未取得時の代理）
  ├─ SNS・その他CTA: LINE / Instagram / その他CTA（別成果）
  └─ 流入系中間KPI: 記事セッション / 検索順位 / 検索CTR
       └─ 記事KPI: 記事タイプ別の成功指標(Notion『成功指標』=記事ごとの仮説)
```

| 階層 | KPI | データ源 | 見る場所 |
|---|---|---|---|
| **北極星** | 月間実予約数（記事帰属／施設全体） | 予約サービスCSVまたは同週手入力 | 週次レポート経営サマリ(§4) / PerformanceBoard |
| **予約完了(GA4)** | `labola_reserve_complete + labola_reserve_complete_program`（記事帰属は landingPage）。真値はあくまでCSV実予約で、GA4完了は捕捉率(=GA4完了÷セルフ予約)付きの参考値 | GA4 `metrics.ts` の `reserveComplete`(P3b) / スナップショット `funnel.capture` | 経営ボード「予約ファネル」(記事別はNotionミラーJSONに保存のみ。PerformanceBoard表示は未実装) |
| **予約意図** | `reservation_click + reserve_entry_click`（予約完了とは別バケット。合算しない） | GA4 `ctaEvents.reservationClick/reserveEntryClick` | PerformanceBoard「予約意図」/ 週次レポート |
| **SNS・その他CTA** | LINE / Instagram / その他CTA（相互に合算しない） | GA4 `ctaEvents.lineClick/instagramClick/other` | PerformanceBoard「SNS」「その他CTA」/ 週次レポート |
| **流入系中間** | 記事セッション(views)/ 平均掲載順位(position)/ 検索CTR | GA4 `topPages`(views)/ GSC(clicks・impressions・ctr・position。`metrics.ts` の `search`) | PerformanceBoard / 週次レポート先頭の数字 |
| **記事KPI** | 記事タイプ別の成功指標(記事ごとの仮説) | Notion `成功指標`(週次で記入=S4/S5)＋ 上記の実測 | 承認画面「記事の仮説」カード / `growth:review-due` の判定メモ |

- 実装の突き合わせは [50-publish-metrics.md](50-publish-metrics.md)「計測ループ #C4」を正典とする(`metrics.ts` が GA4/GSC を記事の `articlePagePath` に紐付けて Notion `成績データ` へ書き、PerformanceBoard が描画)。
- `GROWTH_GA4_KEYEVENTS_SINCE=YYYY-MM-DD` とレポート期間を比較する。期間全体が設定日以降なら完全計測、期間が設定日をまたげば部分計測、期間前・未設定・GA4取得失敗は未計測とし、0件と断定しない。記事公開日はこの判定に使わない。
- 旧 `keyEvents` / `keyEventsMeasured` は既存Notion JSONを読むためだけの後方互換。分類不能なので予約意図・SNS・その他CTAのいずれにも変換しない。

### 記事タイプ→中間KPIの対応(どの型が何を狙うか)

`記事タイプ`(獲得/不安解消/資産/比較/イベント。#C4・[40-notion-props.md](40-notion-props.md))ごとに、主に効かせたい中間KPIが違う。読者向けカテゴリ(category)との対応は `scripts/growth/columnCategory.ts` の `ARTICLE_TYPE_TO_CATEGORY` を正典とするマッピング(再掲: 獲得→`start`/不安解消→`start`/資産→`rules`(or `improve`/`health`)/比較→`compare`/イベント→`event`)に従う(#222)。

| 記事タイプ | 主に効かせる中間KPI | 狙い |
|---|---|---|
| **獲得** | freshな実予約、次いで予約意図 | 来店/予約に直結。記事帰属実予約を最優先 |
| **不安解消** | 予約意図率 | 始める前の不安を消し、背中を押す |
| **資産** | 指名/ローカル検索インプレッション・掲載順位(流入系) | 検索で長く読まれる土台。順位とセッションが主役 |
| **比較** | 記事セッション・掲載順位(流入系) | 他競技/他手段からの検討流入 |
| **イベント** | 記事セッション・実予約・予約意図(時期依存) | 時期ものの瞬発。事後ルポは資産化も狙う |

## 3. 記事タイプ別の既定成功ライン(初期仮置き・四半期で見直し)

記事ごとの `成功指標`(Notion・仮説)は週次で個別に書く(例「『本八幡 ピックルボール』10位以内＋freshな記事帰属実予約1件。帰属不能時は予約意図5件/月を代理指標」)。ここでは**型ごとの既定の目安**を置く。**開業直後で母数が小さく、断定できる基準値はまだ無い**。下表は**初期仮置き**であり、公開データが溜まった四半期ごとに見直す。

| 記事タイプ | 既定の成功ライン(仮置き・28日) | 根拠・見直し方針 |
|---|---|---|
| **獲得** | freshな記事帰属実予約が1件以上。帰属なし／未取得時だけ予約意図1件以上を代理ラインにする | 実予約を優先し、代理指標採用時は必ず注記。母数蓄積後に見直す |
| **不安解消** | 記事セッションが付き、予約意図率が0でないこと | 「読まれるが予約意図弱い」(views≥50・計測済み・予約意図=0)を避ける |
| **資産** | 狙うクエリで掲載順位が改善傾向(1ページ目手前=5〜15位に入る)＋セッションの継続 | `metricsReview` の「順位あと少し」(position 5〜15)を「あと一歩」の目安に。順位1ページ目定着を四半期目標に |
| **比較** | 記事セッションが付き、狙うクエリで表示されていること | 検討層は指名より一般クエリ。impressions の立ち上がりを見る |
| **イベント** | 公開直後の瞬間セッション＋(事後ルポなら)資産としての継続表示 | 時期依存のため単発の到達で可。ルポは資産型の基準を併用 |

- しきい値の出所(実装の判定ロジック): `metricsReview.ts`(CTR弱い=impressions≥100 かつ CTR<3% / 順位あと少し=position 5〜15 / 読まれるが予約意図弱い=views≥50・予約意図計測済み・`reservation_click + reserve_entry_click=0` / 予約意図未計測=views≥50かつイベント別未計測 / 要改稿=公開28日でviews<50かつclicks<10)。
- **公開後判定は人が最終決定**する(`成功`/`様子見`/`要改稿`)。CLI(`growth:review-due`)は上記から判定メモの**候補**を作るだけで上書きしない([50-publish-metrics.md](50-publish-metrics.md))。

## 4. 週次レポートの経営サマリ仕様(実装は別途・#221/P2⑧後段)

週次レポート([growth-weekly-runbook.md](../growth-weekly-runbook.md) §5)本文は現状「①サマリー ②優先上位5〜8 ③論点 ④データ注意」。経営者が**30秒で「続ける/縮小/方向転換」を判断できる**よう、本文の**先頭に経営サマリ5行**を置く。

**経営サマリ(先頭に置く5行)**:

1. **今週公開本数**(今週 microCMS で公開した記事数。累計も併記)
2. **セッション**(今週の記事セッション合計＋前週比。流入系の全体感)
3. **実予約と予約意図**(freshな実予約を主表示。欠損・古い・収録不足時は予約意図を代理指標と明記)
4. **SNS・その他CTA／記事タイプ別の判定**(LINE・Instagram・その他CTAを分離し、型別の成功率・判定済み母数・未判定率・観測条件を併記。判定済み3本未満は探索中)
5. **次週の一手**(例「記事帰属実予約が出た獲得型を厚く」「予約意図未計測を解消」「予約意図0の導線を見直す」)

- 数字は `summarizeMetrics` と記事タイプ別成果集計を使い、weekly プロンプト(`scripts/growth/prompts/weekly.md`)も同じ「実予約→予約意図→SNS/その他CTA」の定義に従う。記事タイプは成功本数・成功率・公開本数で自動順位付けせず、率・母数・未判定率と公開後日数/計測期間/views/impressionsの観測条件をセットで読む。条件が揃わなければ直接比較しない。
- 3行目は実予約の状態を必ず併記する。実予約を使えない場合だけ予約意図を代理表示し、未計測なら設定を促す。

## 5. 用語・値の整合(#221 学習ループと一致させる)

学習ループ(#221・P2⑨)が使う軸と、本 KPIツリーの軸を**完全に一致**させる(表記ゆれで集計が割れないため)。

- **記事タイプ**(5値・そのまま日本語): `獲得` / `不安解消` / `資産` / `比較` / `イベント`(`prompts/weekly.md`・下書きオーケストレーター・[40-notion-props.md](40-notion-props.md) と同一)。
- **公開後判定**(人が最終決定・3値): `成功` / `様子見` / `要改稿`。
- **判定ラベル**(`metricsReview.ts` の `reviewLabels`・打ち手の示唆): `伸びている` / `CTR弱い` / `順位あと少し` / `読まれるが予約意図弱い` / `予約意図未計測` / `要改稿` / `未計測`。
- 記事タイプ→category マッピング(獲得→`start`/不安解消→`start`/資産→`rules`(or `improve`/`health`)/比較→`compare`/イベント→`event`)は `scripts/growth/columnCategory.ts` の `ARTICLE_TYPE_TO_CATEGORY` を**単一の真実源**とする(#222。解決コマンドは `npm run growth:column-category`。category=読者向け・articleType=内部計測の別軸共存)。

## 6. 実装・運用上の補足

以下も§1〜§5と同じイベント定義を使う:

- **weekly.md の経営サマリ**: §4 の5行を週次レポート本文の先頭に出し、実予約が使えない場合だけ予約意図を代理指標と注記する。
- **Notion プロパティ**: 記事タイプ別の勝敗集計には公開済み記事の `公開後判定`(既存)＋`記事タイプ`(既存)で足りる見込み。北極星の月次追跡用に「月間予約数」等の月次サマリを置く DB/プロパティを新設するかは要検討([40-notion-props.md](40-notion-props.md) に追記候補)。
- **指名検索トレンド**: GSC の指名/ローカルクエリ(「本八幡 ピックルボール」等)を週次で束ねる集計は現状 `metrics.ts` の記事単位取得に含まれない。北極星の先行指標として別途集計する余地(設計書 P2⑧ 受け入れ基準「指名検索の週次トレンドが集計される」)。
- **イベント別計測設定(オーナー作業・前提)**: runbook「GA4 keyEvents 設定手順」を完了させ、予約意図・SNS・その他CTAをeventName別に取得する。設定前は予約意図未計測として扱う。

## 7. オーナー週次手入力(実 KPI 接地・改善案#4)

GA4/GSC だけでは見えない**実 KPI**(実予約・SNS・口コミ)を、オーナーが週次で「週次グロースレポート」DB の任意 number プロパティに手入力する。週次モードは `growth:existing` 出力の「オーナー手入力」節でこれを読み、分析・成功指標の分母に接地させる(未入力なら「手入力データなし」で従来動作=推測しない)。

| プロパティ | 型 | 入力元(オーナーが週次で確認する場所) |
|---|---|---|
| `予約件数` | number | 予約サービス(RESERVA/labola)の当週予約数 |
| `LINE友だち数` | number | LINE 公式アカウント管理画面の友だち数 |
| `IGフォロワー数` | number | Instagram プロフィールのフォロワー数 |
| `口コミ件数` | number | Google ビジネスプロフィールのクチコミ総数 |
| `口コミ平均評価` | number | 同 平均評価(例 4.6) |

**入力手順(オーナー・週次数分)**: 木曜の週次実行**前**に、対象週の「週次グロースレポート」DB 行(まだ無ければ `対象週開始` を当週にした行を新規作成し、数字だけ入れる)へ上記の数値を入れる。**レポート本文(`レポート` title)は空のままでよい**——本文が空の行は「レポート作成済み」に数えないので、週次モードは通常どおりレポートを新規作成し、その際この手入力を分析に取り込む。

- **手入力行は必ず `対象週開始`=当週(対象週の開始日)にする**。`growth:existing` は `対象週開始` の一致でしか行を拾わないため、日付がズレている・空だと**当週分析に載らず黙って未反映**になる(エラーは出ない)。
- **すべて任意・欠落耐性**: 一部だけ・全部未入力でも週次は壊れない(入力済みの指標だけ使う)。
- Notion プロパティ定義は [40-notion-props.md](40-notion-props.md) の「週次グロースレポート DB」節も参照。

## 8. 実予約とCTAイベントの分離（#280）

- 北極星は予約サービスCSVまたは同週手入力の**実予約**。GA4 `keyEvents` 合計を月間予約数とみなさない。
- 予約意図は `reservation_click + reserve_entry_click`。LINE、Instagram、その他CTAは別成果として扱う。
- 成功判定の優先順位は freshな記事帰属実予約、freshな施設全体実予約/同週手入力、予約意図（代理指標）、判断保留。
- 判定ラベルは `読まれるが予約意図弱い` / `予約意図未計測`。旧 `keyEvents` は分類不能な旧データであり予約意図へ変換しない。
