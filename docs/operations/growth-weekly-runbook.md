# グロース運用 指示書(AI 実行用ランブック)

THE PICKLE BANG THEORY のグロース運用を AI が行うための手順書。
`claude -p` でこの手順を渡して実行する想定。設計の「② AI が分析 → ③ 成果物」を担う。

- 設計書: [2026-06-12-growth-loop-mvp-design.md](../superpowers/specs/2026-06-12-growth-loop-mvp-design.md)
- データ取得実装: `scripts/growth/`(`npm run growth:fetch`)
- 記事トーンの参考: [ai-news-prompt.md](./ai-news-prompt.md)

## 2つの実行モード

| モード | いつ | 何をするか |
|--------|------|-----------|
| **週次モード** | 自動・毎週木曜朝 | データ分析 → 週次レポート(Notion)→ 記事ネタ案を提案(Notion に `提案中`)。**記事下書きは作らない** |
| **下書きモード** | 手動・人間が承認した後にいつでも | 「記事ネタ案」DB の `承認` を拾い、コンテンツ+画像チームで microCMS 下書きを作る |

承認のサイクル: 週次モードがネタ案を出す → 人間が Notion で `承認`/`却下` → **下書きモードを手動実行すると即反映**(承認分が下書き化)。webhook は使わず、実行時に Notion を読む。

> 実行例(PC 側、想定): 週次 `npm run growth:weekly` / 手動 `npm run growth:drafts`(いずれも内部で `claude -p` に該当モードの指示を渡す。具体的なコマンドは Windows セットアップ時に確定)。

| 用途 | 先 |
|------|----|
| 週次レポート | Notion DB「週次グロースレポート」 data source: `collection://49694014-8e7d-4e9c-b94c-620341c4fb2e`(URL: https://app.notion.com/p/02e56ff5cdfd4fb29146225dbb51561e) |
| 記事ネタ案(承認ゲート) | Notion DB「記事ネタ案」 data source: `collection://5adab8b1-f182-4123-b963-9463a2580d4a`(URL: https://app.notion.com/p/057f4e5afac243a885a323d1f4b492ba) |
| 記事下書き | microCMS(MCP 経由・**下書きのみ**)。**承認済みネタ案のみ**下書き化 |

## 基本原則(厳守)

1. **本番を直接変更しない**。microCMS は下書き作成のみ。公開・マージは人間が行う
2. **根拠のない提案を出さない**。各施策に「どの数字がそう示すか」と確度(高/中/低)を必ず添える
3. **ブランドの世界観を守る**。配色・トーン・世界観の変更提案は案出しまで。決定は人間
4. **専門用語を避ける**。スタッフ(非エンジニア)が読む前提で言い換える
   - 例: 「CTR 1.2%」→「表示された100回のうち1回しかクリックされていない」

## 週次モード(自動・毎週木曜朝)

### 1. データ取得
- `npm run growth:fetch` を実行する
- 標準出力の JSON、または `data/snapshots/<実行日>.json` を読む
- JSON 構造: `period`(対象週)/ `priorPeriod`(前週)/ `ga4` / `gsc` / `errors`
- `errors` が空でないソースは「データ取得失敗」として扱い、レポートにその旨を明記(推測で数字を埋めない)

### 2. データの読み解き
- GA4: セッション・ユーザー・エンゲージメント率・キーイベント、チャネル別/デバイス別/人気ページ/ランディングページ、各前週比
- GSC: クリック・表示・CTR・掲載順位、上位クエリ/上位ページ/クエリ×ページ/デバイス別、各前週比
- 特に注目すべきシグナル:
  - **CTR ギャップ**: 表示回数が多いのに CTR が低いクエリ/ページ(タイトル・メタ改善の好機)
  - 掲載順位が 5〜15 位のクエリ(あと一押しで上位化しうる)
  - 前週比で大きく動いたチャネル・ページ
  - 対応するページが無い流入クエリ(新規コンテンツの好機)

### 3. 外部文脈の補強(Web 検索)
複数のスケールで横断的に調べ、施策の妥当性やネタの裏付けに使う(新しいデータパイプラインは作らない)。

- **地域(市川・本八幡・千葉)**: 近隣の動向・競合施設・地域イベント
- **東京・首都圏**: ピックルボール施設の増加状況、都市部のトレンド、メディア露出
- **日本全国**: 国内の競技人口・大会・協会の動き、季節要因(大会シーズン、長期休暇、企業レク需要)、報道
- **世界**: 海外(米国等)のプロツアー・用具・施設運営・マーケティングのトレンド(国内に先行する話題は記事ネタ・差別化の宝庫)

スケールの大きい話題(世界・全国)は「国内・地域でこれから来るネタ」の先取りに、地域の話題は「今すぐ刺さる集客」に使い分ける。

### 4. 施策立案 ―― 「プロのマーケターチーム」で分析する

単一視点で結論を出さず、**役割の異なる専門家サブエージェントを並列起動して多角的に分析 → マーケティングディレクターが統合**する。Task/Agent ツールで各ロールを並列ディスパッチし、各自に「2.のデータ」「3.の外部文脈」を渡す。

**分析チーム(並列・各自が所見を返す)**

| ロール | 視点 | 主に見る |
|--------|------|----------|
| SEO/検索アナリスト | 検索流入の最大化 | GSC: CTRギャップ、掲載順位5〜15位、未対応の流入クエリ |
| ローカル/地域マーケター | 市川・本八幡の地域集客 | 地域クエリ、競合、季節・イベント、コミュニティ |
| CRO/コンバージョン担当 | 来店・予約への転換 | GA4: 導線・離脱・デバイス・キーイベント計測・予約導線 |
| ブランド戦略家 | 長期ポジショニング | ブランド世界観との整合、トーン、安っぽくならないか |

各ロールの返答は「発見 / 根拠(数字・クエリ名)/ 推奨施策 / 確度」に圧縮させる。

**統合(マーケティングディレクター役 = メインが実施)**
- 各所見を突き合わせ、重複を排除し、インパクト × 実現性 × 安全性で順位付け
- **最大3件**に絞る。各施策に必ず付ける:
  - 施策名(平易な言葉)
  - 根拠(具体的な数字・クエリ名。複数視点が支持するものを優先)
  - 確度(高/中/低)
  - 想定アクション(コンテンツ系/メタ改善系/デザイン提案系のいずれか)
- ロール間で意見が割れた点は「論点」として簡潔に併記(人間の判断材料)

### 5. Notion へレポート作成
data source `collection://49694014-8e7d-4e9c-b94c-620341c4fb2e` に1行(1ページ)追加:
- プロパティ:
  - レポート(タイトル): `週次レポート YYYY-MM-DD〜YYYY-MM-DD`
  - 対象週開始: `period.start`
  - セッション / セッション前週比% / クリック_GSC / 表示回数 / 平均掲載順位: 対象週の値
  - 施策提案数: 今回の提案数
  - ステータス: `新規`
- ページ本文の構成:
  1. サマリー(今週の数字と前週比を平易に。良かった点・気になる点)
  2. 施策提案(最大3件。各: 根拠・確度・想定アクション)
  3. データの注意点(取得失敗・データ不足があれば明記)

### 6. 記事ネタ案を提案する(本文は書かない)

**この週次モードでは下書きを作らない。** 案出しのみ。承認後の下書き化は別の「下書きモード」で行う。

- **コンテンツ戦略担当**が、4.の施策と 2.〜3.(データ・外部文脈)を基に **記事ネタ案を3件**立案
- 「記事ネタ案」DB(`collection://5adab8b1-f182-4123-b963-9463a2580d4a`)に各案を1行追加:
  - タイトル案(タイトル)/ 概要(1〜2文)/ 優先度(高・中・低)/ 対象週開始 / ステータス=`提案中`
  - ページ本文に「狙うクエリ・読者像・根拠(数字)」を簡潔に記載
- 提案するだけで終わる。承認は人間が後で行う

### 7. 完了報告(週次モード)
- 作成した週次レポートの Notion URL
- 今回新規提案した記事ネタ案の件数(`提案中`)
- 次アクション喚起: 「記事ネタ案 DB で承認/却下をしてください。**承認後に『下書きモード』を実行**すると下書きになります」

## 下書きモード(手動・承認した後にいつでも)

承認済みの記事ネタ案を、コンテンツ+画像チームで microCMS 下書きにする。週次モードとは独立に、**人間が承認した直後に実行できる**(承認の即時反映)。

### 手順
1. 「記事ネタ案」DB から `ステータス = 承認` の行をすべて取得(無ければ「承認済みなし」と報告して終了)
2. 各案を **コンテンツ作成チーム** で執筆
3. **画像チーム** で画像を用意(**アイキャッチ必須**、本文画像は任意)
4. microCMS MCP で **下書き(draft)** 作成(**公開しない**)。title / slug / locale=ja / category / excerpt / displayMode=html / bodyHtml / **eyecatch(必須)** を埋め、末尾に「AI生成の下書き。公開前に確認を」
5. 当該行の `ステータス` を `下書き作成済み` に更新し、ページ本文に microCMS 下書きのタイトル/ID を追記
6. `却下` の行は無視する

**コンテンツ作成チームの工程**(Task/Agent でディスパッチ)
1. **構成担当** ― 承認案と検索意図から、狙うクエリ・読者像・見出し構成を作る
2. **SEOライター** ― 構成に沿って執筆(狙うクエリを自然に。地域名=市川・本八幡を適切に)
3. **ブランドボイス編集** ― [ai-news-prompt.md](./ai-news-prompt.md) のトーンに合わせ推敲。専門用語を平易に、安っぽい・煽り表現を排除
4. **ファクト/校正チェック(並列可)** ― 事実誤り・誇大表現・効果の断定・誤字、ルール等の事実確認

**画像チームの工程**(プロのデザイナー・写真家・イラストレーターのチーム)

> 方針: **サイトの世界観に合わせる必要はない。記事の内容に最も合った画像**を作る。表現形式(写真風/イラスト/図解)は記事ごとにアートディレクターが選ぶ。

1. **アートディレクター** ― 記事の内容・読者・検索意図から、最適な画像を設計する
   - **アイキャッチ(必須)**: 記事の主題を一枚で的確に表す。記事ごとに必ず1枚。**文字入れは避ける**(記事カード/OGP で日本語が崩れて見えるのを防ぐ)
   - **本文画像(任意)**: 説明を助ける箇所にのみ。無理に入れない。**文字入れOK**(図解・ラベル・キャプション等)
   - **表現形式を記事ごとに判断**する。例: 初心者ガイド→親しみやすい写真風 or やさしい図解、ルール解説→図解イラスト、業界トレンド→写真風、季節記事→季節感のある写真風。記事内容と矛盾しない題材にする(例: 屋内施設の記事に屋外コートを出さない)
   - 担当ロールを形式に合わせて起用: 写真風=**写真家**、イラスト/図解=**イラストレーター**。レイアウトや配色の整えは**デザイナー**
2. **画像生成** ― `openai-image-gen` スキル(gpt-image-2)で、選んだ形式に沿ったプロンプトで生成。アイキャッチは記事カード/OGP 向けに横長(16:9 目安)、文字なし。本文画像は文字入れ可(図解等)
3. **画像選定/品質チェック** ― 生成物から「記事内容と合っているか」「プロ品質か(安っぽくない・破綻=不自然な手指/歪みが無い)」で選ぶ。**文字を入れた本文画像は、文字が正しく読めるか・日本語が崩れていないかを必ず確認**し、崩れていたら再生成(難しければ文字なしで生成し、デザイナーが後から正確な文字を載せる)。NG ならプロンプトを直して再生成
4. **アップロード/添付** ― 採用画像を `npm run growth:upload-media -- <画像パス>` でアップロードし、出力された microCMS アセット URL を取得。`microcms_patch_content`(`isDraft: true`)で下書きの `eyecatch`(必須)/ 本文 img に設定する
   - MCP の `upload_media`(base64)は大きい画像で不確実なため**使わない**。必ず上記スクリプト経由でアップロードする(管理 API キーが `.env` の `MICROCMS_MANAGEMENT_API_KEY` に必要)
   - 画像は 5MB 上限。生成画像が大きい場合は事前に縮小する
   - `OPENAI_API_KEY` 未設定で画像生成できない場合は、その旨を報告し、アイキャッチ無しでは公開しないよう人間に促す(下書き自体は本文のみで作成)

### 完了報告(下書きモード)
- 下書き化した記事のタイトル / microCMS 下書き ID / 使用画像枚数
- 画像生成できなかった場合はその理由

## データに関する注意

- **GA4 タグは 2026-06-10 頃に導入**。それ以前の期間は GA4 データが存在しない(空でも正常)。前週比が出せない場合 `deltaPct` は `null` になる(「前週データなし」と表記する)
- GSC は計測タグと無関係に履歴を持つため、過去週も取得可能
- 対象週は「直近の確定した完全な週(月〜日)」。GSC の反映遅延(2〜3日)を見込み、実行は木曜朝
- 数字は丸めて提示(セッションは整数、率は小数1位、順位は小数1位)

## やってはいけないこと

- microCMS の記事を公開する / 既存記事を編集する
- サイトのコードを変更する・PR を作る(本 MVP では提案文に留める)
- 取得できなかった数字を推測で埋める
- 確度の根拠を示さずに施策を断定する
