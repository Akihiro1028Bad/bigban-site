週次の下ごしらえは**クラウドルーチン `weekly-driver`(木曜 10:00)が自動で行い、結果はメッセージで届く**

  Claude Code をこのリポジトリで開き「週次分析やろう」と言えば、以下の手順を対話でそのまま回せる。

## 週次セッション(毎週木曜・15〜20分)

Claude Code をこのリポジトリで開き、「週次分析やろう」と言うだけ。手順:

```
【毎週やる】
① 予約ペース : 今週の新規予約・キャンセル・来週の埋まり(台帳)
② 稼働の谷   : 直近7日+今後7日の曜日×時間帯で空きが目立つ枠(主KPI=稼働率)
②'実験レーン : 判定日到来分の判定 → 空いた枠に新提案1〜2案を補充(施策台帳v2・下記)
③ 流入速報   : query.mjs(既定7日)の前週比。急変だけ拾う
④ 一次情報   : オーナーから→現場の肌感・イベント予定・打ち手・システム変更
→ 出力: 今週のアクション1〜2個(なければ「なし」でよい)

【月初の週だけ追加(+15分)】
⑤ 月次確定   : 前月の稼働率・リピート率・ビジター→会員転換・PBT Club推移
⑥ SEO        : query.mjs --days 28 の取りこぼしクエリ→記事ネタ判定
⑦ 記事成績   : query.mjs --days 28 の「## 記事成績」→継続/改稿/看取り判定(旧 review-due の代替)
              + IG フォロワー・口コミ現状値の共有
```

### コマンド

```bash
node scripts/analytics/query.mjs            # 週次(直近7日 vs 前7日)
node scripts/analytics/query.mjs --days 28  # 月初(28日窓 + SEO詳細)
```

## ②' 実験レーンの判定と補充(施策台帳 v2)

施策は月次バッチではなく**カンバン**で回す。台帳は Notion「施策提案」DB(状態 / 種別 / ベースライン値 / 実装リンク / 学び を追加済み)。

```
提案中 ─人間─▶ 採用 ─▶ 計測中 ─検証日─▶ 判定待ち ─▶ 勝ち/負け/引き分け ─▶ 学びを1行記録
   └─人間─▶ 却下(理由1行)                │
                            判定待ち2週間放置 ─▶ 撤去候補(実装を戻す)
```

- **WIP は同時2件まで**（計測中＋本番で影響が残る判定待ち）。しかも別指標・別ページ面に限る(同じ面で2本走らせると帰属が壊れる)。
- **成功指標は大カウンタ5つから選ぶ**: `reservation_click` / `reserve_entry_click` / 実予約件数 / 対象ページ PV / HYROX 枠実予約（週平均10件未満のあいだは判定ウィンドウ最短4週）。
  提案時に**イベント名・閾値・検証日**まで確定させる。決まらない施策は起票しない。
- 判定ウィンドウは最短2週。期間や変化率だけでは効果を確定しない。共通契約のデータ品質・事前閾値・交絡確認を行い、データ不足は判定待ち、差を確認できない場合は引き分けとする。
- 検証日が来たら、**ベースライン値 vs 実測を並べて判定案まで作る**。人間は「同意」か「覆す」だけ。
- 判定案は共通契約の**時刻付き48時間方式**で扱う。提案識別子・ISO日時を記録し、異議は対話からも台帳へ転記する。日付だけの旧行は自動確定しない。
- **判定待ちのまま2週間放置されたら自動で撤去候補**へ落とし、撤去のdraft PRを提案する。本番反映は人間が判断する。
- 枠が空いたらその場で新提案1〜2案を補充する。季節・イベントの割り込み提案(`docs/growth/seasonal.md`)は WIP と無関係に出せる。
- 判定が確定したら**学びを1行** `docs/growth/playbook.md` に追記する(人間レビュー後に PR でコミット)。
  提案前に必ずプレイブックを読み、負け筋を再提案しない。

## 台帳の個人情報の扱い

リスクは「AI が読むこと」ではなく「**どこに残るか**」。会話は画面で台帳を見るのと同じだが、ファイル・コミットは永続する。

| 場面 | 方針 |
|---|---|
| **読む・会話に出す** | **可**。氏名・生年月日(年齢)・性別・住所(商圏)まで個票で見てよい。離反検知・常連把握・ビジター→会員転換・重複登録チェックなど、集計値では不可能な分析に必要 |
| **取得しない** | 電話番号・メールアドレス。分析価値がなく漏洩時の実害だけ大きい。`SELECT *` を避けて必要な列だけ指定する |
| **書き出さない(厳守)** | ファイル・レポート・コミット・記事・Notion ページ・Artifact に個人を残さない。**git 履歴は消せないため最大の漏洩経路** |
| **公開物** | 出すなら市区町村レベルの集計まで(「本八幡・市川で6割」は可、個人が特定できる粒度は不可) |

## 集計ルール

- **時間帯の表記ゆれ**: 台帳の `時間帯` は `10:00～12:00` / `10:00-12:00` / `10:00〜12:00` が混在。集計時は開始時刻(先頭5文字)で正規化する。
- **ベースライン**: 予約システム移行(2026-08-03 完了)前の台帳は不完全。**需要トレンドは 2026年8月以降のデータだけで判断**し、7月以前との比較を根拠にしない。
- **GA4 クロスドメイン断絶(2026-08-07 導入)**: labola 側に測定ID `G-XEP1C5L70P` を設置し、自社サイト→labola のセッションが継続するようになった。それ以前の labola 配下ページは**別 Direct セッション**として計上されている。従って (1) チャネル別セッション(特に Direct)と labola 配下ページのセッション数は 8/7 前後で非連続、**チャネル系の前週比は 8/14 以降(比較の両側が新仕様)を正**とする。(2) `labola_reserve_complete` のチャネル帰属は **8/7 以降のみ有効**(それ以前は全件 Direct に落ちている)。(3) 決済往復(`fep.sps-system.com` / `api3.veritrans.co.jp`)の参照元除外を GA4 側で設定するまで、完了イベントの一部は Referral(決済代行)に化ける。
- **稼働率**: 共通契約に従い、A/B/C別に重複を統合した占有時間÷提供可能時間。予約行数×2時間は使用しない。HYROXは別集計とする。
- **指名クエリ**: 「ピックルバン」「pickle bang」「PBT」「セオリー」系は指名。SEO の伸びしろ判断は非指名クエリで行う。判定ロジックの正準実装は `scripts/analytics/articleMetrics.mjs` の `isBrandQuery`。
- **記事成績の指標定義**(`## 記事成績` セクション):
  - **主指標は GA4 の入口セッション**。GSC を主指標にしない理由は、記事流入の約1/4を占める Yahoo 経由が GSC に写らないため(2026-08-12 実測)。8/7 のクロスドメイン導入による非連続は、記事の入口セッションには影響しない。
  - **CTAは100PVあたりのクリック回数**。一般クリックと複数クリックを含むため、100を超え得る。予約転換率ではない。
  - 記事の範囲は `/columns/` と `/news/` の**両方**。`/news/` にも SEO 記事(例: hyrox-official-training-gym)があり、columns だけに絞ると欠落する。

## 判断の型

- ③で前週比 ±30% を超える変動があれば、原因(記事公開・SNS・システム変更・季節)を④の一次情報と突き合わせてから解釈する。数字だけで断定しない。
- ⑦の記事判定は**入口セッションを主指標**に、次の順で当てる(上から評価して最初に当たったものを採る):

| 状況 | 打ち手 |
|---|---|
| 順位≤5 かつ 非指名CTR<5% | タイトル・description 改稿 |
| 非指名表示≥100 かつ 順位4〜10 | 本文強化・内部リンクで押し上げ |
| 入口S≥10 かつ 100PVあたりCTA<8回 | 記事内リンクの目的・配置を確認。予約成果の不足とは断定しない |
| 入口S≥5 | 継続(触らない) |
| 非指名表示<10 かつ 入口S<3 | 看取り候補。季節・キャンペーン終了なら放置でよい |

  判定を当てる前に必ず**指名表示の列を見る**。指名クエリはホームがクリックを取るため記事側の CTR が低く出るのが正常で、ここを見落とすと不要なタイトル改稿を提案してしまう(2026-08-18 の棚卸しで実際に誤判定した)。
- アクションは毎週最大2個。積み残しは翌週に持ち越さず、月初⑤で棚卸しする。
