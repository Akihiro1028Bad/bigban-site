# 分析・判定の共通契約

日次・週次・月次・対話分析の集計と判定はこのファイルを正典とする。取得・集計はスクリプトまたは明示した式で行い、AIは解釈と提案を担当する。情報不足を推測値で補わない。

## 取得状態と比較期間

- 値は「取得成功した実数」「取得不可」「観測中」を区別する。成功した完全なレポートに対象行がなければ0。API失敗、取得上限、未成熟データの欠落を0としない。
- 比較は同じ指標・対象・期間長で行う。前期値は直接取得する。上位抜粋の14日値−7日値で復元しない。前期0は変化率を出さず実数を示す。
- GA4の前日値は速報。ゼロや急変だけでサイト障害・需要減を確定しない。前日の異常は他の計測やHTTP確認で裏付け、確定前なら「速報・要再確認」とする。
- GSCはPT基準・既定は確定データのみ。GA4と同じ日付文字列でも観測窓は一致しない。取得期間・取得日・鮮度・上位抜粋かどうかを併記する。
- `query.mjs --days 28`は28日移動窓であり、前暦月の確定値と呼ばない。月次で暦月データを取得できなければ暦月の指標は取得不可とし、28日値を参考値として別に表示する。

## 日次用の直接比較

```bash
node scripts/analytics/query.mjs --days 1 --prev-offset 7 --monitor-only --json
node scripts/analytics/query.mjs --days 7 --monitor-only --json
```

`periods.current/previous`と、`metrics`の`name/current/previous/deltaPercent/currentError/previousError`を読む。`/reserve`・`/hyrox`は日本語・英語の対象ページPVの合計。各CTAはイベント回数であり利用者数ではない。`null`は取得不可で、比較を保留する。監視項目の一部が取得不可ならJSONを出したうえで終了コード1になるため、出力を捨てず成功した項目は使う。OAuth等の開始前失敗はJSONが出ないため全監視項目を取得不可とする。

## 台帳の取得範囲

| 用途 | 日付・対象集合 |
|---|---|
| 新規受付ペース | 受付日時が対象期間内の予約 |
| キャンセル発生数 | キャンセル日時が対象期間内の予約。日時がなければ発生数は取得不可。受付期間内の現在キャンセル件数とは区別 |
| 稼働・利用・売上 | 利用日時が対象期間内の有効予約。受付が28日より前でも含める |
| 今後の予約 | 利用日時が今後の対象期間内の予約。受付日で打ち切らない |
| 再訪・離反・コホート | 観測開始以降の利用履歴。最終利用日・初回観測日・利用回数を会員単位で集計 |

受付日順のビューを28日で打ち切った結果を全用途に流用しない。必要なフィルタを適用できなければ、必要範囲を全ページ取得する。取得が完了しない指標は取得不可とする。利用日・受付日時・金額・会員番号の欠損件数も記録する。空の会員番号を1人の会員として集計しない。個人情報は成果物に残さない。

30日転換率・90日生存率は、その観測期間を満たした対象者だけを分母にする。未到達者は観測中とし、失敗に数えない。履歴開始以前を確認できないため「初回来訪」ではなく「初回観測」と区別する。データは2026年8月以降を利用し、それ以前との需要比較を行わない。

## 稼働・単価の定義

- ピックルの稼働率：A/B/Cの各コートで利用時間区間の重複を統合した占有時間 ÷ 同じコートの提供可能時間。イベント参加者が13行でも同じ2時間枠なら2時間。1時間予約は1時間で数える。開始・終了時刻がなければ正確な稼働率は取得不可。
- 提供可能時間は通常3面×17時間×日数から休業・提供不能時間を除いたもの。分母の情報が欠ける場合は「通常営業時間を分母とした参考値」と記す。HYROXの予約・売上はピックルの分子に混ぜず、設備・定員に対応した別指標とする。
- RevPACH：上記A/B/Cの対象利用期間の売上 ÷ A/B/Cの提供可能時間。参加者単位の料金と予約単位の料金を区別し、売上の重複計上をしない。金額欠損率を併記し、30%超は判断根拠にしない。
- ピークは暫定で平日18時以降＋土日終日。18時をまたぐ予約は時間区間で分割する。料金表の境界とは別の分析定義である。
- MEP：対象28日の有効な利用が2回以上あるユニーク会員数。ピックルとHYROXを別に集計し、横断値は会員番号の和集合とする。未来の予約は来訪回数へ含めない。
- RPP：同じ期間の、識別できる利用会員に帰属する売上 ÷ その売上に対応するユニーク利用会員数。MEPだけを分母にしない。会員番号・金額欠損による対象外を明記する。
- TennisBear未反映のイベントは「未取得」と注記し、Labolaの参加数ゼロから集客不振を判断しない。

## クリックとファネル

記事のCTAは一般クリックを含む「100PVあたりクリック回数」。複数回のクリックにより100を超え得る。予約転換率とは呼ばず、記事の性質・設置リンクを確認して参考に使う。

`reservation_click`は外部予約へのクリック、`reserve_entry_click`は自社予約案内への入口。実予約は台帳等で別に確認する。Labolaの段階別PV比は参考比率であり、同一セッション内の順序を検証できない限り「通過率」「離脱率」と呼ばない。取得していない完了イベントをクリックから推定しない。

## 施策判定

1. 対象・期間・計測仕様が一致し、必要なデータが取得できているかを先に確認する。欠損なら判定待ちを維持する。
2. 実装が本番に反映された日時から最短2週（週10件未満のHYROX枠は最短4週）を観測する。この日数だけで検出力が保証されるわけではない。
3. 提案時に決めた閾値を使用する。未設定の既存施策の暫定境界は+15%以上＝改善候補、-10%以下＝悪化候補、-10%より大きく+15%未満＝判断保留。一致する境界は1つだけとする。前期0・分母不足は実数のみで判断を保留する。
4. 季節・流入構成・同時変更を確認する。単純な前後比較だけで因果効果を断定しない。「横ばい＝負け」としない。データが十分でも差を判断できない場合は「引き分け（差を確認できず）」を提案し、データ不足は判定待ちに残す。
5. 閾値を超えた候補は根拠と交絡要因を確認して勝ち／負けの判定案にする。勝敗は自動的なコード変更・公開を許可しない。

WIPは計測中に加え、本番で影響が残る判定待ちを含めて最大2件。別指標でも同じ予約導線に作用する施策は干渉を確認する。

48時間の異議期間を使う場合、検証メモに`判定案(未確定) 2026-09-07T10:00:00+09:00:`のような時刻付きISO日時と提案識別子を記録する。日付だけの旧行は自動確定しない。対話での異議はその提案に紐づけて判断者メモへ記録して初めて日次から参照できる。確定直前に状態・提案・判断者メモを再取得し、変更・異議・不明確なメモがあれば保留する。同じ提案の再実行は確定済みなら無操作とする。
