> 施策判定から得た「学び」を1行ずつ積む台帳。設計: `docs/superpowers/specs/2026-08-05-growth-copilot-design.md` §8
> **全ルーチン(日次ウォッチ / 週次ドライバー / 月次ストラテジスト)のプロンプトがこのファイルを読む。** 負けた打ち手を再提案させないための唯一の記憶装置。

## フォーマット

| 列 | 内容 |
|---|---|
| 日付 | 判定が確定した日(YYYY-MM-DD) |
| 施策名 | 施策台帳(Notion「施策提案」DB)の行と同じ名前 |
| 種別 | バナー / ポップアップ / セクション / ページ / 記事 / ニュース / その他 |
| 判定 | 勝ち / 負け / 引き分け / 撤去 |
| 学び | **1行**。次の提案の判断材料になる形で書く(「何が効いた/効かなかったか」であって、感想ではない) |

## 運用ルール

- 追記は**判定確定時のみ**。週次ドライバーが1行を提案し、人間レビューを経て通常の PR フローでコミットする(ルーチンが自分でマージしない)。
- **1施策1行**。考察が長くなるものは `docs/reviews/` に別文書を作り、ここには結論1行とリンクだけ置く。
- 負け判定の打ち手は、**同一の面 × 同一の指標では再提案しない**。条件を変えて再挑戦する場合は、施策台帳の仮説欄に「前回から何を変えたか」を明記する。
- 数字を書くならベースライン→実測の1組だけ(例: `750→? /週`)。表や詳細は施策台帳側に置く。
- **個人情報は書かない**(`docs/operations/interactive-analysis-runbook.md`「台帳の個人情報の扱い」)。書けるのは集計値まで。
- 引き分け(検出下限未満)は「効かなかった」ではない。学び欄に「差が検出できなかった」と書き、指標の選び方を疑う。
