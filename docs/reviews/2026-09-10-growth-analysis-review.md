# 分析ツール・フロー再レビュー(2026-09-10)

> 問い: 「週次ドライバー/日次ウォッチ/`query.mjs` の分析は、プロ級のマーケティング判断を支えられる品質か」
> 調査方法: 2026-09-10 の週次ドライバーを実際に一周(GA4/GSC・Notion 台帳 892 行・会員台帳 364 行・Labola スナップショット・Morning Business Brief)し、そこで踏んだ摩擦を設計書(`docs/superpowers/specs/2026-08-05-growth-copilot-design.md`)・共通契約(`docs/growth/analysis-contract.md`)・`scripts/analytics/*.mjs` と突き合わせた。
> 本文の数字はすべて集計値。個人情報は含まない。

## 1. エグゼクティブサマリ

1. **「検証を一周させる」骨格は正しく機能している。** 8月に2件が判定まで到達し(負け1・引き分け1)、学びが `playbook.md` に残った。v1 の死因(提案だけ増えて検証 0 件)は解消済み。
2. **しかし分析の実体は「毎週その場で手書きする集計」に依存している。** 稼働率・RevPACH・MEP・離反・集中度は、今日もルーチンが即席の Node スクリプトで計算した。定義は共通契約にあるが、実装はどこにもない。再現性がなく、個人情報が毎週コンテキストを通過する。
3. **成功指標が「件数」なので流入の増減に埋もれる。** 今週 reservation_click +32% だがオーガニックセッションは +74%。件数のままでは施策効果と流入変動を分離できない(8月の「負け」判定の一因)。**率(分母つき)へ置き換えるべき。**
4. **時系列がどこにも残らない。** 週次の数字はメッセージに書いて流れるだけ。4週トレンド・季節性・異常の基準線は毎回「±30%」の経験則で代用している。
5. **設計書の前提が2〜3倍に膨らんだ。** 設計時(2026-08-04)の reservation_click 約 750/週・オーガニック約 830 セッション/週に対し、今週は 1,397 / 2,818。設計書 §11「A/B テスト基盤は流入が2倍になったら再検討」の条件を満たした。判定閾値・ウィンドウ・WIP 上限は再校正の時期。

推奨は **Tier 1(4件・2週間)を先に入れる**こと。派手な新機能より、この土台が伸びしろの大半を占める。

## 5. 改善ロードマップ

### Tier 1 — 2週間で入る・効果が大きい(本 PR の実装タスク。§7 に受け入れ条件)

1. **週次 KPI 履歴 DB(Notion)を作り、毎週 1 行書く**
2. **`scripts/analytics/ledger.mjs` — 台帳集計を共通契約どおりコードに固定する**(必要列だけ取得し個人情報を最初から読まない)
3. **`query.mjs` の4点拡張**: GSC 前期取得(新出/消失/順位変動) / CTA location 別の前期比 / Referral・Unassigned のソース内訳 / `labola_reserve_complete` のチャネル別監視
4. **成功指標を「率」へ(共通契約の改定)**: `イベント ÷ セッション` または `対象 location クリック ÷ 対象面 PV`

### Tier 2 — 1ヶ月

5. **取り込み側で PII フリーの分析ミラーを作る**: ローカルの予約メール取り込みが、会員キー(メールのハッシュ)/ 利用日 / 受付日時 / **キャンセル日時** / コート / 時間帯(正規化済み) / 金額 / 予約種別 / 会員タイプ だけの分析用 DB を別に書く。§2 の #2・#7・#8・#9 が同時に消える
6. **実験マニフェスト + 自動判定材料**: 施策台帳の行に JSON(指標・location・面・ベースライン窓・閾値)を持たせ、`query.mjs --experiment <id>` がベースライン vs 実測を並べて出す。提案時に**検出力チェック**(過去 8 週の週次分散から必要観測数)を走らせ、検出不能な実験を起票させない
7. **判定閾値・ウィンドウ・WIP の再校正**: KPI 履歴 4 週で分散を実測して閾値を再設定。WIP を「3 レーン(HYROX 台帳指標 / 記事・GSC 面 / サイト大カウンタ面)各 1 本」へ(§6 改定案 B)

### Tier 3 — 四半期(マーケティング戦略そのもの。ルーチンの対象外)

8. **オフピーク商品化**: 今週の稼働はピーク 63% vs オフピーク 23%。ルーチンが触れるのは文言だけなので、谷を埋めるのは商品(平日昼パス・法人/貸切 P10・101 型入門クラス)。人間の四半期テーマとして扱う
9. **リテンション・レーン(第 6 の指標)**: 離反予備軍 17 → 26 人と増え始めた一方、対応する面(LINE・メール)も指標(再活性率)もない。Tier 2-5 のミラーで「30日以内 2 回目転換率」「90日生存率」を週次で追い、再活性の打ち手をオーナーが持つ
10. **顧客の声**: Labola 予約完了メールに 1 問(来訪理由・知った経路)。GA4 のチャネルより信頼できる獲得経路データになる
11. **A/B テスト基盤の再検討**: ホーム・/reserve のセッション量なら 50/50 配信で 2 週判定が現実的。feature flag + GA4 `experiment_variant` カスタムディメンションの軽量版から

### やらなくていいこと

- 分析バッテリー項目の追加(11 項目で十分。空欄を埋める方が先)
- リサーチの拡張(R1 が機能している。同日重複ページの解消を優先)
- ダッシュボード UI(KPI 履歴 DB ができれば Notion のチャートで足りる)

## 7. Tier 1 実装タスク(受け入れ条件つき)

すべて通常の PR フロー(TDD・lint・テスト green・人間レビュー)。`scripts/analytics/**` はルーチンのガードレールで変更禁止のため、**対話セッションで実装する**。

### T1-1. 週次 KPI 履歴 DB

- Notion に「週次 KPI」DB を新設(列: 週キー(月曜) / 新規受付 / 有効利用 / 稼働率 A・B・C / ピーク稼働 / オフピーク稼働 / RevPACH / 金額欠損率 / HYROX 件数 / HYROX 売上 / MEP ピックル / MEP HYROX / 再訪率 / 離反予備軍 / 新規会員 / PBT Club 累計 / reservation_click / reserve_entry_click / /reserve PV / /hyrox PV / オーガニックセッション / 記事入口セッション / 備考)
- 週次ドライバーが Step 1 の末尾で 1 行を upsert する(同じ週キーがあれば更新)。`weekly-driver.md` に手順を 10 行以内で追記
- 受け入れ: 2 回目の実行で「前週の行を読み、4 週トレンドを DB から出す」ことができる。DB に個人情報列がない

### T1-2. `scripts/analytics/ledger.mjs`

- 入力: Notion API(`filter_properties` で **利用日・受付日時・コート・時間帯・予約種別・会員タイプ・会員番号・ステータス・金額** のみ)。トークンは env(`GROWTH_NOTION_TOKEN` / `GROWTH_NOTION_RESERVATION_DB` / `GROWTH_NOTION_MEMBER_DB`)。ローカルは `.env.local`、クラウドは env secrets
- 出力(すべて集計値・共通契約の定義):
  - 受付ペース 4 週(受付日 JST)/ 有効・キャンセル内訳
  - 曜日 × 開始時刻(先頭 5 文字で正規化)のヒートマップと谷(4 週連続 0〜1 件のセル)
  - コート別 件数・売上・平均単価・構成比(直近 7 日 + 4 週推移)
  - 稼働率 A/B/C(重複統合・提供 17h)・ピーク/オフピーク別・RevPACH・金額欠損率
  - 28 日ユニーク会員・再訪率・MEP(ピックル/HYROX)
  - 離反予備軍(2 回以上・最終利用 21 日以上前)当週/前週
  - 集中度(上位 10% のシェア)
  - 欠損件数(利用日・受付日時・金額・会員番号)
- オプション: `--as-of YYYY-MM-DD`(判定日の再現用)/ `--json`
- テスト: `ledger.test.ts` にフィクスチャ(架空データ)で各指標の入出力テスト。重複区間の統合・表記ゆれ・JST 変換・分母 10 未満で比率を出さないことを検証
- 受け入れ: `weekly-driver.md` 1-1・1-2・1-4・1-6・1-7・1-8 が「実行して読む」だけになる。氏名・連絡先・住所・生年月日を API から取得しない

### T1-3. `query.mjs` 拡張

- GSC: 前期も取得し「新出(前期 0 表示・今期 10 表示以上)」「消失」「順位 ±3 以上」を列挙。`--gsc-page <path>` で特定ページの page × query を出す(実験中の記事の判定用)
- CTA location 別: 前期を取得し前期比を併記(既存フォーマットに `(+12%)` を足す)
- チャネル: Referral と Unassigned について `sessionSource` 上位 5 を出す
- 監視対象(`monitoring.mjs`): `labola_reserve_complete` を追加し、チャネル別(`sessionDefaultChannelGroup`)の内訳を出す。8/7 以前を含む比較には注記を自動付与
- テスト: 既存 `query.test.ts` / `monitoring.test.ts` にケース追加
- 受け入れ: 週次バッテリー 1-9 ④(新出)・1-10(ドメイン内訳)・1-11 の「取得不可」が消える

### T1-4. 共通契約の改定(率ベースの成功指標)

- §6-A の文言を `analysis-contract.md` に反映。`weekly-driver.md` Step 2-4 の「成功指標」項に分母の選び方を 3 行で追記
- `monitoring.mjs` に率(`reservation_click / sessions` 等)を併記
- 受け入れ: 次回起票する施策の「成功指標」「ベースライン値」が率と件数の両方を持つ
