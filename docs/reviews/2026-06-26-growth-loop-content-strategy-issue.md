# Issue draft: グロースループ改善: 記事提案・執筆・効果検証の精度向上

## 背景

現在のグロースループは、GA4/GSC の取得、Notion への記事案・施策登録、承認画面、下書き生成、成績ボードまでつながっており、基盤としては十分に強い。

一方で、運用品質をさらに上げるには「記事を増やす」よりも、以下を強化したい。

- 記事提案時点の仮説を明確にする
- 記事ごとの検索意図・事業価値・勝ち筋を残す
- AI原稿に施設固有の一次情報を必ず入れる
- 公開後28日/56日/90日の効果判定をNotionに戻す
- 新規記事だけでなく、既存記事の改善サイクルを作る

Google公式ガイドでも、検索順位操作目的の量産ではなく、読者にとって有用で、独自情報・実体験・信頼性のあるコンテンツが重要とされている。AI生成も禁止ではないが、独自価値の薄い自動生成は避けるべき。

参考:

- https://developers.google.com/search/docs/fundamentals/creating-helpful-content
- https://developers.google.com/search/blog/2023/02/google-search-and-ai-content
- https://support.google.com/business/answer/7091
- https://developers.google.com/search/docs/appearance/structured-data/article
- https://developers.google.com/search/docs/appearance/structured-data/local-business

## 目的

グロースループを「記事生成システム」ではなく、ローカル施設集客の仮説検証システムとして強化する。

具体的には、記事案の提案、下書き執筆、公開後計測、改善判断までを一貫したデータ構造で扱えるようにする。

## 推奨方針

### 1. 記事提案をタイプ別に分類する

週次提案で、記事案ごとに以下の分類を持たせる。

- `獲得`: 市川・本八幡・千葉・屋内・ピックルボール等の検索流入を狙う
- `不安解消`: 初心者、一人参加、年齢、持ち物、服装など予約前の心理障壁を下げる
- `資産`: ピックルボールとは、ルール、始め方、ラケット競技経験者向けなど長く使う基礎記事
- `比較`: 屋内/屋外、テニス/卓球/バドミントン経験者向け、他スポーツとの違い
- `イベント/ニュース`: 短期流入、SNS/LINE共有、施設の動きの可視化

月間配分の目安:

| 種別 | 目安 | 目的 |
| --- | ---: | --- |
| ローカル獲得記事 | 2本 | 市川・本八幡・千葉周辺の検索流入 |
| 不安解消記事 | 2本 | 初心者・一人参加・年齢不安の解消 |
| 資産記事 | 1本 | 長期的な内部リンク・基礎情報の受け皿 |
| イベント/ニュース | 1本 | 鮮度・SNS共有・再訪 |

### 2. 記事案Notionプロパティを追加する

記事ネタ案DBに以下のプロパティ追加を検討する。

| プロパティ | 型の例 | 用途 |
| --- | --- | --- |
| 記事タイプ | select | 獲得 / 不安解消 / 資産 / 比較 / イベント |
| 狙う読者 | rich_text | 誰向けの記事か |
| 検索意図 | select or rich_text | 場所探し / 初心者不安 / 比較 / 予約直前など |
| 勝ち筋 | rich_text | 他サイトにない施設固有の価値 |
| 想定CTA | select | 体験予約 / Instagram / アクセス / 料金確認など |
| 成功指標 | rich_text | 公開後28日で見る基準 |
| 公開後判定 | select | 継続 / 改稿 / 内部リンク追加 / 見送り |
| 判定メモ | rich_text | なぜその判断にしたか |
| 28日判定日 | date | 公開後レビュー用 |
| 56日判定日 | date | 改稿/内部リンク判断用 |
| 90日判定日 | date | 統合/資産化判断用 |

既存の `根拠` は維持しつつ、上記で「誰に、何を、なぜ、どう測るか」を補う。

### 3. 週次分析プロンプトを強化する

`scripts/growth/prompts/weekly.md` の記事提案ルールに、以下を必須化する。

- 記事タイプ
- 狙う読者
- 検索意図
- 勝ち筋
- 想定CTA
- 成功指標
- 公開後にどう判定するか

記事案は最大件数を埋めるより、強い仮説に絞る。
毎週「本命1件 + 補欠2件」程度でもよい。

提案時の優先順位は以下で判断する。

| 軸 | 高評価の条件 |
| --- | --- |
| 検索機会 | GSC表示、関連クエリ、地域検索意図がある |
| 事業価値 | 体験予約・来店・問い合わせに近い |
| 独自性 | 施設の一次情報を入れられる |
| 競合余地 | 市川/本八幡/屋内などで競合が薄い |
| 改善可能性 | 公開後に追記・内部リンク・CTA改善ができる |

### 4. AI執筆前に記事ブリーフを必ず作る

下書き生成時、AIにいきなり本文を書かせず、以下のブリーフを先に組み立てさせる。

```text
1. 想定読者:
2. 読者の悩み:
3. この記事で解決すること:
4. 検索意図:
5. 施設だから言える一次情報:
6. 入れるべき内部リンク:
7. CTA:
8. 書いてはいけないこと:
9. 公開後の成功指標:
```

特に `施設だから言える一次情報` を必須にする。

例:

- 実際のコート環境
- 初回体験で多い不安
- レンタル有無
- 駅からの行き方
- 服装・持ち物
- スタッフが見ている初心者のつまずき
- 天候に左右されないメリット
- どんな人が来やすいか

### 5. 記事構成の標準型を定義する

`docs/operations/growth-article-style.md` に以下のような標準型を追加する。

```text
H1: 読者の検索意図にそのまま答えるタイトル

冒頭:
- 結論
- この記事が誰向けか
- 施設視点で答えることを明記

H2: 悩みへの直接回答
H2: 選び方・判断基準
H2: THE PICKLE BANG THEORY でできること
H2: 初めての人が不安になりやすい点
H2: 予約・アクセス・次の行動

FAQ:
- 初心者でも大丈夫？
- 一人でも参加できる？
- 持ち物は？
- 雨の日でもできる？
```

FAQは初心者系、ローカル系、予約直前系の記事で特に有効。

### 6. CTAを検索意図別に変える

全記事で同じCTAにしない。

| 検索意図 | CTA |
| --- | --- |
| 場所探し | アクセスを見る / 体験予約 |
| 初心者不安 | 初回体験を見る / Instagramで雰囲気を見る |
| 料金比較 | 料金ページ / 体験メニュー |
| 予約直前 | 予約 / 営業時間 / Googleマップ |
| 資産記事 | 関連記事 / 始め方 / 体験案内 |

記事案の `想定CTA` と本文末尾のCTAが一致しているか、下書きチェックで見る。

### 7. 公開後レビューを成績ボードに接続する

既存の `growth:metrics` と `PerformanceBoard` を活かし、記事ごとにレビュー判定を入れる。

| 時点 | 見るもの | 判定 |
| --- | --- | --- |
| 7日 | index有無、初期表示 | noindex/未クロール問題の検知 |
| 28日 | GSC表示・クリック、GA4表示・ユーザー | 継続 / 改稿 / CTA改善 |
| 56日 | 順位・CTR・内部リンク効果 | 追記 / 関連記事追加 |
| 90日 | 長期資産性 | 統合 / リライト / 放置 |

成績ボードは将来的に以下の分類表示にしたい。

- 伸びている
- 表示はあるがクリックされていない
- 読まれているがCTAが弱い
- 要改稿
- 未計測/データ不足

### 8. ローカルSEOと記事を接続する

Googleビジネスプロフィール側と記事側の情報を揃える。

確認対象:

- 施設名
- 住所
- 最寄駅
- 営業時間
- 電話/連絡導線
- 写真
- Googleマップ
- 料金/体験導線
- 口コミへの返信
- Googleビジネスプロフィールとサイト内表記の一致

Google公式では、ローカル検索の主な要素として `関連性`、`距離`、`知名度` が説明されている。記事は特に関連性と知名度の補強に使う。

## 実装候補

### Phase 1: プロンプト・運用ルールのみ

- [ ] `weekly.md` に記事タイプ/検索意図/勝ち筋/成功指標を必須化
- [ ] `growth-article-style.md` に記事ブリーフと一次情報ブロック必須ルールを追加
- [ ] 記事案作成時の件数を「質優先」に明記

### Phase 2: Notionプロパティ追加

- [ ] 記事ネタ案DBに記事タイプ/狙う読者/検索意図/勝ち筋/想定CTA/成功指標を追加
- [ ] 既存の `growth:weekly` 出力で各プロパティへ書き込む
- [ ] 欠落していても落ちないように後方互換を保つ

### Phase 3: 公開後判定

- [ ] 公開後28日/56日/90日のレビュー対象を抽出するロジックを追加
- [ ] `growth:metrics` の結果と記事案の成功指標を並べて判定しやすくする
- [ ] 成績ボードに `要改稿` / `伸びている` / `CTA弱い` の分類を追加

### Phase 4: リライトループ

- [ ] 新規記事だけでなく既存記事改善案を週次提案に含める
- [ ] 月1回は「新規記事」ではなく「既存記事リライト週」にする
- [ ] リライト後も変更日だけ更新するのではなく、実質的な変更内容をNotionに残す

## 受け入れ条件

- [ ] 週次記事提案に、記事タイプ/狙う読者/検索意図/勝ち筋/想定CTA/成功指標が含まれる
- [ ] AI下書き生成時に、施設固有の一次情報が少なくとも1ブロック含まれる
- [ ] 公開記事について、28日後の判定をNotion上で確認できる
- [ ] 成績ボードまたはNotionで、改善対象記事を見つけられる
- [ ] 新規記事提案だけでなく、既存記事の改稿提案が運用に入る

## 注意点

- 検索順位目的の大量記事生成に寄せない
- 未確定情報、健康効果、上達保証を断定しない
- 施設の実態と違う訴求をしない
- Googleビジネスプロフィールとサイト内情報の不一致を避ける
- AIには生HTMLや本番公開を直接任せず、現行通り人間承認を挟む
